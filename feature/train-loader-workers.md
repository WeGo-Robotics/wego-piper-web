# 학습 데이터 로더 진단 — 병목 표시와 workers 권장값

> ◐ 1~4 ☑ (2026-10-28). 계산은 §6 실측으로 확인했다. 남은 것: 원격(SSH) CPU (§7-5).

학습 메트릭 카드가 **step 시간이 어디에 쓰이는지**를 보여 주고, 데이터 로더가 GPU 를
굶길 때 **num_workers 를 몇으로 올리면 되는지** 숫자로 말한다. 다음 학습의 폼에도 같은
숫자를 미리 채운다.

## 0. 왜

- 카드에 있던 "GPU 연산 병목 → AMP(bf16)·Batch가 효과적" 은 **지웠다**(같은 날). `data_s` 가
  작다는 건 GPU 가 쉬지 않는다는 뜻이지 고칠 게 있다는 뜻이 아니고, AMP·배치가 이미
  한계인지는 그 비율로 알 수 없다.
- 남은 경고는 `data_s > updt_s` 하나 — GPU 가 **절반 넘게 쉬어야** 뜬다. 30~40% 쉬어도
  말이 없고, 떠도 "늘리세요" 뿐 몇으로인지 없다.
- 폼의 Workers 칸 도움말(`data_s > updt_s면 ↑`)은 학습을 돌려 보고 숫자를 읽은 다음 손으로
  고치라는 말이다.

## 1. 로그가 알려 주는 것 (LeRobot 실측)

`lerobot_train.py` 메인 루프:

```python
start = perf_counter()
batch = next(dl_iter); batch = preprocessor(batch)   # → data_s
update_policy(...)                                    # → updt_s (loss.item() 이 동기화)
```

- 둘은 **차례로** 잰다. 그래서 **step 시간 = updt_s + data_s** 이고, `data_s` 는 GPU 가 배치를
  기다리며 논 시간이다.
- 둘 다 `log_freq` 구간 평균이다(`reset_averages`). 기본 200 step.
- DataLoader 설정은 `prefetch_factor=2`, `pin_memory=True` 이고 `persistent_workers` 는 기본값(False)이다.
  ⚠ 그래서 **에폭마다 워커를 새로 띄운다** — 그 구간의 `data_s` 는 튄다. 스크린샷의 학습은
  에폭이 약 2,650 step 이라 13구간에 한 번꼴이다.
- `data_s` 에는 `preprocessor`(정규화·GPU 전송)도 들어 있다. 이 부분은 메인 스레드가 하므로
  **workers 를 늘려도 줄지 않는 바닥**이다.

이 숫자들로 **알 수 없는 것**: CPU 가 포화됐는지, 디스크가 느린지, AMP·배치에 여유가 있는지.

## 2. 권장값 계산법

로더가 병목이면 워커 N 개가 쉬지 않고 돈다. 워커 하나가 배치 하나를 만드는 데 걸리는
시간을 **T_b** 라 하면 워커들은 T_b/N 마다 배치 하나를 내놓고, 그게 곧 step 시간이 된다.

```
updt_s + data_s = T_b / N          →   T_b = N · (updt_s + data_s)
GPU 를 안 굶기려면  N' ≥ T_b / updt_s = N · (updt_s + data_s) / updt_s
권장  N_rec = ⌈ N · (updt_s + data_s) / updt_s · 1.2 ⌉     (1.2 = 흔들림·에폭 재기동 여유)
N = 0 이면 메인 스레드가 로드하므로   T_b ≈ data_s  →  N_rec = ⌈ data_s / updt_s · 1.2 ⌉
바꾼 뒤 예상 step 시간 = max(updt_s, T_b / N')
```

**workers 로 얻을 수 있는 최대 이득은 (updt_s + data_s) / updt_s 배다.** 누가 병목인지 판정하는
대신 이 숫자를 보여 준다. 이 숫자는 거짓말을 하지 않는다.

| 상황 | N | updt_s | data_s | 대기 | 최대 이득 | 권장 |
|---|---|---|---|---|---|---|
| 스크린샷 | 4 | 0.064 | 0.002 | 3% | 1.03배 | **유지** — 늘려도 얻을 게 없다 |
| 로더 부족 (가정) | 4 | 0.064 | 0.040 | 38% | 1.63배 | T_b=0.416 → 6.5 → **8** |
| workers 0 (가정) | 0 | 0.064 | 0.300 | 82% | 5.7배 | **6** |
| 코어 부족 (가정, 20코어) | 4 | 0.030 | 0.200 | 87% | 7.7배 | 37 → 상한 **18**, 그래도 대기 41% 남음 |

### 이 계산이 틀리는 곳

- **대기가 작을 때(< 10%)는 상한만 안다** — T_b ≤ N·step 이라 N 이 충분하다는 것까지만 알 수
  있다. 이때는 권장하지 않고 **유지**한다. 줄여도 되는지는 이 숫자로 알 수 없으므로
  줄이라는 권장도 하지 않는다.
- **T_b 가 N 과 무관하다는 가정** — 코어·메모리 대역폭·디스크를 나눠 쓰면 워커가 많아질수록
  T_b 가 늘어난다. 영상 디코더가 워커마다 스레드를 따로 띄우면 더 그렇다. 그래서 이 계산은
  **낙관적**이다(실측 5~7%, §6). 대책은 셋이다. 여유 1.2 를 곱하고, 코어 상한으로 자르고,
  바꾼 뒤 다시 재서 한 번 더 고친다.
- **메인 스레드 바닥** — 워커를 올렸는데 `data_s` 가 그대로면 남은 대기는 preprocessor·디스크
  때문이다. 이 기계에서는 2~3ms 라 판정하지 않는다(§3).

### 값을 고르는 법

- 마지막 5구간의 **중앙값**을 쓴다(에폭 재기동이 튀는 구간을 거른다). 첫 구간은 버린다
  (워커 기동·cudnn 자동 튜닝이 섞인다). 3구간이 쌓이기 전에는 `warming` 이다. 기본
  `log_freq` 200 기준으로 1분 안팎이 걸린다.
- 상한은 **학습 기계 코어 − 2** 다(메인 프로세스 + pin_memory 스레드). 워커 하나가 코어
  하나쯤을 쓰고, 데몬(robotd·camerad…)은 쉴 때 거의 안 쓴다(§6).

## 3. 병목 구분 — 무엇을 보고 무엇을 말하나

| 신호 | 판정 (`reason`) | 화면 |
|---|---|---|
| 대기 < 10% | `enough` | "데이터 대기 3% · workers를 늘려도 최대 1.03배" — **처방 없음** |
| 대기 ≥ 10%, CPU 여유, N_rec ≤ 상한 | `add_workers` | "workers 4 → **8** 권장 (예상 대기 0%)" |
| 대기 ≥ 10%, CPU ≥ 90% 또는 N_rec > 상한 | `cpu_limit` | "CPU가 모자라 workers로는 다 못 메운다 (18로도 대기 41%)" |
| 구간 < 3 | `warming` | "측정 중" |

- **CPU** — 로컬은 이미 있는 `trends.latest_cpu()`(/proc/stat 차분)와 `os.cpu_count()` 를 쓴다.
  학습은 녹화·추론과 배타라 기계 전체 CPU 가 곧 학습의 CPU 다. 원격(SSH)은 아직 코어도
  CPU 도 모른다 — 상한 없이 계산만 낸다(§7-5).
- **`floor`(메인 스레드 바닥) 판정은 만들지 않았다** — 실측 바닥이 2~3ms 라(§6, N=12 에서
  data_s 0.002~0.003) 이 기계에서는 말할 거리가 없다. 다른 기계에서 workers 를 올렸는데도
  대기가 안 줄면 그때 지난 프로파일과 견주는 판정을 붙인다.
- **GPU 사용률(nvidia-smi)은 판정에 안 쓴다** — "커널이 하나라도 돌던 시간 비율" 이라 포화를
  뜻하지 않는다. 대기 3% 가 이미 같은 사실을 더 정확히 말한다.
- **AMP** — 비율이 아니라 **설정값**으로 말한다. `enough` 인데 `amp == "off"` 일 때만
  "AMP 꺼짐 — bf16을 켜면 GPU 연산이 빨라질 수 있다" 를 덧붙인다.
- **배치는 권하지 않는다** — lr·일반화를 바꾸는 학습 손잡이다. 속도 손잡이로 내놓으면 안 된다.

## 4. 화면

**(a) 학습 메트릭 카드** ([TrainingMetrics.tsx](../frontend/src/components/TrainingMetrics.tsx))

```
step 시간  ███████████████████████████████████▌  0.066s
           GPU 연산 97%                     대기 3%
데이터 대기 3% · workers를 늘려도 최대 1.03배
```

`add_workers` 일 때는 막대 아래에 "workers 4 → 8 권장 · 다음 학습부터" 를 띄운다. 문장은
`reason` 코드를 받아 프론트가 `t()` 로 만든다(백엔드는 숫자와 코드만 준다).

**(b) 학습 폼 Workers 칸** ([TrainingPage.tsx](../frontend/src/pages/TrainingPage.tsx))

- **같은 데이터셋·정책·AMP** 로 이 기계에서 잰 지난 실측이 있으면 "지난 실측(workers 4):
  데이터 대기 66% → 15 권장 [15로]" 를 보여 준다. 배치가 달라도 쓰되 "배치 8" 처럼 잰 배치를
  밝힌다 — 배치 2배에 필요한 워커는 12% 늘 뿐이라(§6) 여유가 덮는다.
- 실측이 없으면 "학습 시작 1분쯤 뒤 실측으로 나옵니다". 기본값 4 는 그대로 둔다.
- 지금 있는 `data_s > updt_s면 ↑` 는 이것으로 바꾼다.

**(c) 돌고 있는 학습에 바로 적용 — 1차에서 하지 않는다.** 재개(resume)로 다시 시작하면
마지막 체크포인트 이후의 진행을 잃는다(save_freq 기본 20000). 게다가 LeRobot 은 재개할 때
"체크포인트 설정을 쓴다" 고 적어 두었다 — `--num_workers` 덮어쓰기가 먹는지 확인이 필요하다.

## 5. 백엔드

- 구간 타이밍은 `TrainHistory` 가 아니라 `MetricsTracker.timings`(최근 5구간)에 둔다 —
  히스토리는 `step:25K` 가 되풀이되면 덮어쓰므로 구간이 사라진다. 영속하지 않는다:
  게이트웨이가 재시작하면 재부착이 저널을 처음부터 다시 읽어 채운다.
- 순수 함수 `training/loader.py` 의 `advise(samples, …)`(중앙값) → `judge(updt_s, data_s, …)` →
  `{wait_pct, max_gain, num_workers, recommended, cap, predicted_wait_pct, cpu_pct, cpu_busy,
  amp_off, reason}`. `tests/test_train_loader.py` 가 §2 표를 그대로 검사한다.
- N 은 `spec.cmd` 의 `--num_workers` 에서 읽는다(빼먹으면 LeRobot 기본값 4).
- `get_status()` 에 `loader` 필드를 싣는다 → WS 로 카드에 간다.
- **프로파일**: 로컬 job 레코드는 `"local"` 하나라 다음 학습이 덮어쓴다. 그래서 따로
  남긴다 — Redis 해시 `piper:train:loader_profiles` 의 `데이터셋|정책|amp` →
  `{num_workers, batch_size, updt_s·data_s 중앙값, cpu_pct, at}`. 구간이 쌓일 때마다 갱신한다
  (끝까지 안 돌아도 남는다). **이 기계 학습만** 남긴다 — 임대 기계는 매번 달라 다음 기계에
  안 맞는다. 재부착한 학습은 AMP 를 몰라(유닛 argv 에 없다) 남기지 않는다.
  폼은 `GET /api/training/loader-hint?dataset=&policy=&amp=` 로 읽는다.

## 6. 검증 실험 (2026-10-28, RTX 5090 · 20코어)

`singlearm_apple_random_v2`(21,224프레임, 15fps) · ACT · bf16 · 600 step · `log_freq` 100.
첫 구간을 뺀 5구간 중앙값. CPU 는 기계 전체(20코어 기준).

| 배치 | N | updt_s | data_s | step | T_b = N·step | 대기 | CPU | 판정 |
|---|---|---|---|---|---|---|---|---|
| 8 | 0 | 0.040 | 0.585 | 0.625 | (0.585) | 94% | 40% | 18 권장 |
| 8 | 1 | 0.042 | 0.416 | 0.458 | 0.458 | 91% | 10% | 14 권장 |
| 8 | 2 | 0.041 | 0.195 | 0.236 | 0.472 | 83% | 15% | 14 권장 |
| 8 | 4 | 0.041 | 0.079 | 0.120 | 0.480 | 66% | 27% | 15 권장 |
| 8 | 8 | 0.044 | 0.018 | 0.062 | 0.496 | 29% | 49% | 14 권장 |
| 8 | 12 | 0.047 | 0.003 | 0.050 | — | 6% | 63% | 충분 |
| 16 | 2 | 0.073 | 0.406 | 0.479 | 0.958 | 85% | 15% | 16 권장 |
| 16 | 4 | 0.074 | 0.167 | 0.241 | 0.964 | 69% | 27% | 16 권장 |

- **가정이 맞다.** T_b 가 N=1→8 에서 0.458→0.496(+8%)뿐이다. N=1 의 T_b 로 낸 예측 step 은
  N=4·8·12 에서 0.114·0.057·0.047, 실측 0.120·0.062·0.050 — **5~7% 낙관적**이다. 워커가 늘면
  메인 스레드도 조금 느려지기 때문이다(updt_s 0.041→0.047). 여유 1.2 가 이걸 덮는다.
- **권장값이 수렴한다.** 어느 N 에서 재도 14~15 가 나온다. 실제로 필요한 건 12(대기 6%) —
  2~3개 더 권하지만 그 대가는 코어 2~3개뿐이고, 모자라게 권하는 것보다 낫다.
- **워커 하나 ≈ 코어 하나.** 그래서 상한 "코어 − 2" 를 유지한다. 데몬들은 쉴 때 거의 안 쓴다.
- **N=0 은 과하게 권한다** — 메인 프로세스의 배치 시간(0.585)이 워커 하나(0.458)보다 28%
  길어서다(전처리·전송을 같이 한다). 기본값이 4 라 드물고, 한 번 올린 뒤 다시 재면 맞춰진다.
- **배치 2배** — updt_s 1.8배, T_b 2.0배. 필요한 워커는 11.6 → 13.0(+12%). 다른 배치의
  프로파일을 써도 여유가 덮는다(§4(b)).
- **메인 스레드 바닥**은 2~3ms(N=12) — `floor` 판정을 만들지 않은 이유다(§3).
- 스크린샷의 학습(workers 4 로 보이는데 대기 3%)은 이 측정과 안 맞는다 — 배치·데이터셋이
  달랐거나 workers 를 더 줬던 것으로 본다. 확인하지 못했다.

## 7. 단계

1. ☑ §6 실험 — 여유 1.2·문턱 10%·상한 코어−2 확정
2. ☑ `loader.advise`/`judge` + 테스트 + `get_status` 의 `loader` 필드
3. ☑ 메트릭 카드 막대·판정 줄(i18n)
4. ☑ 프로파일 저장 + 폼 권장값·[N로]
5. ☐ 원격(SSH) — 시작 시 `nproc`, 주기적 `/proc/loadavg` 로 상한·`cpu_limit`

## 열린 질문

- 재개할 때 `--num_workers` 덮어쓰기가 먹나 — 먹으면 (c) "이 값으로 재개" 를 다시 볼 수 있다.
- 첫 구간을 버리고 중앙값 5구간을 쓰는 것으로 에폭 재기동이 충분히 걸러지나 — §6 은
  600 step 이라 에폭 경계를 안 넘었다. 데이터셋이 작아 에폭이 짧으면(구간 3~4개당 한 번)
  부족할 수 있다.
