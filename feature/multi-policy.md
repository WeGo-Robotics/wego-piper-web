# 여러 정책을 올려 두고 바꿔 쓴다 — 추론 하나, 체크포인트 여럿

> 상태: **◐ 1~3단계 ☑ (2026-11-02)** — 래퍼(`policy_slots.py`·정책 적재 함수·전환·유지·텔레메트리), 게이트웨이
> (시작 검증·`/api/params/policy`·`/hold`·`active` 확인), SDK `set_policy`·`hold`, 추론 화면(§3-1), 테스트
> `test_multi_policy.py`. 실제 ACT 체크포인트 셋으로 적재·추론 확인(GPU 1.1GB, 전환 직후 첫 추론 6ms — §1).
> 남은 것: 플러그인·실기. 요청: "물체를 집어 바코드를 읽고 분류한다. ACT 둘 — ① 물건을 집어 카메라 앞에
> 가져오기 ② 카메라 앞에 가져온 물건을 받아 트레이에 넣기. 플러그인이 바코드를 읽고 어느 모델의 추론을 쓸지
> 정한다." 결정(2026-11-02): **양팔**(건네받기), **집는 물체별로 모델을 따로**, 바코드는 **기본**(번들 `barcode`
> 플러그인의 기본값 — 형식 전부).

## 0. 요지

추론 프로세스 **하나**에 체크포인트를 **이름 붙여 여럿** 올려 두고, 버스 키 `policy` 로 지금 쓸 것을 바꾼다.
`hold` 는 새 추론 없이 마지막 액션을 계속 보낸다 — 물건을 든 채 바코드를 읽는 동안이다. 팔 연결·토크·카메라는
그대로다. **정책이 하나면 명령줄도 동작도 지금과 같다.**

```
            ┌─ pick        (공통 — 바코드를 읽기 전이라 물체를 모른다)
  wrapper ──┼─ place_a     ── 매 스텝 도는 것은 지금 정책 하나 ──▶ 같은 양팔 로봇
            └─ place_b
  버스: policy="place_a" · hold=true|false            플러그인: barcode 검출 → 정책 이름
```

## 1. 왜 — 끄고 켜는 길로는 안 된다

| 길 | 막히는 곳 |
|---|---|
| 정지 → 다른 체크포인트로 시작 | 정지가 팔을 원점에 **파킹하고 토크를 끈다**(`ParkingController`) — 물건을 든 채면 놓친다. 전환마다 파킹(최대 18초) + 재기동 |
| 추론 프로세스 둘 | 같은 팔이면 액션 shm 세그먼트가 **락 없는 단일 라이터**(`piper_shm/arm.py` `_Writer`)라 두 프로세스의 명령이 섞인다. 팔을 나눠도 `process_manager` 는 하나뿐이고, 건네받는 순간 두 모델이 서로의 때를 모른다 |
| **한 프로세스, 정책 여럿** | ✓ 연결·토크 유지, 전환 비용은 다음 추론 한 번 |

GPU 는 걸리지 않는다. ACT(resnet18) 하나가 51.6M 파라미터·가중치 198MB. 한 프로세스면 CUDA 컨텍스트를 같이
쓰고, 매 스텝 도는 것은 지금 정책 하나다. 실측(RTX 5090, 양팔 ACT 셋, AMP, 2026-11-02):

| | |
|---|---|
| 셋을 올린 VRAM | 594MB(텐서) · 프로세스 1.1GB(컨텍스트 포함) · 최고 1.4GB |
| 추론 | 중앙값 6.0ms, p95 6.1ms |
| 프로세스의 맨 첫 추론 | 538ms — cuDNN·cuBLAS 초기화. 지금도 시작할 때 한 번 겪는다 |
| **바꾼 직후 첫 추론** | **6.1ms** — 평소와 같다. 예열이 필요 없다 |

## 2. 래퍼 — `wrapper/policy_slots.py` + `lerobot_wrapper.py`

### 2-1. 인자

- `--policy-path` 는 첫 정책 그대로, 이름은 `--policy-name`(기본 `main`).
- `--extra-policies` — 더 올릴 정책 JSON 배열 `[{"name", "path", "action_space", "delta_spec", "target_spec"}]`.
  액션 공간·목표 입력 사양은 첫 정책처럼 **백엔드가 체크포인트를 보고 싣는다** — 사람이 고르지 않는다.
- 이름이 `main` 이고 더 올릴 정책이 없으면 두 인자 다 안 실린다 — 명령이 한 글자도 안 바뀐다.
- **로봇을 만들기 전에** 정책마다 막는 것: 이름(영숫자·`_`·`-`, 겹침), 액션 공간 표식, 액션 길이가 첫 정책과
  같은가. 목표 입력은 로봇 state 이름이 있어야 해서 **연결 직전**에 정책마다 본다(`_target_input_for`).

### 2-2. 버스 키

| 키 | 값 | 하는 일 |
|---|---|---|
| `policy` | 이름 | 그 정책으로 바꾸고 돈다. 유지가 풀린다. 지금 이름이면 처음부터 다시(큐를 비운다). 모르는 이름은 버리고 로그를 남긴다 |
| `hold` | bool | 켜면 새 추론을 띄우지 않고 **마지막 액션을 매 스텝 다시 보낸다.** 유지하다 끄면 지금 정책을 처음부터 다시 |

⚠ **유지는 일시정지가 아니다.** 일시정지는 명령을 **안 보낸다** → 300ms 뒤 robotd 데드맨이 "지금 측정한 자세"를
명령한다(`robot/piper_robot/publish.py` `_hold`). 물체에 막혀 벌어진 그리퍼의 측정 폭이 목표가 되면 쥐는 힘이 빠질
수 있다(실기 확인 전 — §8). 유지는 "쥐어라"는 마지막 지령을 그대로 보낸다. 일시정지는 큐 모드의 큐도 안 비워,
재개하면 낡은 청크가 이어진다.

리셋(`reset`)은 유지를 풀지 않는다 — 풀려면 `hold: false` 나 `policy`.

### 2-3. 갈아끼우는 때 — 도는 추론이 끝난 뒤

1. 요청이 오면 새 추론을 띄우지 않는다. 돌던 추론은 끝까지 두고, 그 사이 큐는 그대로 나간다.
2. 추론 스레드가 쉬면 갈아끼운다: 세대 증가(낡은 결과 폐기), 큐·앙상블·RTC 비우기, 정책·전후처리·rename·
   목표 입력·델타·stage 이름을 새 것으로, 새 정책 `reset()`.
3. 같은 스텝에 새 정책의 첫 추론이 뜬다(큐가 비었으니 바로). 결과가 오기 전 한두 스텝은 직전 액션을 유지한다.
4. **파킹·`step=0`·액션 필터 초기화는 안 한다** — 리셋과 다른 점이다. 팔은 지금 자리에서 새 정책의 첫 청크로
   이어진다. 큐 모드면 청크 이어 붙이기가 직전에 보낸 액션에서 크로스페이드하고, 시간 앙상블이면 새 정책의
   청크만으로 평균이 다시 쌓인다. 액션 필터(EMA·속도 제한)는 그대로 이어진다.

⚠ **순서가 안전장치다.** 메인 루프는 관측 슬롯(`_obs_for_inference`)을 **먼저 비우고** 추론 중 표시를 본다. 추론
스레드는 추론 중 표시를 **먼저 올리고** 관측을 읽는다. 그래서 둘 중 하나는 반드시 상대를 본다 — 스레드가 관측을
쥐었으면 메인 루프는 끝날 때까지 기다리고, 못 쥐었으면 빈 슬롯을 읽고 쉰다. 이 순서가 깨지면 A 의 정규화
통계로 편 관측을 B 가 읽는다. 테스트가 두 순서를 다 잡는다.

### 2-4. 정책마다 따로 / 같이

- **따로**: 정책 객체, 전·후처리(정규화 통계가 체크포인트마다 다르다), rename_map, 액션 공간(델타), 목표 입력,
  RTC 가능 여부, stage 이름.
- **같이**: 로봇·카메라·액션 필터·고쳐 잇기·청크 이어 붙이기·시간 앙상블·실시간 파라미터 전부(액션 청크 크기
  포함). 튜닝 값은 프로세스에 하나다 — 정책마다 달라야 하면 그때 나눈다.
- 정책 객체에 거는 실시간 설정(`PARAM_SETTERS` — `use_amp`·RTC)은 올린 정책 **전부**에 건다.

### 2-5. 보이는 것

- 텔레메트리: 정책이 둘 이상이면 `policy`(지금 이름), 유지 중이면 `holding: true`.
- 실행 기록(`piper_inference_*.json`): `policies`(이름 → 체크포인트). 전환은 `changes` 에 `policy`·`hold` 로 그대로
  남는다.

## 3. 게이트웨이

- `POST /api/models/inference/start` 에 `policy_name`(기본 `main`)·`extra_policies: [{name, checkpoint_path}]`.
  **로컬 모드만**. 정책마다 장치를 건드리기 전에 보는 것: 이름, 체크포인트가 있나, `checkpoint_dim_problem`,
  액션 공간·목표 입력(모름이면 400), **정책 종류와 액션 길이가 첫 정책과 같은가**. 카메라를 연결한 뒤에는 학습
  카메라 대조를 정책마다 한다. 표식(액션 공간·목표 입력·학습 카메라)도 정책마다 남긴다.
- `POST /api/params/policy {"name"}` — 올린 이름만 보낸다(돌고 있지 않으면 409, 모르는 이름이면 400).
  `POST /api/params/hold {"on"}`. 플러그인 범위는 둘 다 `params.write`.
- `GET /api/models/inference/policy` 에 `policies`(이름 → 체크포인트)·`active`·`holding`. `checkpoint_path` 는 지금
  정책의 것이다. **`active` 는 래퍼가 텔레메트리로 확인해 준 값**이다 — 요청을 보냈다고 바뀌었다고 적지 않는다.
- 배타·E-stop 은 그대로다 — 프로세스가 여전히 하나다.

정책 종류를 하나로 묶은 이유: 정책별 파라미터 판정(`foreign_to`)과 `task` 판정이 "지금 정책 종류" 하나를
기준으로 돈다. ACT 와 SmolVLA 를 섞으면 그 판정이 전환마다 달라져야 한다 — 필요해지면 그때.

카메라는 매핑된 것만 연결된다. 학습 카메라 대조는 매핑에 없는 카메라를 "모름" 으로 넘기므로, 더 올릴 정책이
쓰는 카메라가 매핑에 다 있는지는 시작 검증이 따로 본다 — 빠지면 시작은 되고 그 정책으로 바꾸는 순간부터 매
추론이 관측 키 없음으로 죽는다.

### 3-1. 추론 화면

**정책 고르기는 추론 화면에 둔다 — 플러그인 화면이 아니다.** 추론을 시작하려면 양팔 좌/우, 카메라 매핑,
카메라 프로파일, 파라미터, 사전 검증, CLI 미리보기가 다 필요하고 그것은 추론 화면에만 있다. 플러그인 쪽에
두면 시작 설정이 두 벌이 된다. 기존 양팔 앱(apple-sort)도 사람이 추론 화면에서 띄운 추론에 붙어 조종만 한다.
앱 상태(코드·트레이·실패)는 플러그인 화면 몫이다(§5).

- 준비: "체크포인트" 카드 아래 [+ 함께 올릴 정책] — 줄마다 이름·체크포인트(같은 고르기 창)·✕. 하나라도 있으면
  위 체크포인트의 이름 칸이 생긴다. 고르기 창은 종류가 다른 체크포인트를 흐린다. 이름·종류·액션 길이·카메라를
  화면이 미리 보이고 시작을 막는다 — 판정은 시작 API 가 다시 한다(`types/policySlots.ts`). 고른 목록은 선택
  저장(`/api/inference/selection`)에 남는다.
- 실행: 정책이 둘 이상이면 요약 바 아래 칩 줄 — 누르면 바꾸고(텔레메트리가 확인할 때까지 깜박인다), [유지]·
  [유지 풀기]. 확인 창은 없다(파킹하지 않는다). 칩 목록은 `GET /api/models/inference/policy` — 누가
  시작했든(화면·플러그인) 게이트웨이가 기억한다.
- 정책이 하나면 준비 화면엔 [+ 함께 올릴 정책] 한 줄뿐, 실행 화면과 시작 요청은 예전과 같다.

## 4. SDK

`self.robot.set_policy(name)`, `self.robot.hold(on=True)`. `self.robot.policy()` 에 `policies`·`active`·`holding`.
시작은 `self.robot.start_inference(ckpt, cams, policy_name="pick", extra_policies=[{"name": "place_a",
"checkpoint_path": …}])`.

## 5. 바코드 분류 플러그인 (4단계)

- 정책: `pick`(공통) + 물체별 `place_<물체>`.
- 판독은 번들 **`barcode`** 플러그인이 한다(zxing-cpp, 형식 전부가 기본). 분류 플러그인은 그 검출을 입력 슬롯
  (`kind: detections`)으로 받는다 — 디코더를 두 번 들지 않는다. OpenCV 내장 디코더는 같은 시험 이미지 다섯 장에서
  QR 하나만 읽어 쓰지 않는다(`plugins/barcode/main.py` 머리말).
- 흐름: `pick` → (코드 읽힘 + 팔 정지) → `hold` → 코드 → 물체 → `policy=place_<물체>` → (원점 근처·빈손·정지) →
  `policy=pick`. 코드 → 정책 대응은 설정의 `값=정책` 줄(apple-sort 의 지시문 규칙과 같은 모양).
- 실패: 판독이 시간 안에 안 되면 유지한 채 알린다 — 사람이 판단한다.

## 6. 데이터·학습

- 모든 정책을 **같은 로봇 구성(양팔 14축)·카메라·fps** 로 학습한다 — 한 프로세스에 올리는 조건이다.
- 한 데이터셋에 단계별 에피소드를 번갈아 녹화하고 task 문장으로 가른다(녹화 중 task 변경은 다음 에피소드부터,
  `wrapper/start_record.py`). ACT 는 task 를 안 보니 라벨은 가르는 데만 쓴다.
- `pick` 시연은 카메라 앞에서 1~2초 멈춘 채 끝낸다 — ACT 가 거기서 서는 법을 배운다. 다음 에피소드 전 리셋
  구간은 → 로 넘긴다(그동안에도 텔레옵은 돈다).
- `delete_episodes` + `--new_repo_id` 로 정책별 사본을 뽑는다(원본은 남는다). 사본엔 사이드카가 안 따라온다.

## 8. 열린 것

- **데드맨이 쥔 물체를 놓는가** — 실기로 본다. 안 놓으면 일시정지로도 되지만 유지가 해롭지는 않다.
- ~~전환 직후 첫 추론 지연~~ — 닫힘(§1 실측). 느린 것은 프로세스의 맨 첫 추론뿐이고, 바꾼 정책의 첫 추론은
  평소와 같은 6ms 였다. 예열은 넣지 않는다.
- 정책별 튜닝 값.
- `pick` 이 끝난 것을 어떻게 아는가 — 코드 판독 + 팔 정지가 1차. ACT-S(stage 헤드)로 학습하면 stage 도 같이 볼 수
  있다.
