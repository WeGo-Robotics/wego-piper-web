## 2. 무엇을 노리나

밖에서 온 사람이 **스크롤 두 번 안에** 세 가지를 알게 한다.

1. **무엇을 푸는가** — 실기 로봇 모방학습의 한 바퀴(수집→학습→추론→평가)를 브라우저에서.
2. **진짜 도는가** — 화면 그림과 **실측 숫자**. 로보틱스 쪽 독자는 주장보다 숫자를 본다.
3. **우리 사정에 맞는가** — 팔 없이도 되나(된다, 시뮬), GPU 없어도 되나(수집·시뮬은 된다),
   안전은 어떻게 하나(E-stop 이 웹과 분리된 독립 프로세스다).

그리고 **설치는 앞에서 내린다.** 판단하는 사람에게 "처음 한 번은 두 번 돌린다"는 사서 겪을
고생이지 결정의 재료가 아니다.

## 3. 뼈대

```
# Piper Studio                        한 문장 + 대표 화면 1장
## 이 물건이 푸는 것                   터미널에 흩어진 한 바퀴를 화면 하나로 (5~7줄)
## 한 바퀴                             등록 → 수집 → 학습 → 추론 → 평가, 단계마다 그림 1장
## 팔이 없어도 된다                    시뮬레이터로 같은 한 바퀴 · GPU 없는 PC
## 멈추는 것이 먼저다                   E-stop = 웹과 분리된 워치독. 실측 2.5초
## 어떻게 만들어졌나                    컨테이너 ↔ 호스트 데몬, 장치 소유가 하나인 이유
## 화면                                21개를 묶음별로 한 줄씩
## 설치                                3줄 + docs/install.md 링크
## 더 읽을 것                          링크 표 (docs 전부)
```

### 왜 이 순서인가

- **"한 바퀴"가 2번**인 이유: 이 제품의 값은 기능 목록이 아니라 **끊기지 않는 흐름**이다.
  기능을 21개 나열하면 그 사실이 안 보인다.
- **"팔이 없어도 된다"가 3번**인 이유: 평가하는 사람의 첫 장벽이 하드웨어다. 시뮬로 한 바퀴가
  돈다는 사실은 **데모 약속을 그 자리에서 지울 수 있는** 카드다.
- **안전이 4번**인 이유: 로봇을 사는 쪽은 여기서 신뢰를 정한다. 지금 README 에서는 첫 문장
  끝에 "E-stop 안전 정지" 다섯 글자로 지나간다.
- **아키텍처가 5번**인 이유: 기술 독자에게는 "컨테이너는 장치를 안 연다"가 곧 품질 신호다.
  지금은 설치 절 뒤에 묻혀 있다.

## 4. 설치는 `docs/install.md` 로 내린다

지금 README 의 45줄이 거의 그대로 간다 — **버리는 게 아니라 옮기는 것**이다. 옮길 것:
설치 3줄 · "두 번 돌린다" 문단 · 접속 주소·포트 · simd/so101d 가 꺼진 채 깔린다 ·
업데이트·제거 명령 · 필요한 것 표 · 데이터 위치 표.

README 에 남는 설치 절은 **행복한 경로 3줄 + 링크**다:

```bash
curl -fsSLO .../deploy/piper-install.sh && chmod +x piper-install.sh && ./piper-install.sh
```
> 처음 한 번은 sudo 명령을 찍고 멈춘다 — 그대로 실행하고 다시 돌린다.
> 자세히 → [docs/install.md](docs/install.md) · 막히면 → [트러블슈팅](docs/install-troubleshooting.md)

⚠ **링크를 깨뜨리지 않는다.** 지금 README 의 `#설치` 앵커를 **셋**이 가리킨다 —
[CLAUDE.md](../CLAUDE.md), [deploy/RELEASE-CHECKLIST.md](../deploy/RELEASE-CHECKLIST.md),
[docs/install-troubleshooting.md](../docs/install-troubleshooting.md). 옮기면서 셋 다 고친다.
(README 에 설치 절이 남으므로 앵커 자체는 살지만, **가리키는 곳이 3줄짜리 요약이 된다** —
"자세한 절차" 를 기대하는 링크는 `docs/install.md` 로 돌려야 한다.)

## 5. 숫자 — 쓰되, 약속이 되는 것은 뺀다

저장소에 실측이 많다. 밖에 내는 순간 **그 숫자는 약속**이 되므로 고른다.

| 쓸 만한 것 | 어디서 나온 값 |
|---|---|
| 시뮬 팔이 실기와 **FK 0.00mm / 0.00°** | 같은 AgileX URDF 로 대조 (sim-env 1단계) |
| E-stop **2.5초**에 SIGKILL | heartbeat 끊김 실측 |
| 업데이트 전송 **약 104MB** | 직전 버전을 가진 호스트 실측 |
| 시뮬 데모가 **11.9초**에 한 바퀴, 20 에피소드 4분 | sim-env 4단계 |
| GPU 없는 PC 에서 수집·시뮬·조종 | 설계상 · 실측 |

⚠ **안 쓸 것**: 학습 성공률·정책 성능. sim-env 문서가 "이 기획의 목표는 파이프라인 검증과
**상대 비교**이지 실기 성능 예측이 아니다" 라고 못 박아 뒀다. 밖에 내는 문서가 그 선을 넘으면
안 된다.

## 7. 순서

1. `docs/install.md` 를 만들고 지금 README 의 설치·요구사항·데이터 위치를 **그대로 옮긴다**
   (내용 변경 없음 — 옮기는 것과 고치는 것을 같은 커밋에 섞지 않는다). 앵커를 가리키는
   세 문서도 같이 고친다.
2. README 를 §3 뼈대로 다시 쓴다. 그림 자리는 비워 두고 주석으로 표시한다.
3. 새 스크린샷 둘(클라우드 GPU·가상환경)을 받아 끼운다. 받기 전까지는 그 절이 글만 있다.
4. 링크 점검 — `docs/` 전부가 README 에서 닿는가. 안 닿는 셋을 어디에 걸지 정한다
   (`data-preprocessing`·`robot-daemon-contract`·`vibration_reduction`).

## 8. 열린 질문

- **언어.** 지금은 한국어다. 밖이 국내 고객·채용이면 그대로가 맞고, 해외 파트너나 공개
  저장소가 섞이면 영어가 필요하다 — 그때는 `README.md`(영어) + `README.ko.md` 가 흔한 모양이다.
  **둘 다 유지하는 비용**이 있으니 사람이 정할 일이다.
- **비공개 저장소인가.** 공개라면 라이선스·서드파티 고지가 첫 화면 가까이 와야 한다.
- 안 닿는 문서 셋을 README 에 거는 게 맞나, 아니면 그것들이 애초에 내부 메모인가.
