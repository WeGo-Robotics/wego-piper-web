# so101d — SO-101 리더암과 외부 로봇 데몬의 표준 통로 (기획)

상태: **기획.** 구현 전. 1차 목표: **SO-101 리더 → Piper 팔로워 텔레옵·수집.**

실물 확인 (2026-09-08): 어댑터 1개 — `/dev/ttyACM0`, WCH CH343(1a86:55d3),
고유 시리얼 58FA096736 → by-id 식별 가능. 사용자 dialout 그룹 확인.

## 0. 외부 로봇이 웹과 만나는 통로 — 이미 셋으로 표준화돼 있다

새로 발명할 것이 없다. robotd·camerad·rsd 가 전부 같은 세 채널을 쓴다:

```
웹(React) ── REST/WS ── 게이트웨이(FastAPI)
                          │
                          ├─ ① 제어면: 허브 클라이언트 → Redis 버스 rpc_call → 데몬
                          │     scan/attach/release/estop/설정 — 저속·요청응답
                          │     (realsense_manager._call, robot_manager._call 과 동형)
                          ├─ ② 데이터면: /dev/shm seqlock — 고속 스트림
                          │     piper.arm.<id>.state (데몬→소비자, ≥50Hz)
                          │     piper.arm.<id>.action (소비자→데몬, deadman 내장)
                          │     소비자 = 게이트웨이(조그·릴레이·감시) + LeRobot 프로세스
                          └─ ③ 버스 계약: heartbeat(estopd 감시), 최신값+TTL 텔레메트리
```

**웹은 데몬을 직접 모른다.** 프론트엔드는 `/api/robots/*` 만 보고, 데몬과의
유일한 통로는 게이트웨이의 허브 클라이언트다. 그래서 로봇을 추가할 때 웹이
바뀌지 않게 하는 일 = **게이트웨이 추상화를 바로잡는 일**이다 (§4).

## 1. 경계 — 별도 데몬 `piper-so101d`

| 자리 | 판정 |
|---|---|
| **so101d 신설** | ✅ `daemons/so101d.py` + `so101/piper_so101/` — rsd/camerad 골격(버스 RPC + heartbeat + shm 발행) 그대로 |
| robotd 안에 통합 | ❌ Feetech 시리얼이 걸리면 CAN 제어가 같이 죽는다. 유닛 분리가 곧 격리다 (rsd 가 D-state 로 물려도 camerad 는 돈다) |
| 게이트웨이가 직접 열기 | ❌ 장치는 호스트 데몬이 독점. 컨테이너로는 shm 만 간다 |
| `serialarmd` 일반화 | ❌ 두 번째 시리얼 팔이 오면 그때. 일반화는 §4 의 **계약**으로 하지, 데몬 병합으로 하지 않는다 |

모터 접근은 **scservo_sdk 직접** — LeRobot 을 데몬에 import 하지 않는다
(robotd ↔ piper_sdk 와 동형: 업데이트가 데몬을 못 흔들게).

## 2. shm 계약 — 그대로 쓴다 (여기가 "덜 복잡한" 이유)

팔 shm 레코드는 위치 인덱스 7-float 이고 어디에도 Piper 가 박혀 있지 않다.

- 세그먼트: `piper.arm.so101_leader1.{state,action}` — 세그먼트 이름이 곧
  팔 id 다 (CAN iface 자리에 이 문자열이 들어간다).
- 7f 매핑: [0..4]=shoulder_pan·lift·elbow·wrist_flex·wrist_roll, [5]=0(미사용),
  [6]=gripper. 자리↔이름은 `so101/piper_so101/joints.py` **한 곳** (Piper 의
  joints.py 와 대칭).
- 정규화 규약 동일: 관절 -100..100, 그리퍼 0..100 → 소비자 무수정.
- deadman·estop: 계약 헤더에 이미 있다. deadman 경과 = 위치 유지,
  estop RPC = 토크 OFF (Piper 기본값과 동일).

기각: 이름 싣는 계약 v2 — 소비자 전부를 같이 올려야 한다. 필요 없다.

## 3. 캘리브레이션 — SO-101 의 진짜 숙제

3D 프린트 + 수조립이라 **개체마다 다르다** (Piper 의 고정 테이블 불가).
LeRobot `lerobot-calibrate` 가 만드는 팔별 JSON(homing_offset + range)을
so101d 가 **그대로 읽어** raw(틱)↔정규화 변환한다 — 파일이라 import 불필요,
LeRobot 네이티브 경로와 숫자 호환. v1 절차: so101d `release` RPC → 터미널
캘리브레이션 → `attach` (카메라 force_release 전례). 캘리브레이션 없는 팔은
연결은 되되 **등록 거부** — 그 팔로 모은 데이터는 그 팔 전용 쓰레기다.
웹 위저드는 v2.

## 4. 로봇을 추가하기 쉽게 — 계약·레지스트리·capabilities

앞으로 로봇 N번째를 추가할 때 해야 하는 일이 "데몬 하나 + 파일 몇 개"로
끝나려면, 지금 세 가지를 바로잡아야 한다. **카메라 쪽이 이미 정답을 갖고
있다** — camerad/rsd 를 `_hub` 한 곳에서만 가르는 camera_manager 구조다.

### 4.1 로봇 데몬 계약 (명문화 — `docs/robot-daemon-contract.md`)

새 로봇 데몬이 구현해야 하는 전부:

| 채널 | 의무 |
|---|---|
| 버스 RPC | `scan() / attach(id) / release(id) / estop(id) / info(id)` — 이름과 시그니처 고정 |
| shm | 표준 7f state/action 세그먼트 + deadman 준수 + 정규화 규약 |
| 버스 | heartbeat 발행 (estopd 감시 대상 등록) |
| systemd | 유닛 + Restart=always, 기동 시 세션 reattach |

### 4.2 capabilities 선언 — UI 가 모델 문자열로 분기하지 않게

`scan()`/`info()` 가 팔마다 선언한다:

```json
{ "model": "so101", "transport": "serial", "dof": 5, "gripper": true,
  "joint_names": [...], "kinematics": "so101",
  "features": { "master_slave": false, "hw_zero": false, "slip_reset": false,
                "parking": false, "rate_limit": true } }
```

디바이스 탭은 **features 를 보고 버튼을 그린다** — 마스터/슬레이브·0x150·
영점굽기·슬립경고는 `features` 가 없다고 하면 안 그린다. `if model == "piper"`
분기를 UI 에 만들면 로봇 셋째부터 프론트 수술이 반복된다 — 금지.
`/attach` 의 로봇 타입 기본값(지금 `piper_follower` 고정)도 model 에서 온다.

### 4.3 게이트웨이 허브 레지스트리

`robot_manager` 가 robotd 하나에 묶여 있는 것을 허브 목록 순회로 바꾼다:
scan = 모든 허브의 scan 합집합, 팔 id → 소유 허브 매핑 **한 곳**
(camera_manager `_hub` 와 동형 — 그 테스트가 강제하는 "소유 판단은 한 곳"
규칙을 그대로 가져온다). 포트 패널은 transport 별 카드 종류
(CAN: Rx/Tx·bitrate·UP/DOWN / serial: by-id·baud·present — 시리얼엔 링크
상태 개념이 없으니 CAN 카드 틀에 욱여넣지 않는다).

### 4.4 기구학 레지스트리 — **이미 있다**

`ArmModel.load(name)` 이 이름별 geometry npz 를 로드하고, docstring 에
이미 `build_arm_geometry.py --urdf ... --out so101_geometry.npz` 예시가
적혀 있다. SO-101 추가 = SO-ARM100 저장소 URDF 로 npz 한 개 생성.
relay 는 이미 `ArmModel.load(leader_arm)/load(follower_arm)` 로 리더·팔로워
모델을 따로 든다 — 크로스 모델 설계가 처음부터 있었다.

## 5. SO-101 리더 → Piper 팔로워 — 두 모드를 만들고 실측으로 고른다

릴레이에는 이미 `mode` 개념("joint"/"pose")과 비교에 쓸 통계
(`sent`/`blocked`/`ik_iters`)가 있다. 두 모드를 모두 크로스 모델로 열고,
텔레옵 패널에서 **사람이 선택**하게 한 뒤 실측으로 비교한다 — 어느 쪽을
기본으로 열지(또는 한쪽을 접을지)는 그 결과가 정한다.

### 5-공통. 정합(클러치) — 영점도 시작 자세도 다른 두 팔을 잇는 방법

두 팔은 기구 배치도, 영점 규약도, 지금 서 있는 자세도 다르다. **절대
매핑은 이 셋 전부와 싸워야 한다**: 기준 자세 대응표를 손으로 맞춰야 하고,
물리기 전에 사람이 리더를 팔로워 자세에 맞춰 들고 있어야 하며, 표의 오차는
물리는 순간의 점프가 된다. 그래서 절대 매핑을 기각하고 **정합 앵커**로 간다:

> [정합] 순간의 리더 자세와 팔로워 자세를 앵커로 잡고, 이후 **리더의
> 변화량만** 팔로워 앵커 위에 얹는다. (VR·스페이스마우스·수술 로봇
> 텔레옵의 표준 방식 — 마우스를 들어 옮기는 것과 같다.)

성질 셋이 공짜로 따라온다:

1. **물리는 순간 점프가 구조적으로 0** — 첫 목표가 곧 팔로워의 현재
   자세다. 시작 위치가 얼마나 달라도 상관없다. 이후는 기존 한걸음 상한이
   지킨다.
2. **영점 규약 차이가 소거된다** — 변화량은 상수 오프셋을 빼기에서
   지운다 (ACT-delta 와 같은 산수).
3. **재정합(re-clutch)** — 해제하고 리더를 편한 자세로 옮겨 다시 물리면
   작업 공간을 이어서 쓸 수 있다. SO-101 작업 반경이 Piper 보다 작은
   문제의 1차 해법이기도 하다.

정합/해제는 텔레옵 패널 버튼 (SO-101 리더엔 버튼이 없다). 남는 정적 설정은
모드별로 최소만: 관절 모드의 부호 테이블, POSE 모드의 베이스 정렬 회전.

### 5a. 관절 매칭 모드 — 5관절 → 6관절 정적 매핑

축 구성이 겹치는 관절끼리 잇고, 남는 Piper joint4(전완 롤)는 고정한다:

| SO-101 | Piper | 비고 |
|---|---|---|
| shoulder_pan | joint1 | yaw |
| shoulder_lift | joint2 | pitch |
| elbow_flex | joint3 | pitch |
| — | joint4 | **0 고정** (빠진 자유도) |
| wrist_flex | joint5 | pitch |
| wrist_roll | joint6 | roll |
| gripper | gripper | 0..100 통과 (정합 대상 아님 — 절대량) |

- 목표식: `팔로워[j] = 팔로워_정합[j] + 부호[j] × (리더[i] − 리더_정합[i])`.
  정적 테이블은 **부호뿐**이다 (축 방향 규약 차이) — 오프셋은 정합이
  잡아주므로 손으로 맞출 표가 없다.
- ⚠ **매핑은 각도 공간에서 한다** — 리더 rad ↔ 팔로워 rad. 정규화
  공간(-100..100)에서 매핑하면 두 팔의 관절 범위가 달라 **각도가 비선형으로
  왜곡**된다 (Piper 마스터 그리퍼 사고와 같은 병). 부호 테이블은
  `so101/piper_so101/joints.py` 옆 한 곳.
- joint4 는 0 이 아니라 **정합 시점 값 유지** — 물리기 전에 조그로 원하는
  전완 롤을 세팅해 두면 그대로 간다. 재정합 때마다 다시 세팅 가능.
- 안전 층 유지: 팔로워 관절 한계 클램프 + **팔로워 모델 FK 로 바닥 검사**
  (pose 모드가 쓰는 `lowest_z` 재사용 — IK 만 안 탈 뿐 검사는 같다).
- 장점: IK 없음(특이점·해 실패·진동 원천 차단), 지연 최소, 리더 관절을
  그대로 따라와 조작감이 직관적. 단점: 두 팔의 링크 길이가 달라 **말단
  궤적은 사람이 리더에서 본 것과 다르다**, joint4 고정만큼 자세 손실.

### 5b. 말단 6D POSE 모드 — 기존 POSE 릴레이 + 상대 자세

리더 shm state → FK(so101) → **정합 기준 상대 자세** → IK(piper, 직전 해
시드) → 바닥·한걸음 상한 → goal 발행:

> `목표 = T_팔로워정합 · R_정렬 · (T_리더정합⁻¹ · T_리더) · R_정렬⁻¹`
> (리더 변화량을 팔로워 정합 자세 위에 얹는다. 위치 성분에는 배율 옵션 —
> SO-101 반경이 작으므로 1.0~1.5 를 비교 항목에 넣는다.)

- `R_정렬` = 두 베이스의 장착 방향 차이를 잇는 고정 회전 (설정, 기본
  항등 — 두 팔이 같은 방향으로 작업대를 보면 그대로 맞는다).
- 절대 자세를 버렸으므로 기존 POSE 릴레이의 "첫 프레임 점프" 문제도 같이
  사라진다 — 정합 순간 상대 자세가 항등이라 첫 목표 = 팔로워 현재 자세.

고쳐야 할 Piper 고정 이음새 셋 (relay.py):

1. `K.ARM_JOINTS` 로 norm→rad 하는 자리 — 리더 **모델의** 관절 테이블로.
2. `near_gimbal_lock` — 모델별 판정 (5DOF 손목 구성이 다르다).
3. `_follower_seed` — 이미 팔로워 모델 기준이라 확인만.

5DOF 리더의 뜻: FK 는 항상 완전한 6D 를 주지만 리더가 만들 수 있는 자세는
5차원 다양체다. Piper 는 그 부분집합을 따라간다(joint4 를 IK 가 활용).
장점: 말단 궤적이 리더와 일치 — 작업 공간에서의 의도가 보존된다. 단점:
IK 실패·짐벌 근처 차단·한걸음 상한 등 pose 경로의 기존 마찰 전부.

### 5c. 비교 — 열지 말지는 숫자가 정한다

같은 과제(표준 픽앤플레이스)를 두 모드로 조작해 비교한다:

| 항목 | 출처 |
|---|---|
| 완료 시간·체감 조작감 | 사람 (조작자 평가) |
| 차단율 (`blocked`/`sent`), IK 반복수 | 릴레이 통계 — 이미 있다 |
| 팔로워 goal 궤적의 jerk RMS | goal 세그먼트 기록 |
| 리더→goal 지연 | 두 모드 공통 계측 추가 |
| (최종) 수집 데이터로 학습한 정책의 성공률 | 시간이 허락하면 — 이것이 진짜 심판이다 |

결정 게이트: 한쪽이 명백히 이기면 기본 모드로 두고 다른 쪽은 선택지로
남기거나 접는다. 둘 다 쓸 만하면 둘 다 연다 — 과제 성격(정밀 자세 vs 빠른
반복)에 따라 갈릴 가능성이 크다. **결정 전에는 어느 쪽도 "정식"이라
말하지 않는다.**

**수집(녹화)의 액션 소스**: Piper 끼리는 마스터가 CAN 으로 직접 지령을 쏘지만
SO-101 리더는 릴레이가 goal 세그먼트를 쓴다. 즉 **릴레이가 발행한
`piper.arm.<팔로워>.action` 이 곧 action** 이다 — LeRobot 플러그인에 그
세그먼트를 읽는 텔레오퍼레이터 클래스(`piper_shm_goal_teleop`) 하나를 더해,
robot=Piper shm + teleoperator=goal 리더로 record CLI 를 돌린다.
액션 공간이 팔로워 관절계라 학습·추론(팔로워 단독)과 그대로 맞는다.

## 6. 안전 — 달라지는 것이 없어야 한다

| 층 | SO-101 에서 |
|---|---|
| estopd heartbeat → 활동 PID SIGKILL | 그대로 |
| action deadman | 계약 그대로 — so101d 가 지키면 끝 |
| E-stop → 토크 OFF | so101d `estop` RPC (계약 동사) |
| 기구학 필터·바닥 | 릴레이·robotd 가 **팔로워(Piper) 쪽에서** 이미 수행 — 리더는 사람 손안이라 해당 없음 |
| 변화율 상한 | so101d 스텝당 틱 클램프 (Feetech 과전류 퓨즈) — 리더는 토크 OFF 상태라 실질 대상은 v2 의 SO-101 팔로워 |

## 7. 하지 않는 것 (v1)

- SO-101 **팔로워** 지원 (지금 있는 개체는 리더로 쓴다 — 팔로워 세트가 오면
  §4 계약 위에서 등록만 늘어난다)
- 캘리브레이션 웹 위저드, SO-101 파킹
- serialarmd 일반화, 다른 Feetech 팔

## 8. 위험

| 위험 | 대응 |
|---|---|
| CH343 폴링 지연 → 리더 15Hz 미달 | 실측 첫 번째. latency timer 조정. 릴레이는 리더 신선도(stale) 감시가 이미 있다 |
| 캘리브레이션 JSON 포맷이 LeRobot 버전 따라 변함 | 버전 필드 검사, 모르면 등록 거부 (조용한 오독보다 낫다) |
| 5DOF FK 특이 구성(손목 정렬)에서 IK 진동 | 직전 해 시드 + 한걸음 상한이 기존 방어. 모델별 gimbal 판정으로 보강 |
| 어댑터 시리얼 없는 개체 | by-path 폴백 + "포트 옮기면 다른 팔" 경고 |
| goal-as-action 의 시점 어긋남 (릴레이 발행 시각 vs 프레임) | 세그먼트 wall_ns 가 이미 있다 — 녹화 fps 대비 지연 실측 후 판단 |

## 9. 순서

1. `so101/piper_so101/` — scservo IO·joints 테이블·캘리브레이션 리더 (순수
   함수 테스트) + `so101_geometry.npz` 생성 (URDF → 기존 도구)
2. `daemons/so101d.py` — 계약 동사 + 상태 발행 + heartbeat + 유닛.
   **실기: 토크 OFF 손으로 움직여 상태 발행 50Hz 확인**
3. 게이트웨이 — 데몬 계약 문서화, 허브 레지스트리, capabilities 기반
   디바이스 탭(시리얼 포트 카드), `/attach` 모델별 타입
4. 릴레이 — 관절 매칭 모드(매핑 테이블 + 바닥 검사) 와 POSE 모드(모델별
   이음새 셋) 둘 다 + 텔레옵 패널 모드 선택 + 지연 계측 →
   **실기: 두 모드로 SO-101 리더 Piper 조종, §5c 표 채우기**
5. 수집 — `piper_shm_goal_teleop` 플러그인 → record e2e (액션은 goal
   세그먼트라 **모드와 무관하게 팔로워 관절계로 동일**) → 학습·추론 무수정

## 열린 질문

- 관절 모드의 **대응 표류** — 정합을 어긋난 자세에서 걸수록 리더와
  팔로워의 자세 대응이 비틀린 채 시작한다 (변화량은 맞지만 절대 대응이
  다르다). 조작감을 얼마나 해치는지는 실측 몫이고, 심하면 "권장 정합
  자세" 안내(양쪽 준비 자세 근처에서 물리기)를 UI 에 얹는다.
- POSE 모드 위치 배율 — 1.0(그대로) vs 1.3~1.5(작은 리더로 큰 작업 공간).
  배율이 크면 미세 조작이 거칠어진다. §5c 비교에 포함.
- ~~리더 발행 주기 실측~~ **닫힘 (2026-09-08)**: 6모터 GroupSyncRead
  실측 **685Hz** (200회 실패 0, CH343 + 1Mbaud). 50Hz 발행에 13배 여유 —
  §8 의 "CH343 폴링 지연" 위험도 함께 해소. (같은 날 모터 4~6 무응답은
  팔꿈치→손목 3핀 케이블 접촉 불량이었다 — 재장착으로 해결. 조립 팔의
  데이지체인은 이런 식으로 끊긴다: so101d 는 **연결 시 6모터 전수 핑**을
  하고 빠진 ID 를 사람이 읽을 문구로 말해야 한다.)
- SO-101 리더의 그리퍼(트리거)가 캘리브레이션 후 0..100 을 실제로 꽉 채우나
  — Piper 마스터 그리퍼 스케일 사고(2× + 닫힘 오프셋)의 재판 방지. 등록 시
  범위 검사에 넣을 것.
- goal-as-action 지연 실측 — 프레임 타임스탬프와 액션 시각의 정렬.
