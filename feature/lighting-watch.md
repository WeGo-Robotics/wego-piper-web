# 조명 변화 감시 — 밝기·색이 튀면 알람

> 상태: **§8 의 1~4·6 구현됨** (2026-09-02 — 라이브러리·버스 발행·경보·수집/추론
> 표시·뷰어 프레임 값). 5(실측 튜닝)와 7(트랙 곡선·차트·녹화 메타)은 아직.
> 조사일 2026-09-02 — "지금 이런 상태다"는 코드에서 확인한 것.

## 1. 왜

정책과 데이터셋은 조명에 물든다. 형광등이 나가거나, 해가 창으로 들어오거나,
누가 스위치를 건드리면 **녹화 중인 에피소드와 추론 품질이 조용히 망가진다** —
지금은 그걸 사람이 화면을 보고 있어야만 안다. 감시가 있으면 알람(토스트+벨)으로
바로 안다.

[회색 카드 보정](gray-card-calibration.md)이 "시작점을 재현 가능하게"라면,
이건 **"시작한 뒤에 변하지 않았는가"**다. 서로 보완한다.

## 2. 지금 이런 상태다 — 쓸 수 있는 재료

| 재료 | 사실 | 함의 |
|---|---|---|
| 프레임 | camerad/rsd 가 `/dev/shm` 세그먼트로 상시 발행, 다중 소비자, 읽기는 memcpy 한 번 | **카메라를 새로 열 필요가 없다.** yolod 와 같은 소비 방식 |
| 측정 지점 | 세그먼트 = 녹화·정책이 읽는 바로 그 프레임 | **"정책이 보는 그대로"를 감시한다.** AE 가 보상해서 화면이 안정하면 정책 입장에선 문제 없음이 맞다 — 보상 못 한 변화만 남고, 그게 정확히 잡고 싶은 것 |
| 알람 경로 | `device_watch`(게이트웨이 2초 루프) → 전이에서만 WS `device_alert` → SystemMessages 토스트+벨, 복구 시 clear | **다 있다.** 판정 하나 얹고 문구는 백엔드가 조립하는 기존 규칙 그대로 |
| 노출·WB 잠금 | [카메라 프로파일](camera-profiles.md) ☑ — connect 시 자동 적용 | 잠근 카메라는 측정이 곧 장면이다. AE 켠 카메라는 §4 교란 참고 |

## 3. 알고리즘 — 프레임을 숫자 몇 개로, 숫자를 판정으로

### 3-1. 프레임 → 특징 (매 샘플, 카메라당)

64×64 로 축소(INTER_AREA)한 뒤 계산한다. 축소가 곧 노이즈 평균화고, 비용은 μs 대라
게이트웨이 루프에 얹어도 된다.

| 특징 | 계산 | 잡는 것 |
|---|---|---|
| 밝기 | 평균 luma (0.299R+0.587G+0.114B) | 조명 세기 변화 |
| 포화/암부율 | 250 초과·5 미만 픽셀 비율 | 과다·과소 노출 (회색 카드 문서의 "포화 5%" 와 같은 개념) |
| 색 | **log₂(R̄/Ḡ), log₂(B̄/Ḡ)** | 색온도·WB 변화. 절대 Kelvin 은 안 구한다 — 보정 없인 숫자가 거짓말이고, 우리가 필요한 건 **변화량**뿐. 로그라 노출과 분리된다 |
| 3×3 그리드 luma | 칸별 평균 luma 9개 | 전역/국소 구분 (아래) |

⚠ **팔이 화면을 지나간다.** 손목 카메라는 어두운 팔이 화면 30%를 덮는 게 정상
동작이다 — 전체 평균만 보면 이게 조명 변화로 보인다. 그래서 **전역성 판정**을
넣는다: 9칸 중 7칸 이상이 같은 방향으로 움직였을 때만 조명이다. 물체·팔은
몇 칸만 움직인다. 이게 이 설계에서 거짓 경보를 막는 핵심 한 수다.

### 3-2. 시계열 → 판정

**EWMA 두 개** (지수이동평균, 시간 상수 fast≈2초 / slow≈60초):

```
이상 = |fast − slow| > 임계  가  N=3 샘플 연속
```

- slow 가 "지금까지의 정상", fast 가 "방금". 괴리가 급변이다.
- **임계는 절대 단위다** (밝기 Δ20/255, 색 Δ0.10 부터 시작해 실측 조정).
  σ 기반(z-score)을 안 쓰는 이유: 야간 정지 장면은 분산이 0 에 수렴해
  z 가 폭발한다 — 조용한 화면일수록 예민해지는 감시는 못 쓴다.
- **히스테리시스**: 진입 3연속, 해제 5연속 정상 → alert clear (device_watch 의
  add/clear 와 같은 모양). 경보가 깜빡거리면 아무도 안 믿는다.
- 판정 후 slow 는 새 값으로 수렴한다 → 조명이 **바뀐 채 유지**되면 경보는 한 번
  뜨고 새 상태가 정상이 된다. 원하는 동작이다 — "바뀌었다"를 알리는 것이지
  "옛날과 다르다"를 영원히 우기는 게 아니다.

### 3-3. 기각한 후보

| 후보 | 기각 이유 |
|---|---|
| CUSUM / Page-Hinkley | 수십 분짜리 완만한 드리프트(해가 진다)용으론 정석이지만 파라미터 직관이 없다. 1단계 요구는 "심하게 튀면"이라 EWMA 괴리로 충분. 드리프트는 2단계에서 재검토 |
| 히스토그램 거리 (EMD·χ²) | 평균+그리드로 못 잡는 조명 변화가 실측에서 나오면 그때. 지금 넣으면 임계값 튜닝만 두 배 |
| z-score (rolling σ) | 위 서술 — 정지 장면에서 폭발 |
| 30fps 전수 분석 | 조명 사건은 초 단위다. 1Hz 샘플이면 2~4초 안에 알람 — 충분하고, 60Hz 플리커는 어차피 이 방법론 밖(§6) |
| ML / 장면 이해 | 평균 다섯 개로 되는 일이다 |

## 4. 교란 요인 — 알고 시작해야 하는 것

- **AE/AWB 가 켜진 카메라**: 조명이 변해도 카메라가 보상하면 측정은 안 움직인다.
  §2 대로 그건 오보가 아니라 **정답**이다(정책도 못 느끼니까). 대신 보상이
  **진동**하면(노출 헌팅) fast EWMA 가 흔들리는 것으로 보인다 — 2단계에서
  "노출이 흔들립니다" 경보 후보.
- **팔·사람 통과**: 전역성 판정(§3-1)이 막는다. 실측 항목.
- **깊이 세그먼트**: 밝기 감시가 무의미하다 — 컬러 세그먼트만 본다(§7 확인 항목).

## 5. 측정값은 알람 전용이 아니다 — 발행물로 낸다

밝기·색 특징은 알람 말고도 쓸 데가 있다. 측정과 판정(EWMA)을 한 몸으로 짜면
두 번째 소비자가 나타날 때 측정을 다시 꺼내 쓰지 못한다 — 그래서 **측정은
버스 계약으로 발행하고, 알람은 소비자 1호일 뿐이다.**

| 소비자 | 쓰임 | 단계 |
|---|---|---|
| 알람 판정 | §3-2 EWMA — 급변이면 `device_alert`. **수집·추론 중에도 계속 돈다** — 에피소드가 오염되고 추론이 흔들리는 바로 그 순간이라, 활동 중이라고 끄는 건 거꾸로다 | 1단계 |
| 수집·추론 화면 | 프리뷰 옆에 실시간 밝기·색 표시 (REST 미러 폴링 — 프리뷰 갱신 루프에 얹는다) | 1단계 |
| 에피소드 뷰어 | **보고 있는 프레임**의 밝기·색 표시 — 버스가 아니라 저장된 영상에서 잰다 (아래) | 2단계 (확정) |
| 카메라 페이지·대시보드 | 밝기·색 시계열 차트 (대시보드 trends 패턴 재사용) | 2단계 |
| 녹화 메타데이터 | 에피소드에 당시 조명을 기록 — "오전 데이터와 오후 추론이 색이 다르다"([graycard](gray-card-calibration.md) §1)를 사후 검증 가능하게 | 2단계 |
| 오케스트레이터 | 에피소드 시작 전 "조명 안정" 게이트 (`get_detections` 와 같은 `ts` 신선도 검사) | 필요 시 |
| 평가 통계 | eval 기록에 조명 첨부 — 성공률과 조명의 상관 | 필요 시 |

발행 규칙은 vision 검출의 복제다:

- 키 `piper:light:<cam>` — **최신값 덮어쓰기 + TTL** (큐 아님: 소비가 밀리면
  낡은 값이 쌓일 뿐이다). payload 에 `ts` 를 넣어 소비자가 신선도를 재판단한다
- payload 는 **원시 특징만**: `{ts, luma, sat_pct, dark_pct, log_rg, log_bg,
  grid[9]}`. EWMA·임계·연속 횟수 같은 판정 상태는 안 싣는다 — 그건 알람
  소비자의 내부 사정이고, 다른 소비자는 원시값으로 제 판단을 한다
- REST 는 버스 값을 그대로 비춘다 (UI·외부 소비자용, 경로는 구현 때)
- **소비자는 버스 키에만 의존한다.** 발행자를 게이트웨이에서 데몬·전용 유닛으로
  옮겨도(§6) 계약은 불변 — 그게 이 절을 §6 앞에 두는 이유다

### 라이브와 저장본을 같은 자로 잰다

에피소드 뷰어의 요구는 경로가 다르다 — 버스(지금)가 아니라 **저장된 영상**이다.
§6-1 라이브러리가 여기서 값을 한다: 같은 함수가 두 입력을 받는다.

- **라이브**: shm 프레임 → 위 버스 계약으로 발행
- **저장본**: 뷰어가 이미 쓰는 디코드 캐시 프레임(`/frames/{cam}/{i}`)에서
  요청 시 계산 — 64×64 축소 후 평균이라 요청당 1ms 미만. 프레임 응답에 얹거나
  별도 GET
- 에피소드 **전체** 밝기 트랙(스크러버 밑 미니 곡선 — "어디서 튀었나"를 보고
  점프)은 처음 열 때 한 번 계산해 사이드카로 캐시. 프레임 하나 표시보다 이게
  뷰어에서 진짜 쓸모다

⚠ **저장할 때 기록하지 않고 볼 때 잰다.** 동기화 문제가 없고, 데이터셋 스키마를
안 건드리고, **이미 수집해 둔 데이터셋에도 소급 적용**된다. 그리고 자가 같으므로
라이브 알람의 임계와 뷰어의 눈금이 같은 단위다 — "녹화 때 경보 떴던 게 여기구나"
가 숫자로 이어진다.

## 6. 어디서 돌리나 — 수학은 공용 라이브러리, 발행자는 게이트웨이

두 결정을 가른다. **"코드가 어디 사는가"** 와 **"어느 프로세스가 도는가"** 는
다른 질문이다.

### 6-1. 코드는 `piper_cam` — graycard 옆

특징 추출 + EWMA 판정은 순수 함수로 `piper_cam/lighting.py` 에 둔다.
`piper_cam.graycard` 가 정확히 이 선례다 — *"camerad 와 rsd 가 함께 쓰고,
하드웨어 없이 경계를 시험할 수 있어야 한다"*. rsd(piper_rs)도 백엔드도 이미
piper_cam 을 import 한다. 어디서 돌리든 이 경계는 같다.

### 6-2. 발행자를 rsd·camerad 에 심지 않는다 — 검토했고, 이유는 셋

"장치를 쥔 데몬이 판정한다"(device_watch)는 원칙이 있어 데몬 삽입이 구조상
맞아 보이지만, 그 원칙은 **소유자만 알 수 있는 사실**(장치 노드 소멸, 파이프라인
사망)에 대한 것이다. 프레임 **내용**은 소비자 누구나 같은 바이트를 본다 —
특권 정보가 아니고, 그래서 내용 분석인 yolod 도 데몬에 심지 않고 소비자로 뒀다.
같은 이유 셋:

1. **크래시 격리.** camerad/rsd 는 절대 죽으면 안 되는 프로세스다(D405 D-state
   전례, "발행이 실패해도 캡처는 산다"는 publish 의 규칙). 판정 코드를 하드웨어
   데몬 **둘의** 캡처 루프에 넣으면 가장 위험한 자리에 새 코드가 두 벌 생긴다.
2. **재시작 경제학.** 임계값은 실측 튜닝(§8-4)을 여러 번 돈다. rsd/camerad
   재시작은 스트림이 끊겨 녹화·추론 중엔 막혀 있고(`require_idle`), 두 데몬 중
   하나만 재시작하면 **판정 로직 버전이 갈린다**(유닛 낡은 코드 함정). 게이트웨이는
   재시작해도 녹화·스트림이 살도록 이미 설계돼 있다(reattach).
3. **데몬에 넣어도 얻는 게 없다.** 알람은 어차피 게이트웨이 WS 를 지나야 사람에게
   닿는다 — 게이트웨이가 죽어 있으면 어디서 감지하든 알람은 못 간다. 샘플 주기도
   소비자 쪽에서 얼마든지 올릴 수 있다(세그먼트는 30fps 로 갱신된다).

덤: rsd 는 발행 **전에** 프레임을 가공한다(`set_background_mask`). 세그먼트에서
재면 마스킹 **이후** — 정책이 보는 그대로다. 캡처 루프에서 재면 그 지점을
일부러 골라야 한다.

### 6-3. 그래서

`device_watch` 의 2초 루프 옆에 얹는다(세그먼트 나열도 이미 거기 있다). 측정 →
버스 발행까지가 이 루프의 일이고, 알람 판정은 발행된 값을 읽는 소비자다(같은
프로세스라도 층은 가른다 — trends 샘플러와 대시보드 판정의 관계와 같다).
게이트웨이 재시작이면 기준선(slow EWMA)이 리셋되는데, 워밍업 몇 샘플 동안
판정을 쉬면 된다. 주기를 올려야 하면(오케스트레이터 게이트 등) 전용 태스크로
빼면 되고, 게이트웨이 밖으로 옮겨야 하면 §5 계약 덕에 배선 교체다.

## 7. 안 넣을 것

- **자동 대응** — 녹화 중단·노출 자동 조정은 안 한다. 알람만. 에피소드를 버릴지는
  사람이 정한다 (E-stop 대상 재검토와 같은 종류의 결정을 코드가 내리면 안 된다)
- **절대 색온도(Kelvin) 표시** — 보정이 필요하고, 그건 회색 카드 문서의 몫
- **플리커 감지** — 형광등 60/120Hz 는 1Hz 샘플로 원리적으로 못 본다. 필요해지면
  별개 기획(셔터·밴딩 문제라 접근 자체가 다르다)
- **카메라별 개별 임계 UI** — 전 카메라 공통 기본값으로 시작. 실측에서 카메라마다
  갈라야 한다는 게 확인되면 그때
- **프레임 단위 동기 기록** (데이터셋에 프레임별 조명 컬럼) — 뷰어의 프레임별
  표시는 이게 아니라 **볼 때 재기**(§5)로 푼다. 저장이 필요해지는 건 정책이
  조명을 입력으로 먹는 날이고, 그때 wrapper 가 같은 라이브러리(§6-1)로 재면 된다

## 8. 구현 순서

1. `piper_cam/lighting.py` — 특징 추출 + EWMA 판정 (순수 함수: 프레임 배열 in,
   판정 out. 녹화된 npz 로 테스트. graycard 의 포화율 계산과 공유 검토)
2. 버스 계약 (`piper:light:<cam>` — contract.py, vision 복제) + 게이트웨이
   샘플러가 측정·발행 + REST 미러
3. 알람 소비자: EWMA 판정 → `device_alert` (add/clear)
4. 수집·추론 화면에 실시간 표시 (REST 미러를 프리뷰 갱신 루프에서 폴링)
5. 실측 튜닝: 조명 끄기/켜기·창가 구름·팔 통과·사람 통과로 임계·연속 횟수 조정
6. 에피소드 뷰어: 프레임별 값 표시 → 에피소드 트랙 사이드카 캐시(스크러버 곡선)
7. (2단계) 카메라 페이지 밝기·색 시계열 차트, 녹화 메타데이터 기록,
   느린 드리프트·노출 헌팅 경보 재검토
