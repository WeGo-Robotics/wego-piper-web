# 목표 위치 입력 — 집을 물체의 화면 좌표를 정책 입력에 넣는다

상태: **◐ 1~6 구현·학습, 프로브 ☑** (2026-11-02). 변환기·라벨러·wrapper·게이트웨이·apple-sort 0.1.7·프로브.
학습 `outputs/train/2026-11-01/23-20-58_smolvla_s`(110k, 기준 `00-12-04_smolvla_s` 와 같은 설정) — 프로브에서 목표를
쓴다(§8). v0.5.26 으로 나갔다. 117 첫 실기에서 정책이 사과보다 **좌표를 믿는** 것을 봤다 — 플러그인이 목표를 사과에
붙여 둔다(0.1.7, §5·§8-3). 남은 것: .117 실기 A/B. 데이터셋이 부적합했던 이유 정리는 §9.

## 왜

사과 분류 SmolVLA-S 는 판의 정해진 칸에서는 집는데 **임의 자리의 사과**는 못 집는다. 데이터가 모자란 게 아니다
(`dualarm_sort_apple`, 2026-11-01 실측):

| | |
|---|---|
| 목표가 있는 집기 | 285회 — 작업판 70칸 **전부**, 칸당 3~5회 |
| 같은 종류가 판에 하나 더 있던 집기 | 60회 |
| 목표 없음(`empty_target`) | 15회 — 정책은 가만히 |

막히는 곳은 둘이다. (1) 지시문은 종류만 말한다 — 같은 종류가 둘이면 어느 것인지 화면만 보고 정해야 하고,
학습에서 어느 것을 집을지는 시나리오 계획이 정했으니 정책에게는 동전 던지기다. (2) 시연은 40mm 격자점에만
있다 — 칸 사이 자리는 이미지 특징 공간에서 보간해야 한다. 집을 자리를 **저차원 좌표로 직접** 주면 둘 다 풀린다.
팔 쪽(`{arm}` 지시문, apple-sort 0.1.1)이 이미 같은 처방의 1차원판이었다.

## 1. 인코딩 `rff_v1` — 가까운 자리는 비슷한 벡터

좌표는 위 카메라 프레임의 폭·높이로 나눈 `(u, v)` ∈ [0, 1]² 다 — 플러그인의 검출 상자 중심과 같은 정의.
위 카메라는 고정이고 정책의 이미지 입력도 이미 그 카메라 자세에 묶여 있어 새 취약점이 아니다.

"가까운 좌표가 비슷한 벡터" = 내적이 거리의 함수로 줄어든다 = 커널. 가우시안 커널을 랜덤 푸리에 특징으로 편다:

```
p = (u, v·h/w)                              # 등방성 — 세로 1px 과 가로 1px 이 같은 거리
γ(p) = [cos 2π b_k·p, sin 2π b_k·p]  k<m      ⟨γ(p), γ(q)⟩/m ≈ exp(−|p−q|² / 2ℓ²)
b_k ~ N(0, σ²I),  σ = 1/(2πℓ)
state 뒤에 붙는 것: [valid, u, v, cos…(m), sin…(m)]      목표 없음 = 전부 0
```

- **ℓ = 28mm.** 반 칸(20mm) 떨어진 자리가 이웃과 0.77 비슷해 칸 사이를 보간하고, 사과 하나 거리(80mm)면 0.02
  로 갈린다. mm → 화면은 라벨러가 잰 1.072 mm/px (§2) — ℓ = 26.1px.
- **주파수를 무작위로 뽑지 않는다.** 반지름은 레일리 분위수, 방향은 황금각으로 고르게 깐다(준몬테카를로).
  m=7 에서 판 위 거리쌍으로 잰 커널 오차: RMS **0.169** (무작위 200벌 중앙값 0.200), 3ℓ 넘게 먼 쌍의 유사도
  p99 **0.47** (0.58). 시드가 필요 없고 사양에 행렬을 그대로 적는다.
- **원좌표 u, v 도 둔다.** 코사인 7개는 먼 거리에서 되풀이된다(±0.5) — 원좌표가 가른다. 팔 고르기
  (`u < 0.52`)는 원좌표의 선형 경계다.
- **`valid` 는 목표 없는 에피소드가 있을 때만.** 없으면 그 칸이 늘 1 이라 표준편차 0 — MEAN_STD 분모가
  `std + 1e-8` 이라 추론에서 0 이 들어오는 순간 1e8 배로 터진다. 그래서 빼고, 그 체크포인트는 목표가 올 때까지
  서 있는다(§4). 사과 분류는 15개가 있어 `valid` 가 있다 — 목표 없음 = "가만히" 를 배웠다.
- 차원: 14 + 17 = **31 ≤ SmolVLA `max_state_dim` 32**. `state_proj` 가 32 폭을 받고 학습되므로(`train_state_proj`)
  정책 코드는 한 줄도 안 바뀐다. ACT 계열도 state 토큰 하나로 그대로 들어간다(한도 없음).

목표는 **에피소드마다 하나, 끝까지 고정**이다. 쥔 뒤에는 검출이 사라져 값이 흔들리고, 플러그인도 지시문을
쉼 순간에만 정하므로 학습과 추론에서 목표가 바뀌는 때가 같다.

## 2. 라벨 — `plugins/apple-sort/tools/targets.py`

**목표 = 시작 프레임의 그 종류 사과 중 끝 프레임에서 사라진 것.** 계획은 칸을 말하지만 칸은 화면 좌표가 아니고
사람이 놓은 자리는 칸에서 어긋난다. 그래서 위치는 검출에서 얻고 계획은 종류와 확인에만 쓴다.

- 검출·판 위 판정은 **플러그인과 같은 코드**(`main.board_apples`, `_one_per_apple`, 같은 모델·conf·ROI) —
  추론에서 보내는 목표와 학습 목표가 같은 정의여야 한다. 시작·끝 각각 3장(1·3·5 프레임 안쪽)의 중앙값.
- 칸 → 화면 호모그래피: 종류가 판에 하나뿐인 에피소드의 (계획 칸, 검출 중심) 짝 467개, RANSAC 20px(반 칸) —
  inlier 447, RMSE 8.1px, 판 가운데 **1.072 mm/px**. (8px 로 잡으면 inlier 가 절반이다 — 사람이 놓은 자리가
  칸에서 중앙값 8mm 어긋나서. 판이 움직였는지 에피소드 구간별 오차로 봤다 — 안 움직였다.)

결과 (`dualarm_sort_apple`, 300 에피소드, 40초):

| 출처 | 수 | |
|---|---|---|
| `vanished` | 280 | 계획 칸까지 중앙값 7.6mm · p95 16.5mm |
| `plan_cell` | 5 | 전부 복구 변형 — 그리퍼가 사과를 덮은 채 **시작**하는 에피소드라 시작 프레임에 안 보인다. 계획 칸의 화면 자리 |
| `empty_target` | 15 | `valid: false` |

표시된 9개 중 나머지 4개는 사라진 것이 맞는데 계획 칸에서 41~114mm — 사람이 한 칸 옆에 놓았다(접촉 인화로
확인). 표 사본이 변환된 데이터셋 `meta/piper_target_source.json` 에 따라간다.

## 3. 변환기 — `python -m lerobot_policy_piper.target <데이터셋> --targets <표>`

델타 변환기와 같은 꼴: 원본은 그대로, `<이름>_target` 사본, 비디오는 하드링크, LeRobot 로더로 자체 검증.

- **통계**: 앞쪽(로봇 state 14)은 원본 값 그대로 — 기준 학습과 정규화가 **비트 단위로 같다**(실측 확인). 새 칸만
  전 프레임으로 정확히 센다(에피소드 안에서 상수라 에피소드 통계를 모아 분위수를 근사하면 틀린다). 새 칸 중
  하나라도 상수면 거절.
- **사이드카** `meta/piper_target.json`: 사양 전체(이름·주파수·종횡비·ℓ·카메라·로봇 state 이름) + 에피소드별 목표.
- **순서: 목표 → 굽기.** 구운 사본은 거절 — 굽기가 `meta/` 를 통째로 옮겨 `<이름>_target_stage` 도 목표 입력으로
  읽힌다. 델타와는 순서 무관(델타는 액션, 이것은 state, 채널은 이름으로 찾는다).

실측: `dualarm_sort_apple` → `_target`(3.6초) → 굽기 → `_target_stage`. stage 라벨 수가 `_stage` 와 같고, 새 칸
표준편차 valid 0.26 · u 0.22 · v 0.18 · 코사인/사인 0.66~0.70.

## 4. 추론 — 판정은 백엔드, 붙이기는 wrapper

**판정** ([backend/app/services/target_input.py](../backend/app/services/target_input.py)) — 델타와 같은 순서:
체크포인트 표식 `piper_target_input.json` → `train_config.json` 의 데이터셋 → 그 `meta/piper_target.json` →
이름이 `_target` 인데 데이터셋이 없으면 `unknown`(막는다) → 아니면 목표 입력 아님. 목표 입력이면 추론 시작이
`--target-spec <사양>` 을 싣고 표식을 남긴다. 아니면 명령이 한 글자도 안 바뀐다.

**붙이기** ([wrapper/target_input.py](../wrapper/target_input.py)): 로봇 state 뒤에 지금 목표를 같은 식으로 편다.
목표는 버스 파라미터 `target` — `[u, v]`(0~1 로 자른다) 또는 `null`(지움). 관측을 잡을 때 한 번 읽어 모델
입력과 디버그 기록이 같은 값이다.

| 사고 | 방어 |
|---|---|
| 목표 입력 체크포인트를 사양 없이 | wrapper 가 길이(31 vs 14)로 **로봇을 연결하기 전에** 거절. 백엔드는 `unknown` 이면 400 |
| 다른 데이터셋의 사양 | 표식과 인자 대조(wrapper) · 손으로 고친 인자의 `--target-spec` 대조(백엔드) |
| 로봇 state 가 학습 때와 다름 | 이름 대조 — 다르면 거절(순서로 붙이면 엉뚱한 자리에 목표가 붙는다) |
| 정책 서버 모드 | 거절 — 목표 칸을 만드는 것은 로컬 wrapper 다 |
| 목표 없음을 안 배운 체크포인트 | 목표가 올 때까지 일시정지처럼 선다(`waiting_target`) |
| 모양 틀린 목표 | 게이트웨이가 버리고 경고, wrapper 는 지운다(목표 없음 쪽으로 틀린다) |

남는 기록: 텔레메트리 `target_pos`, 디버그 `observations.jsonl` 의 `target_pos`(추론마다), 실행 기록의
`target_input` 요약과 도중 변경. ⚠ CSV 에는 안 넣는다 — 분석 도구가 `target_*` 열을 모터로 읽는다.
추론 검증(`/inference/validate`)은 관절 수를 state 앞부분과 견주고, 목표를 보내는 플러그인을 켜라고 경고한다.

## 5. 플러그인 — apple-sort 0.1.6

지시문을 정하는 순간 집을 사과 하나를 골라 그 중심을 `set_params(target=[u, v])` 로 — **지시문보다 먼저**
보낸다. 고르기: 그 쪽(팔)에 그 종류가 보인 가장 최근 프레임에서 점수가 가장 높은 것, 위치는 쉼 창 프레임마다
그 근처(25px)에 보인 중심의 중앙값. 우리가 추론을 쉬게 하고 지시문을 비울 때 목표도 지운다. 미리보기에 자홍 원,
저널의 결정에 `target_pos`. 게이트웨이가 `target` 을 모르면(이 변경 전) 한 번 경고하고 지시문은 그대로 간다.

**0.1.7 — 목표는 사과를 따라간다** (`_follow_target`, 이유는 §8-3). 집는 동안(판단 → 기록) 프레임마다 그 사과를 다시
찾아, 목표에서 `follow_px`(60) 안의 같은 종류(그 팔 쪽)가 3장 연달아 6px 안에 서 있고 목표에서 20px 넘게
떨어졌으면 목표를 그 자리로 옮긴다. 안 옮기는 때: 쥐고 있다 · 그 쪽의 그 종류가 고를 때보다 덜 보인다(가림·집음) ·
상자 폭·높이가 고를 때에서 ±15% 밖(그리퍼가 덮으면 중심이 그리퍼 반대쪽으로 쏠린다 — 따라가면 목표가 달아나고
팔이 쫓는다) · 두 번째로 가까운 것이 가장 가까운 것의 1.5배 안. 문턱은 시연 280개(검출 18,860장, 5Hz)에서 잰
것이다 — 서 있는 사과의 상자는 99.8% 가 ±15% 안, 그리퍼가 덮어 10px 넘게 쏠린 상자 117개 중 ±15% 안은 6개(쏠림
최대 17px). 같은 규칙을 시연에 돌리면 한 번도 안 옮긴다(2.5·5Hz). `follow_px` 보다 멀리 밀렸으면 따라가지 않고,
지시문 어긋남이 "그 쪽에 그 종류가 있나" 대신 "목표 자리 근처에 있나" 를 봐서 멈추고 다시 고른다. 그 쪽의 그
종류가 고를 때보다 덜 보이면(가렸을 수 있다) 예전 판정으로 물러서서, 집기 전 어긋남은 예전과 같은 수다(시연 모의
1~2개). 남는 기록: 저널 `target_moves`([지시 뒤 초, u, v, 옮긴 px]), 미리보기의 처음 자리(회색 ×)와 선.

**0.1.8 — 회차가 끝나면 목표를 지운다.** 0.1.7 실기에서 빨강 둘 중 목표를 상자에 넣고 회차가 끝났는데 목표가 그 빈
자리에 남았다 — 정책은 원위치에서 잠깐 쉬고 다시 빈 자리로 집으러 가기를 되풀이했고, 쉼이 안 잡혀 다음 판단도 못
했다(13회차까지). 어긋남도 "덜 보이면 가렸을 수 있다" 물러섬이 남은 빨강을 보고 가려 줬다. 그래서 끝난 회차의 목표는
지우고(목표 없음 = 선다), 물러섬은 집는 중 쥐기 전에만 쓴다.

**0.1.9 — 위 카메라 보정** (`_calibrate_view`). 정책은 화면 좌표를 학습 녹화 때 자리로 읽는데 117 위 카메라 화면은
녹화 뒤 38px(≈41mm) 비켜나 있었다(§8-3). 켤 때 판 모서리 AprilTag(36h11, 태그 2·3)로 지금 화면 → 학습 화면
닮음변환을 재고, 검출한 사과 중심을 학습 좌표로 옮긴 뒤 ROI·팔 경계·목표를 정한다. 기준은
`plugins/apple-sort/view_ref.json` — `tools/view_ref.py` 가 학습 데이터셋 프레임 100장에서 잰 표지 모서리(흔들림 p95
0.5~1px)다. 학습 프레임을 117 자리로 옮긴 영상에서 보정 뒤 사과 자리 오차는 중앙 0.3px · p95 1.0px(보정 없으면 36px).
117 실물 프레임은 (+2, +39)px · ×1.016 · 잔차 0.6px이고, 표지에서 300px 위 커튼 경계도 2px 안에서 맞는다. 판이 로봇에
대해 그대로라는 전제다(원위치 팔도 37px 같이 밀려 있었다). 정책이 보는 위 카메라 이미지는 그대로 비켜나 있어 목표만
맞춘다 — 정책이 좌표를 90% 넘게 따르니 남는 어긋남이 작을 것으로 보지만 실기 확인 전이다.

**0.1.10 — 정책 이미지도 편다** (`view_image`, 이유는 §8-3). 잰 변환을 그대로 버스 `view_warp` 로 보내고, wrapper
([wrapper/view_warp.py](../wrapper/view_warp.py))가 그 카메라 스트림을 읽는 정책 카메라 이미지를 학습 화면으로 편다 —
이미지·목표가 같은 행렬로 같이 맞는다. 값은 `{"stream": "top", "frame": [640, 480], "m": 2×3}`(지금 화면 px → 학습
화면 px) 또는 `null`(끔). 게이트웨이(`param_bridge.view_warp_value`)와 wrapper 가 같은 규칙으로 받는다 — 배율 축마다
0.8~1.25 · 회전 10° · 화면 가운데 이동 폭·높이의 절반까지, 뒤집힘·모양 틀림은 버린다(wrapper 는 끈다 — 틀린 행렬로
