# 에피소드 분석기 — POS분석 (파지 자세 분포)

> 상태: ◐ 1단계 ☑ · 2단계 중 A1 커버리지 · A2 접근 동작 ☑ (2026-10-21) · 나머지 ☐ — 다음 후보는 §6

> `GET /api/phase/{id}/grasps` ([backend/app/routers/phase.py](../backend/app/routers/phase.py)) ·
> [frontend/src/components/PosAnalysis.tsx](../frontend/src/components/PosAnalysis.tsx) ·

에피소드 뷰어가 "한 에피소드를 자세히" 라면 분석기는 "전부를 모아서" 본다. 첫 분석은
**물체를 잡는 순간의 팔 자세가 어떻게 퍼져 있나** — 데모가 작업 공간을 고르게 덮는지,
빈손 파지가 어디에 몰리는지, 수집하는 동안 위치가 밀렸는지를 한 그림에서 읽는다.

## 1. 자리 — 에피소드 화면의 탭

`에피소드 [뷰어 | POS분석]` — 탭은 제목 바로 옆. 별도 페이지가 아니라 탭인 이유는
**오가는 화면이기 때문**이다: 분포에서 이상한 점을 고르면 [뷰어에서 열기] 로 그 프레임을
바로 보고, 탭을 돌아오면 고른 데이터셋·필터가 그대로다(상태가 `EpisodesPage` 에 남는다).

- 뷰어의 데이터셋 `<select>` 는 POS분석 탭에서 숨는다 — 여기는 **여러 개**를 고른다.
- 뷰어 단축키(Space·J/K·←→)는 POS분석 탭에서 꺼진다. 안 보이는 재생이 움직이면 안 된다.

## 2. 파지 순간의 정의

새 검출기를 만들지 않는다. 페이즈 사이드카(`meta/phase_labels.json`, [01-phase-annotation](01-phase-annotation.md))의
**GRASP 구간 시작 프레임**이 파지 순간이다. 사람이 고친 라벨도 같은 파일이라 그대로 반영된다.

| 결정 | 근거 |
|---|---|
| 시작(닫기 시작)을 쓴다 | 닫히는 동안 말단 이동 중앙값 1.0~1.6mm, p90 2.7~4.2mm (bolt_two1·min_cube_071410·yeonwonju-0709-team1 실측) — HOLD 시작과 같은 자세다. 빈손에는 HOLD 가 없어 성공·실패를 같은 잣대로 보려면 시작뿐이다 |
| 결과 = 다음 구간 | 다음이 HOLD 면 **물음**, 아니면 전부 **빈손** |
| 그리퍼만 **닫기를 마친 뒤** 값 | 구간 끝에서 0.5초 더 본 최소 열림. 시작에서는 거의 다 열려 있어(95~100) 아무것도 안 말해주고, 구간 끝은 아직 닫히는 중일 수 있다(FSM 은 갭만 보고 5프레임 만에 HOLD 로 넘긴다). 물었으면 물체 폭(큐브 33.9), 빈손이면 0 근처 |
| 라벨이 데이터보다 길면 버린다 | 에피소드를 자르고 재분석 안 한 경우. 마지막 프레임으로 눌러 담으면 엉뚱한 자세가 파지로 찍힌다 |

라벨이 없는 데이터셋은 목록에 [분석] 이 뜬다 (`POST /api/phase/{id}/analyze` 그대로).

녹화를 더 하면 라벨 없는 에피소드가 생긴다 — 목록의 **[재분석]** 이 그것만 분석한다(라벨 없는 에피소드가
있으면 `재분석 (새 N)` 으로 강조). ⚠ **전체 재분석이 아니다.** 전체 재분석은 검토 표시(✔)·메모는 지키지만
사람이 고친 구간을 자동 라벨로 덮어쓴다(`labeler.save`). 기준값도 사이드카에 저장된 것을 그대로 보낸다 —
태스크마다 다르다. 옛 라벨러(사이드카 version 1)로 만든 데이터셋이면 새 에피소드만 지금 라벨러로 매겨진다:
yeonwonju-0710-yonseitest 로 재보니 단계 순서와 **GRASP 시작 프레임은 한 프레임도 안 달랐고**(파지 순간은
그대로) 다른 경계만 조금 움직였다(2026-10-23).

### 양팔 — 두 팔을 다 본다

⚠ **사이드카에는 에피소드마다 한 팔의 페이즈만 있다.** FSM 이 단일 pick 모델이라 라벨러는
더 활동적인 그리퍼 하나(`fsm.main_gripper`)로만 라벨을 낸다. 그런데 실제 양팔 데이터는 거의
매 에피소드 **두 팔이 다 잡는다** (dualarm_cube_4point 15/15, two_arm_bolt_2 49/50), 그리고
"더 활동적" 의 차이는 표준편차 24.6 대 25.0 같은 동전 던지기다. 처음 구현은 사이드카만 읽어
파지가 절반만 나왔다 (dualarm_cube 30 → 15).

그래서 주 팔은 사이드카(사람이 고친 라벨 포함)에서, **나머지 팔은 같은 FSM 을 그 팔의 7채널에
즉석으로** 돌려 뽑는다. 임계값은 사이드카에 저장된 것. 이벤트의 `source`(`sidecar` | `fsm`)가
둘을 가르고, 화면은 `fsm` 파지에 "사람 검토 없음" 을 밝힌다.

## 3. 화면

```
에피소드 [뷰어|POS분석]
┌ 데이터셋 (n개 선택) ┐  파지 318건 · 에피소드 151 · 빈손 12 · 퍼짐 σ x65 y67 z31 mm
│ ☑ ● bolt_two1  파지100│ ┌──────────── 3D ─────────────┐ ┌ 고른 파지 ─────────┐
│ ☑ ● min_cube   파지150│ │  점 = 파지 (● 물음 · ✕ 빈손)  │ │ ep 2 · 1번째 · ● 물음│
│ ☐   sort_apple  [분석]│ │  스틱 = 고른 자세(색) +       │ │ J1 -23.5° +0.5σ ... │
├ 보기 ───────────────┤ │         중앙 자세(회색)       │ │ 그리퍼(닫은 뒤) 34.1 │
│ 색 [데이터셋|몇 번째|  │ │  바닥 z=0 · base ◆            │ │ [뷰어에서 열기 →]    │
│     물음/빈손|수집순서]│ └──────────────────────────────┘ └────────────────────┘
│ 포함 ☑물음 ☑빈손 ☐검토 │ ┌ 관절별 분포 J1 … J6 · 그리퍼 (상자 + 점) ───────────┐
│ 팔 · 몇 번째 파지 칩   │ └────────────────────────────────────────────────────┘
```

- **팔별 패널** — 보이는 팔 종류(단일 팔·왼팔·오른팔)가 둘 이상이면 3D 가 팔마다 나란한 패널로
  갈린다. 좌표가 팔마다 자기 base 기준이고 두 팔 사이 배치는 어디에도 기록돼 있지 않아서다 — 한
  공간에 겹치면 왼팔이 오른쪽까지 뻗은 것처럼 보인다. 하나를 돌리면 나머지도 같은 방향으로 돈다.
  관절별 분포도 관절 칸마다 팔별 열로 나뉜다(왼팔·오른팔 J1 은 거울상이라 섞으면 없는 두 봉우리가
  생긴다). 퍼짐 σ·중앙 자세·선택 파지의 σ 도 **같은 팔끼리** 잰다.
  실제로 이렇게 나눠 보자 dualarm_cube_4point 의 오른팔 파지가 높이 ~300mm 공중에 몰려 있는 것이
  바로 드러났다(건네받기) — 겹쳐 그렸으면 왼팔의 테이블 파지에 묻혔다.
- **점 위치 = 말단** — 그리퍼 손가락 뿌리 두 점의 가운데, 팔 `base_link` 기준 mm. 플랜지보다
  14cm 앞이라 위에서 잡든 옆에서 잡든 **물체 자리**에 찍힌다. 축 비율은 데이터 그대로(`aspectmode: data`).
- **스틱** — FK 마디(base → J1·J2 → J3 → J4·J5 → J6 → 말단)를 잇는 선. 마디마다 색이 다르고
  (베이스·상완·전완·손목·그리퍼) 관절 이름을 글자로 찍어 색만으로 가르지 않는다. 아무것도 안 고르면
  **중앙 자세**(관절 공간에서 평균에 가장 가까운 *실제* 파지)를 그린다 — 평균 관절값으로 FK 를 돌리면
  아무도 취한 적 없는 자세가 나올 수 있다.
- **관절별 분포** — 3D 에는 세 축만 들어가므로 일곱 채널 전부를 띠로. 3D 와 같은 색·기호, 클릭하면 같은 점이 선택된다.
- **색** — 범주 8색 고정 순서(어두운 면 검증). 데이터셋은 **고른 순서대로 칸을 받고, 빼도 남은 것의 색이
  안 바뀐다.** 산점도에서 모든 쌍이 구분되는 것은 앞 세 칸까지 — 넷째부터는 범례·툴팁이 같이 일한다.
  빈손은 색과 별개로 늘 ✕ 기호다.
- **커버리지**(3D 아래, §6 A1) — 팔마다 따로, 지금 보이는 파지 기준:
  - 표: 데이터셋별 파지 수 · σ x·y · **작업면 칸**(위에서 본 말단을 2/3/5cm 정사각 칸으로 나눠 채운 칸 / 같은
    팔 파지 전체를 덮는 칸 — 격자가 같아 데이터셋끼리 같은 자로 견준다) · **자리 덩어리** · **방향 5° 구간**
    (`yaw` 를 5° 로 나눠 채운 구간 / 36). 여럿이면 "합친 것" 행 — 함께 학습하면 정책이 보는 게 그것이다.
  - 덩어리 = 2cm 안으로 이어지고 **반경 2.5cm 안에 뭉친** 묶음(크기 ≥ max(3, 5%)). 반경 조건이 없으면 촘촘하게
    고루 퍼진 데이터도 한 사슬로 이어져 덩어리 하나로 읽힌다. 파지 10개 이상에서 80% 이상이 덩어리에 들면
    "⚠ 자리 N곳에 몰림". 실측(2026-10-21): bolt_two1 10곳 · singlearm_apple_4point 4곳 · min_cube 3곳 ·
    dualarm_cube 오른팔 1곳(건네받는 자리) 87% 가 걸렸고, two_arm_bolt_2 는 덩어리가 없었다.
  - 그림: 위에서 본 점유 지도(빈 칸은 바탕 그대로, 1:1) + 방향 막대(데이터셋별로 쌓음). bolt_two1·min_cube 는
    방향이 3구간(늘 같은 방향으로 잡았다), two_arm_bolt_2 는 8~10구간.
- **접근 동작**(커버리지 아래, §6 A2) — 파지마다 **접근 속도**(닫기 직전 0.5초)와 **닫는 중 속도**(GRASP
  구간)의 말단 최고 속도. 둘을 가르는 이유: 보통은 멈춰 서서 닫는데(닫는 중 중앙값 7~30mm/s), 튀어나가며
  잡는 버릇은 닫는 중에 드러난다. 닫는 구간을 고정 0.5초로 안 잡는 것은 HOLD 가 5프레임이면 넘어가
  들어 올리기가 섞이기 때문이고, 닫기 시작 프레임은 어느 쪽에도 안 넣는다(중심 차분이 한 프레임 뒤를 봐
  튄 움직임이 "직전" 에 섞인다).
  - 표: 데이터셋·팔별 두 속도의 중앙·p90 과 튀는 파지 수. **튀는 파지** = 같은 데이터셋·같은 팔 안에서
    중앙값 + 3×MAD 초과 그리고 40mm/s 이상(거의 멈춘 데이터의 MAD≈0 에 2~3mm/s 로 걸리지 않게).
    한 파지는 한 번만, 닫으며 튄 것이 우선.
  - 목록: 많이 벗어난 순. 누르면 그 파지가 선택되고 3D 에 **접근 궤적**이 그려진다(들어오는 길 흰색,
    닫는 동안 움직인 길 빨강). 보기 패널의 "접근 궤적 — 모든 파지" 로 전부 켤 수 있다.
  - ⚠ **빈손 파지는 ✕ 로 따로 표시한다.** 놓친 걸 알고 팔을 이미 옮기는 동안 그리퍼가 계속 닫히면 "닫으며
    움직임" 으로 크게 걸린다 — yeonwonju 상위 371·360·338mm/s 가 그랬다. 튀어나가며 **잡는** 것과 다르다.
  - 두 속도는 관절별 분포에도 칸으로 들어가 같은 색·같은 선택으로 본다.
- 고른 데이터셋은 `localStorage['pos-datasets']` 에 남는다. 구운 사본(`_stage`)은 원본과 같은 프레임이라 목록에서 뺀다.

## 4. API

`GET /api/phase/{dataset_id}/grasps`

```jsonc
{ "labeled": true, "fps": 15, "episodes": 50, "reviewed": 9,
  "stick": ["base", "J1·J2", "J3", "J4·J5", "J6", "grip"],
  "events": [{ "episode": 0, "cycle": 1, "frame": 70, "t": 4.667,
               "outcome": "hold",            // hold | empty
               "arm": null,                  // 양팔이면 "left" | "right"
               "reviewed": true,
               "joints": [-14.7, 107.5, -65.0, 4.6, 47.5, -22.7],   // 도
               "source": "sidecar",          // 양팔의 나머지 팔이면 "fsm"
               "gripper": 34.1,              // 닫기를 마친 뒤
               "tip": [346.1, -76.6, 13.0],  // mm
               "yaw": 88.4,                  // 손가락 여닫는 축의 수평 방향(도, 0~180). 축이 거의 수직이면 null
               "approach_speed": 47.8,       // 닫기 직전 0.5초의 말단 최고 속도 (mm/s)
               "closing_speed": 14.1,        // 닫는 동안(GRASP 구간)의 말단 최고 속도 (mm/s)
               "trail": [[…], …], "trail_at": 8,  // 닫기 0.5초 전 → 닫기 끝 말단 경로, 그 안의 파지 순간 위치
               "stick": [[0,0,0], …6점] }] }
```

- ⚠ 라벨이 없으면 404 가 아니라 `{"labeled": false, "events": []}` — 여러 데이터셋을 부르는 화면이
  "분석 전" 과 오류를 갈라야 하는데, 오류 문구는 번역되어 오므로 분기에 못 쓴다.
- 결과는 라벨·parquet 의 mtime 서명으로 캐시한다. 라벨을 고치면 다음 요청이 새로 읽는다.
- 양팔은 두 팔 모두 싣는다(위 "양팔"). 두 팔 사이 배치를 모르므로 좌표는 팔마다 자기 base 기준이다.

## 5. 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 탭 · 다중 데이터셋 · 말단 3D + 스틱 · 관절별 분포 · 선택 상세 · 뷰어 연결 · 양팔 두 팔 추출 + 팔별 패널 | ☑ |
| 2 | POS 탭 보강 — §6 의 A1 커버리지(☑) · A2 접근 동작(☑), 그리고 이상치 목록(관절 공간 마할라노비스, 클릭 시 강조) · 손목캠 썸네일 | ☐ |
| 3 | 새 탭 — §6 의 B1 구성 → B2 장면 검사 → B3 궤적·진행률 | ☐ |
| 4 | 추론 중 파지 위치를 데모 분포 위에 겹치기 — "정책이 학습 분포 밖에서 잡으려다 실패하나?" (§6 C3) | ☐ |

추천 순서는 **A1(☑) → B1 → B2(카메라 틀어짐)**. A1·B1 은 이미 받는 데이터로 작게 끝나고, B2 는
영상 첫 프레임 디코딩이 들지만 데이터를 통째로 버리는 사고를 막는다.

데이터와 측정 방식에 있었다"** 이다. 문제를 찾아낸 분석들이 그대로 분석기 기능 후보가 된다.
아래 "근거" 는 그 페이지의 기록이고, 숫자도 그쪽 실측이다.

### A. POS 탭에 붙일 것

| # | 기능 | 근거 | 비용 |
|---|---|---|---|
| A1 ☑ | **커버리지 지표** — 작업면 격자 점유율 · 그리퍼 방향(yaw) 5° 구간 점유 · 덩어리 수 자동 감지와 "N개로 뭉쳐 있음" 경고. 데이터셋을 여럿 고르면 수치를 나란히 — 새로 찍은 데이터가 범위를 넓혔나 | 무작위로 놓았다고 믿은 시연 60개가 파지 순간 각도로는 **세 덩어리**였다. 손실은 0.086 까지 떨어졌는데 자리가 바뀌면 못 집었다. 배치표를 다시 짠 뒤 파지 위치 σ 5.9 → 11.3, 5° 각도 구간 12개 중 채운 칸 5 → 8 | 작음 — 말단·관절값은 이미 받는다. yaw 만 FK 회전에서 하나 더 꺼낸다 |
| A2 ☑ | **파지 직전 접근 동작** — 파지 직전 0.5초의 말단 속도·방향을 점마다 화살표로, 속도 분포와 "튀어 들어간 에피소드" 목록 | 접근하다 앞으로 툭 튀는 동작의 원인이 **시연자 버릇**이었다(잘 안 잡힐 것 같으면 튀어나가며 집음). 자세를 고쳐 다시 찍었다 | 작음 — 사이드카의 `tip_speed` 를 다시 쓴다 |

### B. 새 탭

| # | 기능 | 근거 | 비용 |
|---|---|---|---|
| B1 | **구성** — task · 수집 날짜 · 결과(물음·빈손·**파지 없음**)별 에피소드 수. 지금 POS 는 파지가 없는 에피소드를 아예 안 보인다 — 정지 시연·실패가 몇 개인지 여기서 | 색별·구간별 구성 차트로 균형을 관리했다. 약이 없을 때 멈추는 **정지 시연 32개**를 따로 찍었다 | 작음 |
| B2 | **장면 검사**(에피소드 첫 프레임) — 기준 프레임 대비 **카메라 이동량** 추이(언제부터 틀어졌나) · 배경 차분 지도, 그 차이가 task·결과와 상관 있으면 "가짜 단서" 경고. [조명 감시](lighting-watch.md)의 밝기·색 값도 에피소드 단위 추이로 | 카메라가 틀어진 걸 늦게 알아 **60개를 전부 버렸다.** 세 장면 중 두 장면에만 볼펜이 찍혔는데 그 유무가 목표 색과 겹쳤다 — 배경 차분으로 찾았다 | 중간 — 영상 첫 프레임 디코딩 |
| B3 | **궤적·진행률** — 페이즈로 정렬한 말단 궤적 다발 3D, 그룹(데이터셋·팔·목표)별로 **언제 갈라지나** · 페이즈 구간 길이 분포(출발 지연·접근·파지)와 이상 에피소드 | "목표를 완벽히 본다(상관 1.00)" 가 **파지 직전에 잰 값**이었다 — 그때는 관절각만으로 답이 나온다. 진행률 30% 에서 다시 재니 0.01. 정상 집기가 홈을 떠나는 시각 중앙값 2.68초 | 중간 |

⚠ **목표 다양성 검사(장면당 목표 수)는 아직 급하지 않다.** 로컬 데이터셋 중 task 가 둘 이상인 것은
`sort_apple_old` 하나뿐이다(2026-10-21). 다만 [LLM 연동](llm-integration.md)처럼 **고른 대상을 집는**
구조로 가면 필수가 된다 — 알약 프로젝트의 핵심 교훈이 "한 장면에 정답이 하나면 모델이 목표 입력을
무시한다" 였다(초기 96개, 목표가 인코더 입력 603조각 중 1개 = 0.17%, 언어 지시로 v1~v9 모두 실패).
처방은 같은 배치에서 목표만 바꿔 세 번 찍는 것. 그때 B1 에 "장면 × 목표" 표를 더한다.

### C. 분석기 밖이지만 같이 볼 것

| # | 기능 | 자리 | 근거 |
|---|---|---|---|
| C1 | **체크포인트 반사실 진단** — 틀린 목표·카메라 가림을 줬을 때 행동이 얼마나 바뀌나, 학습 장면 대 처음 보는 장면 | 엔코더 프로브 화면 | 실패마다 8시간 재학습하던 것을 "입력을 망가뜨려 반응을 재는" 진단으로 바꾸자 확인이 분 단위가 됐다. 틀린 목표 오차 비율이 학습 장면 1.33 · 처음 보는 장면 1.03 — 상승분이 장면 암기였다 |
| C2 | **색상 증강 경고** — 색으로 가르는 과제에서 hue 흔들기 폭이 대상 색 간격을 얼마나 덮나 | 학습 화면 | LeRobot 기본 증강은 색상을 ±18° 흔든다. 빨강–노랑 간격 56° 중 64% 를 덮어 라벨에 잡음을 넣는 셈이었다 — 색상·affine 만 끄고 밝기·대비는 유지 |
| C3 | **실기 파지를 데모 분포 위에** (5단계의 4) + 평가 기록 연결 | POS 탭 | 오프라인 1위 체크포인트가 실기에서 알약을 놓치고 꼴찌가 제대로 동작한 적이 두 번 있었다 — "체크포인트는 실기로 고른다" |
