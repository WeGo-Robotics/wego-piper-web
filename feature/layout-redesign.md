# 화면 레이아웃 개편 — 좌측 세로 내비 + 상단 상태바

상단 가로 내비가 한계에 닿았다. 내비를 **좌측 세로**로 내리고, 비워진 상단은
**상태 표시**에 쓴다.

---

## 1. 왜 지금인가 — 증상이 이미 코드에 남아 있다

**메뉴가 이미 밀려났다.** [pages.ts](../frontend/src/config/pages.ts) 를 보면
**모델**과 **데이터셋**은 `card: true` 인데 `nav` 가 없다 — 대시보드 카드로만
갈 수 있고 상단바에는 없다. 자리가 모자라서 뺀 것이고, 그래서 지금 상단바는
12개, 전체 페이지는 14개다.

**앞으로 확정된 것만 넷 더다.**

| 페이지 | 출처 |
|---|---|
| `/cloud` (자격증명·인스턴스 현황) | [cloud-training](cloud-training.md) 9단계 |
| `/cloud/guide` (온보딩 체크리스트) | [cloud-training](cloud-training.md) 10단계 |
| 페이즈 라벨 편집 UI | [phase-annotation](01-phase-annotation.md) 4~5단계 |
| 조그/수동 조작 패널 | [manual-control](manual-control.md) 1단계 |

양팔([bimanual](bimanual.md))과 오케스트레이터까지 오면 20개에 가까워진다.
**가로는 더 이상 안 늘어난다.** 세로는 늘어난다.

**상태를 볼 자리가 없다 — 이건 이미 사고를 냈다.**
학습이 도는지 알려면 학습 페이지로 가야 한다. 같은 뿌리의 문제가 이 저장소에서
두 번 터졌다:

- 수집 페이지에서 카메라 경보가 안 보였다 → [SystemMessages](../frontend/src/components/SystemMessages.tsx)
  를 만들어 **어느 페이지에 있든 같은 자리에** 뜨게 했다
- 경보가 뜬 상태로 카메라 페이지에 가니 뽑힌 카메라가 정상처럼 보였다

둘 다 "지금 시스템이 어떤 상태인가"를 **화면 어디서든** 볼 수 없어서 생긴 일이다.
SystemMessages 는 *사건*을 다루고, 상태바는 *상태*를 다룬다 — 짝이다.

## 3. 사이드바 — `pages.ts` 를 늘린다, 새 목록을 만들지 않는다

[pages.ts](../frontend/src/config/pages.ts) 가 이미 *"페이지 정의 단일 소스"* 다
(커밋 `181ace1`). 그룹도 거기서 나온다.

```ts
export type PageGroup = '장치' | '수집' | '학습' | '실행' | '시스템'

export type PageEntry = {
  path: string
  label: string
  group?: PageGroup      // 없으면 그룹 밖 (대시보드)
  icon?: string          // 접었을 때 이것만 보인다
  // …기존 필드 그대로
}
```

> ⚠ **사이드바가 자기 목록을 갖게 하면 안 된다.** 그러면 페이지 추가가 다시
> 두 곳 수정이 되고, 이 파일이 존재하는 이유가 사라진다. 그룹 순서는
> **리스트 순서**로 정한다 — 정렬 규칙을 따로 두지 않는다.

**아이콘은 이모지로 시작한다.** 아이콘 라이브러리는 의존성과 번들이 늘고,
접힘 상태가 실제로 쓸 만한지 확인한 뒤에 판단해도 늦지 않다.

## 4. 상태바 — 무엇을 띄우나

| 자리 | 내용 | 없을 때 |
|---|---|---|
| 왼쪽 | **활동 칩** — 추론 · 녹화 · 학습 · 정책서버 중 **도는 것만** | 아무것도 안 뜬다 |
| 왼쪽(칩 안) | 활동별 한 줄 요약: 추론 `19.9fps`, 학습 `6200/20000`, 녹화 `ep 3/10` | 상태만 |
| 오른쪽 | **장치 요약** — 로봇 n · 카메라 n. 이상이 있으면 그 숫자가 경고색 | `0` (회색) |
| 오른쪽 | 디스크 사용률 ([DiskUsageBar](../frontend/src/components/DiskUsageBar.tsx) 재사용) | — |
| 오른쪽 | WS 연결 점 · E-stop `armed` 표시 | — |

> ⚠ **상태바는 판정하지 않는다.** 라벨과 경보 문구는 백엔드가 만든다 —
> [DeviceAlerts](../frontend/src/components/DeviceAlerts.tsx) 가 지키는 규율과 같다.
> *"화면이 문장을 조립하면 한쪽만 고쳐져 어긋난다."* 상태바는 `/api/activity` 의
> `labels` 와 요약 API 가 준 숫자를 **그대로** 그린다.

> ⚠ **상태바에 조작을 넣지 않는다.** 읽기 전용이다. 좁은 줄에 정지 버튼을 놓으면
> 오조작이 나고, 실제로 눌러야 하는 순간(급할 때)에는 큰 버튼이 필요하다.

## 5. 값이 어디서 오나 — **새 폴링을 만들지 않는다**

| 조각 | 출처 | 지금 있나 |
|---|---|---|
| 활동 목록·라벨·차단 | `GET /api/activity` ([useActivity](../frontend/src/hooks/useActivity.ts)) | ☑ 있다 |
| 추론 fps | WS `telemetry` | ☑ 있다 |
| 학습 진행 | WS `train_metrics` | ☑ 있다 |
| 녹화 에피소드 | WS `record_status` | ☑ 있다 |
| E-stop `armed` | `GET /api/estop/status` | ☑ 있다 |
| WS 연결 | `useWebSocket().connected` | ☑ 있다 |
| **로봇·카메라 개수** | `GET /api/devices/summary` | ☐ **새로 만든다** |

### 왜 요약 API 하나가 필요한가

개수를 프론트가 세려면 `/api/robots/can` + `/api/cameras/scan` 을 둘 다 불러야
하는데, **스캔은 싸지 않고** 판정(무엇을 "정상"으로 볼 것인가)이 화면에 생긴다.

그런데 백엔드가 **이미 2초마다 세고 있다.**
[device_watch](../backend/app/services/device_watch.py) 의 `_survey_arms()` /
`_survey_cameras()` 가 `(발행 중, 멈춘 채 남아 있는)` 을 매 주기 계산한다.
**그 결과를 들고 있다가 그대로 내면 된다** — 새 조사가 아니라 이미 있는 조사의
결과를 노출하는 것이다. 장치를 건드리지 않고, 응답은 dict 하나다.

```jsonc
// GET /api/devices/summary
{ "robots":  { "ok": 2, "warn": 0 },
  "cameras": { "ok": 3, "warn": 1 },
  "alerts": 1 }        // 지금 떠 있는 경보 수 — 배지용
```

### 갱신 주기

- **활동**: WS 상태 메시지(`state` / `train_state` / `record_state` / `ps_state`)가
  오면 `refresh()`. **새 WS 타입을 추가하지 않는다** — `useActivity` 가 이미 쓰는
  방식이고, [#12 WS 계약](../refactor/12-ws-message-contract.md) 작업과 안 부딪힌다
- **장치 수**: 5초 폴링. `device_alert` 는 **전이에서만** 오므로 그것만으로는
  개수가 안 맞는다(경보 없는 정상 변화 — 카메라를 새로 연결하는 것 — 을 못 본다)

> 주기 WS 브로드캐스트가 더 깔끔하지만 **WS 계약에 타입을 하나 더 얹는 일**이다.
> #12 가 계약을 정리하는 중이라 그 뒤에 판단한다. 그때 폴링 한 줄을 지우면 된다.

## 6. 건드리지 않는 것

**E-stop 버튼은 자리를 안 옮긴다.** 지금 `fixed bottom-4 right-4` 다. 사이드바가
접히든 펴지든, 어느 페이지든 **같은 자리**여야 한다 — 그게 안전 장치의 요건이다.

**SystemMessageHost 는 상수 하나만 바뀐다.** 지금 `top-16` 은 상단 내비 `h-14`
아래를 뜻한다. 상태바가 `h-12` 가 되면 `top-14`. 오른쪽 정렬(`right-4`)이라
사이드바를 안 덮는다.

**대시보드는 남는다.** 역할이 갈린다 — 상태바는 *"지금 어떤가"*, 대시보드는
*"무엇을 할까"*. 다만 카드 목록이 사이드바와 겹치므로 대시보드는 진입점 나열이
아니라 **최근 작업 + 요약**으로 바꾼다 (4단계).

## 7. 반응형

| 폭 | 사이드바 |
|---|---|
| ≥ 1280px | 펼침 (`w-56`, 라벨) |
| 1024~1280px | 아이콘만 (`w-14`), 호버 시 툴팁 |
| < 1024px | 숨김 + 상태바의 햄버거로 드로어 |

접힘 상태는 `localStorage`. 사용자가 접었으면 넓은 화면에서도 접힌 채로 둔다.

**본문 폭**: 지금 `max-w-7xl mx-auto` 인데, 사이드바가 `w-56` 을 먹으면 본문이
가운데로 몰려 오른쪽이 빈다. 사이드바 도입과 함께 **본문은 남은 폭을 다 쓰고**
페이지별로 필요한 곳만 폭을 제한한다.

## 8. 단계

| # | 작업 | 얻는 것 | 의존 |
|---|---|---|---|
| **1** | `pages.ts` 에 `group`·`icon` + `Layout` 2단 골격. **상태바는 활동 칩만** (이미 있는 값) | **메뉴 한계가 풀린다.** 모델·데이터셋이 내비로 돌아온다 | 없음 |
| 2 | `GET /api/devices/summary` + 장치 칩 · 디스크 · WS 점 | 어느 페이지에서든 장치 상태가 보인다 | 1 |
| 3 | 접힘 · 반응형 · `localStorage` | 좁은 화면 | 1 |
| 4 | 대시보드 정리 (중복 카드 제거 → 최근 작업) | 중복 제거 | 1 |

**1단계만으로 원래 목적(메뉴 추가)이 달성된다.** 나머지는 각각 독립으로 배포
가능하다 — 2~4 를 안 해도 1은 완결이다.

---

## 9. 안 하는 것

- **아이콘 라이브러리 도입** — 이모지로 충분한지 3단계에서 확인한 뒤 판단
- **상태바에 조작 넣기** (정지·시작 버튼) — 읽기 전용을 지킨다 (§4)
- **새 WS 메시지 타입** — #12 뒤로 (§5)
- **페이지 자체의 재설계** — 이번 작업은 **껍데기만** 바꾼다. 페이지 내용은
  한 줄도 안 건드린다. 그래야 되돌리기 쉽고, 회귀가 나면 어디서 났는지 분명하다

## 10. 위험

| 위험 | 막는 법 |
|---|---|
| 상태바가 **두 번째 진실 원천**이 된다 | 판정·문구를 백엔드에서만 받는다 (§4). 화면은 그리기만 |
| 상태바가 폴링을 하나 더 만든다 | 이미 도는 `device_watch` 조사 결과를 읽는다 — 새 조사가 아니다 (§5) |
| 사이드바가 자기 목록을 갖는다 | `pages.ts` 파생만 허용. 테스트로 잠근다 — 프론트 구조 규칙을 백엔드 테스트에서 소스로 검사한 선례가 있다 ([test_page_layout.py](../backend/tests/test_page_layout.py) 는 페이지 그리드를 그렇게 잠갔다). **지금 `pages.ts` 를 보는 테스트는 하나도 없다** — 이번에 처음 생긴다 |
| E-stop 이 사이드바에 가린다 | 자리를 안 옮긴다. `z-50`, 사이드바는 `z-40` |
| 좁은 화면에서 본문이 눌린다 | 1024px 미만은 드로어 (§7) |
