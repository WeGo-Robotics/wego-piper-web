# 시뮬 탑뷰 카메라 **높이(z)만** 조절 (기획)

> [sim-scene-editor.md](sim-scene-editor.md) 의 다음 손잡이. 테이블 위 **사물**은 사람이
> 올릴 수 있게 됐는데, 그걸 **보는 자리**는 아직 소스에 박혀 있다 (사용자 요청 2026-09-28).

## 1. 무엇이 문제인가

탑뷰는 [piper_scene.xml](../sim/piper_sim/assets/piper_scene.xml) 에 박혀 있다:

```xml
<camera name="top" pos="0.25 0 0.6" xyaxes="0 -1 0 1 0 0" fovy="55" />
```

바꾸려면 소스를 고치고 wheel 을 다시 깔고 데몬을 재시작해야 한다. 실제로 v0.5.1 에서
**0.9 → 0.6** 으로 한 번 내렸고, 그 이유는 픽셀 밀도였다(큐브 21 → 33px). 그런데 그 판단은
**작업마다 다르다** — 작은 부품을 집으면 더 내려야 하고, 테이블을 넓게 쓰면 올려야 한다.

### 지금 높이에서는 테이블이 다 안 보인다 (실측)

fovy 55°, 640×480 기준. 큐브 px 는 한 변 0.04m 짜리가 화면에서 차지하는 픽셀이다.

| z (m) | 보이는 y 반폭 | 보이는 x 반폭 | 큐브 px | 테이블 y 덮음 |
|---|---|---|---|---|
| 0.40 | 0.208 | 0.278 | 51 | 46% |
| 0.50 | 0.260 | 0.347 | 40 | 58% |
| **0.60 (지금)** | **0.312** | **0.416** | **33** | **69%** |
| 0.70 | 0.364 | 0.486 | 28 | 81% |
| 0.86 | 0.448 | 0.597 | 23 | 100% |
| 1.00 | 0.521 | 0.694 | 19 | 100% |

⚠ **이게 편집기의 버그이기도 하다.** 배치 캔버스가 곧 탑뷰다([ScenePage](../frontend/src/pages/ScenePage.tsx)
— 탑뷰를 클릭하면 물체가 그 자리로 간다). `ray_to_table` 은 테이블 전체(y ±0.45)로 클램프하는데
화면은 ±0.312 까지만 보여준다 — 그래서 **클릭으로는 y ±0.31 밖에 물체를 놓을 수 없고**, 숫자로
입력해 놓은 물체는 **화면 밖이라 보이지도 않는다.** 높이를 올리면 그대로 풀린다.

## 2. 왜 z 만인가

- **fovy 가 고정이라 z 가 곧 줌이다.** 위 표가 그 한 줄이다: 높이 하나로 "얼마나 담기나 ↔
  얼마나 크게 보이나"가 정해진다. 사람이 실제로 조절하고 싶은 것이 그거다.
- **시선이 계속 수직이라 프레이밍이 안 흔들린다.** 중심(0.25, 0)은 그대로고 배율만 변한다.
  x·y 를 열면 탑뷰가 더는 테이블 중앙을 안 보고, "탑뷰"라는 이름이 거짓이 된다.
- **기록과 비교가 숫자 하나다.** 데이터셋 둘을 "0.6 vs 0.75" 로 견줄 수 있다. 자세 전체를 열면
  6개짜리 비교가 되고, 그러면 아무도 안 본다.
- 회전을 열면 `ray_to_table` 의 테이블 클램프와 편집기 캔버스 가정이 같이 흔들린다 —
  그건 다른 기획이다(§8).

## 3. 핵심 사실 — **이건 가상환경 교체가 아니다** (실측)

```python
m.cam_pos[cid][2] = 0.86;  mujoco.mj_forward(m, d)
#  data.cam_xpos: [0.25 0 0.6] → [0.25 0 0.86]
```

모델 **재컴파일도, `MjData` 재생성도, 렌더러 재생성도 없다.** 필드 하나를 쓰면 다음 스텝에
반영된다. 그래서:

- 슬라이더를 끄는 동안 미리보기가 그대로 따라온다 — 물체를 바꿀 때처럼 세계가 끊기지 않는다.
- `invalidate_model()` 을 **안 부른다** → EGL 컨텍스트·렌더러 스레드 문제와 무관하다
  (가상환경 교체가 짊어진 그 복잡함이 여기엔 없다).
- 컴파일 경로에서도 잡힌다 — `MjSpec.cameras` 로 `['top','front','wrist']` 접근 확인.

⚠ **싸다고 위험이 싼 것은 아니다.** 비용이 0이어도 관측이 바뀌는 것은 같다 — §6.

## 4. 값이 사는 곳 — **가상환경 명세**

```json
{ "version": 1, "id": "…", "name": "…",
  "cameras": { "top": { "z": 0.60 } },
  "objects": [ … ] }
```

- **관측을 바꾸는 값이다.** `meta/piper_scene.json` 사이드카가 "이 에피소드는 어떤 세계에서
  모았나"에 답하는 물건인데, 높이가 빠지면 답이 반쪽이다 — 같은 물체를 33px 로 본 데이터와
  19px 로 본 데이터는 **다른 데이터셋**이고, 프레임만 봐서는 구분이 안 된다.
- **옛 파일은 키가 없으니 기본값 0.60** — 오늘과 완전히 같다. `validate()` 가 채운다.
  ⚠ 기본값 상수와 XML 의 `0.6` 이 **갈리면 안 된다** — 테스트가 둘을 대조한다(§7).
- **왜 카메라 사이드카(`piper_cameras.json`)가 아닌가.** 그쪽은 실기 카메라의 "프레임만
  봐서는 모르는 값"(깊이 인코딩·배경 지움)을 담는 자리다. 시뮬 탑뷰의 높이는 **그 세계의
  성질**이고, `piper_scene.json` 이 이미 그 세계를 통째로 담는다. 둘로 쪼개면 볼 곳이 둘이 된다.
- ⚠ **대가: 남이 만든 가상환경을 불러오면 내 카메라 높이도 따라 바뀐다.** 그게 맞다고 본다 —
  그 세계는 그 높이에서 보기로 만들어진 것이다. 대신 적용할 때 화면이 **바뀐 값을 말한다**.

## 5. 어떻게 만드나

### 5.1 데몬 — 손잡이 하나

`World.set_camera_z(z)` + `SimHub.set_camera_z` + `simd._METHODS`. 하는 일은 세 줄이다:
클램프 → `model.cam_pos[cid][2]` → 적용된 값 반환(클램프됐으면 그 사실이 화면에 보인다).
`compose()` 도 같은 값을 `MjSpec` 에 얹어 **새로 굽는 세계가 같은 높이로 태어나게** 한다.

### 5.2 게이트웨이

`PUT /api/sim/scenes/live/camera {z}` — `live/place` 와 같은 자리·같은 규칙(살아 있는 세계를
바꾸고 **그 값을 편집 중인 명세에도 적는다**). 저장하면 명세와 함께 남는다.

### 5.3 화면 — 탑뷰 바로 아래

배치 캔버스 밑에 슬라이더 + 숫자 입력. **숫자만 보여주면 안 된다** — 0.72m 가 무슨 뜻인지는
아무도 모른다. 같이 적는다:

> `0.72 m · 큐브 ≈ 27px · 테이블 전체 보임`

"테이블 전체 보임" 은 `z ≥ 0.864` 에서 켜진다(§1 표). 이 세 값은 **서버가 준다** — 화면이
fovy 를 베껴 적으면 XML 을 고치는 날 조용히 어긋난다.

### 5.4 범위는 0.35 ~ 1.20 m

- 아래(0.35): 더 내리면 팔이 시야를 크게 가리고, 테이블의 절반도 안 보인다(46% @ 0.40).
- 위(1.20): 테이블은 0.86 에서 이미 다 들어온다. 그보다 위는 물체만 작아진다(16px @ 1.20) —
  그래도 여유를 두는 이유는 **넓은 작업대를 쓰는 사람**이 있을 수 있어서다.
- 클램프는 **데몬이** 한다. 화면이 막는 것은 편의고, 정본은 세계를 든 쪽이다.

## 6. 언제 못 바꾸나

⚠ **수집·추론·에피소드 루프가 도는 중에는 거절한다.** 에피소드 한가운데 관측이 바뀌면 그
에피소드는 절반이 A 세계, 절반이 B 세계라 **못 쓴다** — 관측이 바뀐 것을 라벨은 모른다.
추론은 한 겹 더 나쁘다: 정책이 **학습한 적 없는 화각**을 받고 그대로 팔을 움직인다.

⚠ **조종(TELEOP) 중에는 막지 않는다** — 가상환경 교체(`Activity.SCENE_SWAP`)와 **다른 점이
여기다.** 물체가 사라지고 생기는 것은 사람이 팔을 모는 중에 위험하지만, 카메라가 올라가는
것은 팔에 아무 일도 안 한다. 막을 이유가 없는 것을 같이 막으면 "왜 안 되는지" 를 사람이
납득 못 하고, 그런 규칙은 결국 무시된다.

⚠ **조명 감시가 이걸 "조명 급변" 으로 읽는다.** 카메라가 움직이면 밝기·색 통계가 튄다 —
맞는 관측이지만 틀린 해석이고, 쓸모없는 경보는 옆의 진짜 경보를 묻는다(v0.5.6 에서 같은
이유로 카메라별 스위치를 달았다). 높이를 바꾸면 **그 카메라의 판정 기준을 버린다** —
`light_watch._judges["sim:top"]` 를 지우는 것으로 끝이고, 카메라가 끊겼다 붙을 때 이미
같은 일을 한다("재연결하면 기준선을 새로 잡는다").

## 7. 테스트

| 무엇 | 어떻게 |
|---|---|
| 높이가 실제로 먹는다 | `set_camera_z(0.8)` 뒤 `data.cam_xpos[top][2] == 0.8` |
| 재컴파일이 아니다 | 호출 전후 `model` 객체가 **같은 것**이고 `invalidate_model` 이 안 불린다 |
| 굽는 세계도 같은 높이 | 명세에 0.75 를 넣고 `build()` → `model.cam_pos[top][2] == 0.75` |
| 기본값이 XML 과 같다 | 상수 == `piper_scene.xml` 의 `pos` 셋째 값 (**파싱해서** 대조 — 손으로 적으면 갈린다) |
| 옛 명세가 안 바뀐다 | `cameras` 없는 JSON → `validate` 가 0.60, 오늘과 같은 세계 |
| 사이드카에 남는다 | 녹화한 데이터셋의 `meta/piper_scene.json` 에 높이가 있다 |
| 클램프 | 0.1·9.9 → 범위 안으로, 그 사실이 응답에 |
| 수집 중 거절 | 녹화 상태에서 PUT → 409, 사유가 문구에 |
| 조종 중에는 된다 | 릴레이가 도는 상태에서 PUT → 200 (§6 의 의도적인 차이를 잠근다) |
| 조명 기준선을 버린다 | 높이 변경 뒤 `_judges` 에 `sim:top` 이 없다 |

## 8. 하지 않는 것

- **x·y·회전·fovy.** §2 의 이유. 특히 fovy 는 z 와 **같은 것을 두 손잡이로** 만드는 일이라
  더 나쁘다 — 사람이 둘을 조합해 같은 화각을 만드는 경우의 수가 생기고, 기록이 비교 불가가 된다.
- **손목·정면 카메라.** 손목은 링크에 붙어 있어 z 가 아예 다른 뜻이다(팔 기준 오프셋).
  정면은 수직이 아니라 높이만 바꾸면 겨누는 곳이 같이 움직인다 — 둘 다 별도 기획이다.
- **학습된 정책과 높이가 다를 때 자동 경고.** 사이드카에 값이 남으므로 나중에 할 수 있다
  ("이 체크포인트는 0.60 에서 배웠는데 지금 0.85 입니다"). 이번에는 **기록까지만** 한다 —
  경고를 하려면 체크포인트에서 데이터셋을 거슬러 찾아야 하고, 그 길은 아직 없다.

## 9. 순서

1. `World.set_camera_z` + `compose()` 반영 + 기본값 상수. 테스트는 **재컴파일이 아님**과
   **XML 기본값 일치**를 잠근다.
2. 명세 스키마(`cameras.top.z`)와 `validate` 기본값, 사이드카.
3. 게이트웨이 PUT + 수집·추론·루프 거절(조종은 허용).
4. 화면 슬라이더 — 숫자 옆에 **큐브 px·테이블 덮음**을 서버가 준 값으로.
5. 조명 판정 기준선 버리기.

⚠ 2 를 1 과 같은 커밋에 넣지 않는다. 1 은 세계를 만지는 일이고 2 는 파일 포맷을 바꾸는
일이라, 되돌릴 때 같이 되돌아가면 곤란하다.
