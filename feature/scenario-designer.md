# 시나리오 설계기 — 템플릿으로 수집 계획을 짜고, 수집 때 다음 배치를 보여 준다 (기획)

> **◐ 1·2단계 ☑ (2026-10-29)** — 1단계: 템플릿 틀 + 분류 + 설계 화면(수집 → 시나리오 탭) + 작업판 PDF.
> 2단계: 녹화 연결(시도↔에피소드 바인딩·task 자동·안내·음성·안내 창) + 실패 표시와 미결 알림 전부 + 학습 제외.
> 구현하며 바뀐 것은 §4-2·§7-6·§9-3·§10-4·§11-1 에 적었다. 3단계(대조)부터 남았다. 결정은 §17.

## 0. 요지

데이터셋을 **찍기 전에** 설계한다. 시나리오 종류(분류·조립…)마다 **템플릿**이 있고, 템플릿을
고른 뒤 작업판 격자·물체·규칙·실패 비율을 채우면 설계기가 칸·종류·순서가 고르게 퍼진
**시도(trial) 목록**을 만든다. 수집 중에는 지금 시도와 다음 배치를 크게 보여 주고, 에피소드
경계마다 task 문구를 알아서 바꾸고, 어느 에피소드가 어느 시도였는지를 데이터셋 옆에 남긴다.

| 덩어리 | 하는 일 | 산출물 |
|---|---|---|
| **템플릿** | 시나리오 종류별 고유 필드·에피소드 단위·생성기·변형 | `services/scenario/templates/<종류>.yaml` + 생성기 |
| **설계** | 템플릿 + 값 → 균형 잡힌 시도 목록 | 저장한 설정(프리셋) + 계획 |
| **인쇄** | 작업판을 A4 여러 장으로 — 기본은 **사람 눈에만 보이는 흐린 판** | PDF |
| **안내** | 수집 화면에 지금/다음 배치·음성·카메라 겹쳐보기 | — |
| **대조** | 계획 vs 실제, 실패 라벨과 **미결 알림** | 데이터셋 사이드카 |

⚠ **계획은 데이터셋에 붙는다.** 저장한 설정은 프리셋 스토어에, 생성된 계획과 진행은
`<데이터셋>/meta/piper_scenario.json` 사이드카에 둔다. 새 저장소를 만들지 않는다 —
[parameter-presets](parameter-presets.md) 가 "일곱 번째 스토어를 만들지 말라" 고 한 그 규칙이다.
같은 데이터셋에 이어 녹화하면 계획도 이어진다.

## 1. 왜 — 지금은 배치를 사람 머리로 한다

- 수집 화면에 있는 것은 task 한 줄과 에피소드 카운터뿐이다. 어디에 무엇을 놓았는지는
  **어디에도 안 남는다.** 나중에 "이 에피소드는 B3 에 빨강이었나" 를 물을 수 없다.
- [POS분석 커버리지](episode-analyzer.md)(§6 A1 ☑)가 **사후에** 덩어리를 찾는다. 실측(2026-10-21)
  에서 `min_cube` 가 큐브 자리 3곳, `singlearm_apple_4point` 가 4곳에 몰려 있었다. 설계기는
  그걸 **사전에** 막는 쪽이다.
- 알약 조제 로봇의 교훈이 그대로 설계 규칙이 된다([episode-analyzer §6](episode-analyzer.md)):
  무작위라 믿은 시연 60개가 세 덩어리였고, 한 장면에 정답이 하나면 모델이 목표 입력을 무시했고,
  두 장면에만 찍힌 볼펜이 목표 색과 겹쳐 가짜 단서가 됐다.

|---|---|

### 3-1. 로봇 쪽과 상자 자리 (2026-10-29 추가)

로봇이 판의 어느 변에 있는지는 **판마다 고른다**(위·아래·왼쪽·오른쪽). 처음엔 그림의 위쪽을 로봇
쪽으로 고정했지만, 실제로는 위쪽에 상자가 오는 배치가 있다.

- **칸 이름은 그림 기준이다** — `A1` 은 로봇이 어디 있든 그림(=인쇄물)의 왼쪽 위다. 화면과 종이가 같은
  그림을 쓰므로 "B3" 은 늘 같은 칸이다. 로봇 쪽을 따라가는 것은 "가까운 순" 규칙의 거리, 인쇄·화면의
  로봇 표시뿐이다.
- "가까운 순" 에서 거리가 같은 두 칸은 로봇을 지나는 축에 대해 대칭이다. 로봇이 위·아래면 **왼쪽부터**,
  왼쪽·오른쪽이면 **위쪽부터** (`Board.tie_key`).
- **상자는 나머지 세 변에, 격자 안이든 바깥이든.** 작업판 편집기에서 [격자 안 | 격자 바깥]을 고르고
  [+ 왼쪽 변] 같은 버튼을 누른다.
  - **안** — 그 변의 가운데 칸(변 길이가 짝수면 2칸, 홀수면 3칸)을 상자 구역으로, 그 줄의 나머지 칸을
    금지로 칠한다. 칸이라 손으로 고쳐 칠해도 된다.
  - **바깥** — 그 변 바깥 가운데에 직사각형을 붙인다(`zone.outside`: 변 · 몇 번째 칸부터 몇 번째까지 ·
    깊이 · 띄움 mm, 기본 깊이 칸 1.5개 · 띄움 10mm). 변을 따라서는 칸에 맞춘다 — 상자 자리를 칸 이름으로
    말할 수 있고(“위쪽 B~D”), 화면에서 클릭 대신 고르기만 하면 된다. 물체 칸은 줄지 않는다.
    인쇄는 판(띠·태그)을 바깥 구역까지 넓혀 상자 자리도 종이에 찍는다(`Board.frame`).
  - 생성기에게 구역은 담을 곳의 이름일 뿐이라 안·바깥을 구분하지 않는다. 섞어 써도 된다.
- 분류 기본 배치: 7×5, 로봇 아래, 상자 왼쪽(A2–A4)·위쪽(C1–E1)·오른쪽(G2–G4), 물체 자리 B2–F5 20칸.
- 예전에 저장한 설정(로봇 쪽이 없음)은 위로 읽는다.

## 4. 템플릿 — 시나리오 종류마다 하나

### 4-1. 공통과 템플릿의 경계

| 공통 (모든 템플릿이 같이 쓴다) | 템플릿마다 다른 것 |
|---|---|
| 작업판 편집기 · 물체 목록 · 구역 | 고유 필드 (분류의 규칙, 조립의 단계·선행 관계) |
| 변형 비율 틀 · 성가신 변수 · 블록 | 에피소드 단위 선택지와 기본값 |
| 공통 균형기 (§7) | **생성기** — 라운드를 어떻게 구성하나 |
| 인쇄 · 안내 창 · 음성 · 사이드카 · 미결 알림 | task 문구 틀 · 고유 변형 · 안내 문장 |

### 4-2. 파일 둘이 템플릿 하나

`policies/<type>.yaml` 과 같은 관례 — **선언은 YAML, 생성은 Python.**
([episode-orchestrator](episode-orchestrator.md) 가 남긴 원칙 "스텝은 Python, 시퀀스는 데이터" 와 같다.)

자리는 **백엔드 안**이다 — [backend/app/services/scenario/templates/sort.yaml](../backend/app/services/scenario/templates/sort.yaml)
+ [sort.py](../backend/app/services/scenario/sort.py). 처음엔 `policies/` 옆 저장소 루트(`scenarios/`)로 잡았지만, 템플릿은
wrapper 가 읽지 않아(정책 스펙과 다르다) 루트에 두면 Dockerfile `COPY`·릴리스 판정만 한 줄씩 늘 뿐이다.

```yaml
# backend/app/services/scenario/templates/sort.yaml (요지)
spec_version: 1
type: sort
generator: sort                     # app/services/scenario/sort.py
episode_units: [one, all]           # 첫 번째가 기본
fields:                             # 값의 모양만 — 기본값·선택지·범위
  round_sizes: { kind: text, default: "3,5" }
  round_style: { kind: select, options: [chain, restore], default: chain }
  target_by: { kind: select, options: [instruction, rule], default: instruction }
  rules: { kind: data, default: [] }          # 구조가 있는 값 — 생성기가 검증
variants:
  empty_target: { default: 0.05, requires: { episode_unit: one, target_by: instruction } }
  hard_layout: { default: 0.10, per: round }
```

⚠ **YAML 에 화면 문구(label·description)를 두지 않는다.** YAML 문자열은 번역 추출(`tools/i18n.py`)
대상이 아니라서, 두면 영어 화면에 한국어가 섞인다. 문구는 템플릿의 프론트 컴포넌트가 `t()` 로 갖는다
([SortFields.tsx](../frontend/src/components/scenario/SortFields.tsx)). 그래서 "파일 둘" 은 실제로는
**백엔드 둘 + 화면 컴포넌트 하나**다 — 화면 없이 YAML 만 있는 템플릿은 목록에 뜨되 고를 수 없다.

- 필드로 안 되는 편집기(분류 규칙 표, 조립 단계·선행 관계)도 같은 컴포넌트에 있다. YAML 이 JSX 를
  정하지 않는다 — [SpecFields.tsx](../frontend/src/components/SpecFields.tsx) 주석이 그은 선 그대로다.
- 테스트가 모든 템플릿을 기본값으로 생성해 균형 조건(§16 인수 기준)을 검사한다
  ([test_scenario_plan.py](../backend/tests/test_scenario_plan.py)). 템플릿을 추가하면 거기 `FIXTURES` 에
  최소 입력을 넣어야 한다 — 안 넣으면 테스트가 깨진다.

### 4-3. 템플릿 목록

| 템플릿 | 한 시도 (기본 / 선택) | 균형 축 | 고유 변형 | 언제 |
|---|---|---|---|---|
| **분류** §5 | 하나 담기 / 여러 개 연속 분류 | 종류 × 칸, 집는 순서, 물체 수 | 빈손, 잘못 담긴 것 바로잡기 | 1단계 |
| **조립** §6 | 단계 하나 / 전체 조립 | 부품 × 공급 칸 × 방위, 단계 순서 | 뒤집혀 놓임, 덜 끼워짐에서 시작, 부품 없음 | 5단계 |
| 옮기기 | 물체 하나: 시작 칸 → 목표 칸 | 시작 × 목표 쌍, 이동 거리 | — | 분류 뒤 거의 공짜 (물체 1개·목표가 칸인 분류) |
| 쌓기 | 블록 하나 올리기 / 탑 전체 | 블록 순서, 탑 자리 | 무너진 탑 다시 쌓기 | 후보 |
| 양팔 건네기 | 한 번 건네기 | 건네는 자리·높이 | 놓친 것 다시 받기 | 후보 — [bimanual](bimanual.md) 뒤 |

### 4-4. 저장한 설정

템플릿에 값을 채워 이름을 붙이면 프리셋(`domain: scenario`, `scope: shared`)이 된다 —
`values` 에 `template: sort` 와 채운 값. 기기와 무관한 설계라 로봇끼리 공유하는 쪽이다.
"사과 3종 하나씩", "사과 3종 5개 연속" 처럼 같은 템플릿에서 여러 개를 만든다.

**마지막 설계는 브라우저가 기억한다** — 수집 화면의 폼(`piper_record_settings`)과 같은 자리
(`localStorage` 의 `piper_scenario_design`·`piper_scenario_print`). 새로고침해도 하던 설계·인쇄 설정이 그대로
남는다. 이름 붙여 남기거나 다른 기기와 나눌 것은 프리셋이다. 예전 모양으로 저장된 값은 템플릿 기본값 위에
얹어 읽고(프리셋 불러오기와 같은 `mergeDesign`), [처음 값으로]는 두 번 눌러야 지운다.

## 5. 분류 템플릿

### 5-1. 에피소드 단위 — 하나씩이 기본, 여러 개 연속도 된다

| | **하나씩 (기본)** | 여러 개 연속 분류 |
|---|---|---|
| 모양 | 5개 라운드 → 에피소드 5개. 하나를 담으면 **그 자체가 다음 배치** — 사이에 리셋이 없다 | 라운드 전체가 긴 에피소드 하나 |
| 장점 | 짧고 깨끗하다, 남은 사과가 자연스러운 방해물, 리셋은 라운드당 한 번 | 실제 운용 모양 그대로 |
| task 예 | "빨간 사과를 왼쪽 상자에 넣어" | "사과를 색깔별로 상자에 나눠 담아" |
| 맞는 정책 | 지시문을 보는 정책. ACT 는 `순서 규칙` 일 때만 | ACT·ACT-S (단계 헤드와 상성) |

### 5-2. 목표 고르기 — 정책이 지시문을 안 보면 막는다

`target_by` 가 둘이다: `지시문`(어느 사과든 지시로 정한다) / `순서 규칙`(장면만으로 정해진다 —
빨강 → 노랑 → 작은 것, 같은 종류는 가까운 순).

⚠ **ACT 는 task 문구를 안 본다.** 같은 장면에서 지시문만 바꿔 다른 사과를 집는 시연을 주면
고를 근거가 장면뿐인데 정답이 여럿인 모순 데이터가 된다. 설계 화면에서 **쓸 정책**을 고르게
하고, 그 정책 스펙의 `capabilities.language` 가 `false` 면 `지시문` 을 막는다. 여러 개 연속
분류는 늘 `순서 규칙` 이다.

⚠ **순서 규칙은 시연자가 매번 지켜야 한다.** 그날 기분대로 순서를 바꾸면 같은 모순이 생긴다.
안내 화면이 매 시도의 "다음에 집을 것" 을 규칙으로 계산해 보여 주는 이유다.

### 5-3. 물체 구성 — 사용자가 고른다

실물 개수(빨강 3, 노랑 3, 작은 사과 2 …)를 적고, 종류 총량을 **어떻게 맞출지**를 고른다.

| 방식 | 라운드 구성 | 결과 |
|---|---|---|
| **종류 총량 같게** (기본) | 라운드마다 구성을 바꿔 맞춘다 — 실물 개수 안에서 | 종류별 목표 수가 같다. 실물이 모자라 못 맞추면 생성 전에 말한다 |
| 실물 비율대로 | 가진 개수 비율로 뽑는다 | 자연스럽지만 적은 종류는 덜 배운다 |
| 고정 구성 | 사람이 "빨2 노2 작1" 을 직접 | 매 라운드 같은 구성 |

어느 쪽이든 생성 전에 종류별 총량을 숫자로 보여 준다.

### 5-4. 분류 고유 변형

| 변형 | 하는 것 |
|---|---|
| 빈손 | 지시한 종류가 판에 없다 → 원위치에서 기다림 (지시문 모드만). 알약 정지 시연 32개 |
| 잘못 담긴 것 바로잡기 | 빨간 사과가 오른쪽 상자에 들어가 있는 상태에서 시작 → 꺼내 왼쪽으로 |

## 6. 조립 템플릿

- **작업판**: 지그(조립 자리) 구역 하나 + 부품 공급 칸. 격자는 공급 칸에 쓴다.
- **고유 필드**: 단계 목록 `{부품, 슬롯, 선행 단계}` · 방위 구간 수(기본 4) · 부품 뒤집힘 비율.
- **한 시도**: 단계 하나(기본) / 전체 조립. 단계 하나면 분류와 같은 **연쇄** 모양이다 — 앞
  단계의 결과가 다음 시도의 시작 상태가 된다.
- **균형**: 부품 × 공급 칸 × 방위 구간. 선행 관계가 허락하는 범위에서 단계 순서도 섞는다
  (순서가 하나뿐인 조립이면 고정).
- **고유 변형**: 뒤집혀 놓인 부품(다시 잡기) · 덜 끼워진 상태에서 시작(다시 누르기) · 부품 없음(정지).
- **리셋이 비싸다** — 분해가 곧 리셋이다. 예상 시간에 라운드당 분해 시간을 따로 넣는다.
- 인쇄: 공급 칸 중심에 방위 눈금(흐린 모드에서도 사람 눈에 보이게, §10-2).
- 볼트 데이터셋(`bolt_two1`, `two_arm_bolt_2`)이 이 템플릿의 첫 실사용 후보다.

## 7. 고르게 — 공통 균형기

템플릿 생성기는 라운드의 **모양**을 만들고, 칸·종류·순서를 고르는 일은 공통 균형기에 맡긴다.
템플릿이 균형 축을 선언하면 균형기가 채운다. 전체는 백엔드 **순수 함수**
`generate(template, values, seed) -> plan` — 같은 입력이면 같은 계획이다(재현성, 테스트 가능).

### 7-1. 균형기가 하는 일

| # | 축 | 방법 |
|---|---|---|
| 1 | **목표 칸 × 종류** | `count[종류][칸]` 이 가장 적은 칸부터, 동률은 시드 난수. 하나씩 모드에서는 라운드의 모든 물체가 한 번씩 목표가 되므로 **놓는 칸 균형 = 목표 칸 균형** |
| 2 | **종류 총량** | §5-3 에서 고른 방식대로 |
| 3 | **방해물** | 남은 물체 칸도 같은 방식으로. 최소 간격(인접 칸 금지 옵션) |
| 4 | **집는 순서** | 지시문 모드에서 "라운드 첫 목표가 늘 빨강" 이 안 되게 `count[순번][종류]` 균형 |
| 5 | **장면 × 목표** | 지시문 모드 옵션: 같은 배치에서 목표만 바꿔 k번 (알약 교훈). 이때는 담은 것을 되돌려 놓는다 |
| 6 | **물체 수** | 3개·5개 라운드를 비율로 — 방해물 수 자체가 다양해진다 |
| 7 | **방위** | 방향이 있는 물체만 구간 균형 (사과는 무관, 조립 부품은 필수) |
| 8 | **성가신 변수** | 조명·바닥천·**시연자**·날짜를 축으로 받으면 목표 종류와 **교차 균형**. 교차표를 보여 준다 (볼펜 사건, 시연자 버릇 A2) |

### 7-2. 순서도 섞는다

칸·종류별로 몰아 찍으면 시간에 따라 바뀌는 것(조명·카메라 틀어짐·시연자 피로)이 특정 칸·종류와
겹친다. 블록 안에서 섞는다.

### 7-3. 모자라면 말한다

칸 20 × 종류 3 = 조합 60 인데 계획이 40회면 모든 조합을 못 채운다. 생성 전에 숫자로:
"칸을 12개로 줄이거나(칸 크기 ↑) 회수를 120으로 — 조합당 2회". 칸 크기 하한은
`물체 지름 + 그리퍼 여유` 로 권한다(사과 75mm → 칸 80~90mm). 권고보다 작아도 생성기가 크기대로 띄워 놓는다(§7-7).

### 7-4. 블록 — 중간에 그만둬도 고르다

계획 전체만 균형이면 80% 찍고 멈춘 데이터셋은 치우친다. **블록(기본 20시도)마다 따로 균형**을
맞춘다. 화면은 "블록 3/6" 으로 보여 준다.

### 7-5. 생성 직후 보여 줄 것

종류별 목표 칸 히트맵 · 방해물 히트맵 · 종류별 총량 · 변형 비율 · 교차표 · 예상 시간
(`시도 × 에피소드 시간 + 라운드 × 리셋 시간`) · 세션 분할 제안.

### 7-6. 구현에서 배운 것 — 탐욕만으로는 편차 1 이 안 된다

칸당 평균이 정수로 떨어지면(빨강 40회 ÷ 20칸 = 2, 연속 분류 160회 ÷ 20칸 = 8) 한 칸만 3 이 돼도 다른 칸이 1 이
되어 편차가 2 다. 탐욕 배치는 그 마지막 하나를 못 맞췄다(30개 시드 중 다수). 그래서 생성은 세 단계다:

1. **배치** — 블록마다 라운드의 모양을 정하고 칸을 고른다. 순서를 바꿔 여러 번(16회) 놓아 보고 점수 합이 가장 작은 것.
2. **수선** — 모든 블록이 끝난 뒤, 넘치는 칸의 목표 하나를 모자란 칸으로 옮긴다. 옮길 물체는 **어느 블록에서든**
   고른다 — 마지막 블록만 보면 넘치는 칸이 하필 그 블록에서는 덜 쓴 칸이라 블록 균형을 깨는 일이 흔했다. 블록
   편차가 1 을 넘는 이동과 붙여 놓은 짝은 건드리지 않는다.
3. **조립** — 블록마다 에피소드를 만들고(규칙 순서는 칸에 달렸으므로 수선 뒤에), 변형을 넣고, 섞는다.

같은 배치 반복(restore)은 목표를 **먼저** 고른다 — 목표 종류를 균형 있게 정한 뒤 목표 칸 횟수로 놓고, 방해물은
그다음에 놓인 횟수로 놓는다. 다 놓고 나서 목표를 고르면 편차가 3 까지 벌어졌다. 빈손 시도를 넣을 자리(판에 없는
종류가 있는 배치)가 없으면 그 몫을 1단계에서 정상 라운드로 채운다 — 3단계에서 알면 이미 수선한 뒤라 다시 깨진다.

실측(분류, 120시도, 시드 30개): 하나씩·연속 분류·규칙(가까운 순·종류 순)·같은 배치 반복 모두 전체·블록 편차 1 이하.

### 7-7. 물체 크기 — 칸 이름이 아니라 판 위에서 들어가야 한다 (2026-10-29 추가)

처음 생성기는 칸 이름만 봤다 — 물체 목록의 크기는 화면에 원을 그릴 때만 쓰였고, 간격은 칸 수(최소 간격)뿐이었다.
칸 60mm 에 사과 75mm 면 이웃 칸 둘이 "비어" 보여도 판 위에서는 겹친다(그 판에서 라운드 30개 중 29개에 겹치는 짝).
이제 물체는 칸 가운데의 **지름 = 크기(가장 긴 변)** 인 원이고, 셋을 지킨다:

| 무엇 | 규칙 |
|---|---|
| 물체끼리 | 중심 거리 ≥ (두 크기의 합)/2 + **물체 사이 틈**(`clearance_mm`, 기본 0 = 겹치지만 않게). 최소 간격(칸 수)은 그대로 함께 |
| 상자·금지 칸 | 원이 구역 칸·금지 칸·바깥 구역에 걸치면 그 칸에 안 놓는다(닿는 것은 된다). 판 바깥 가장자리는 넘어가도 된다 — 종이 밖도 책상이다 |
| 어려운 배치의 짝 | 틈·최소 간격은 풀고 **겹치지만 않게** 가장 가까운 칸에. 바로 옆(체비셰프 1)이 안 되면 그다음 고리 |

종류마다 못 쓰는 칸이 생길 수 있다(큰 사과는 상자 바로 옆 칸에 못 간다). 균형은 **그 종류가 쓸 수 있는 칸 안에서**
맞추고 요약의 편차도 거기서 잰다 — 못 가는 칸의 0 은 치우침이 아니다. 요약 경고 둘: 칸보다 큰 물체
(`object_over_cell` — 이웃 칸까지 차지한다), 크기 때문에 못 쓰는 칸(`size_keeps_off`). 수선(§7-6 2단계)과
perturb 로 옮길 칸도 같은 검사를 거친다. 어디에도 못 놓는 물체는 생성 전에 이름을 대고 거절한다.

## 8. 실패 시나리오

계획에 넣는 실패(**변형**)와 우연히 난 실패를 나눈다.

### 8-1. 계획에 넣는 변형 (공통)

| 변형 | 하는 것 | 왜 | 기본 비율 |
|---|---|---|---|
| 정상 | — | — | 나머지 |
| **회복: 빗나간 파지** | 그리퍼가 이미 2~3cm 빗나간 자리에서 시작 → 다시 집기 | 실기에서 놓치면 다시 시도할 줄 알아야 한다 | 10% |
| 회복: 떨어뜨림 | 떨어진 자리에 물체를 두고 시작 → 다시 집기 | 같은 이유 | 5% |
| 교란 | 접근 중 사람이 물체를 **지정 칸으로** 옮긴다 | 닫힌 고리 재조준. 옮길 칸도 계획이 정한다 | 5% |
| 어려운 배치 | 붙여 놓기 · 구역 바로 옆 · 도달 경계 칸 | 쉬운 칸만 찍으면 경계에서 무너진다 | 층으로 지정 |

템플릿 고유 변형은 §5-4 · §6.

⚠ **회복 시연은 "빗나간 뒤부터" 찍는다.** 일부러 빗나가는 앞부분까지 녹화하면 정책은
빗나가는 동작도 배운다. LeRobot 에는 구간 마스킹이 없으므로, 리셋 시간에 리더 팔을 빗나간
자세로 가져다 둔 상태에서 에피소드를 시작한다. 안내 화면이 "리셋 중: 그리퍼를 사과 오른쪽
3cm 위에 두고 기다리세요" 처럼 시작 자세를 말한다.

### 8-2. 우연히 난 실패 — 라벨 붙여 남기고, 나중에 정한다

| 언제 알았나 | 처리 |
|---|---|
| 녹화 중·리셋 중, 다시 찍고 싶다 | ← 재녹화. 계획 포인터는 **그 시도에 머문다** |
| 녹화 중·리셋 중, 남기고 싶다 | **[실패로 표시]** → 저장된다. 그 시도는 블록 끝에 다시 들어간다 |
| 저장된 뒤 | 에피소드 화면에서 같은 표시 |
| 배치가 물리적으로 안 됨 (도달 불가 등) | **[이 배치 미루기]** — 리셋 중에만. 블록 끝으로 |

⚠ "미루기" 는 → 버튼과 다르다. →(`/skip`)는 **지금 에피소드를 저장**한다(recording.py
`skip_episode` 의 경고). 계획 쪽 버튼에 "건너뛰기" 라는 말을 쓰지 않는다.

실패 표시는 지우지 않는다. 사이드카에 `outcome: failed`, **`decision: pending`(미결)** 으로 남고,
학습에 넣을지(`include`) 뺄지(`exclude`)는 나중에 정한다.

### 8-3. 미결은 반드시 알린다

미결이 있는데 아무도 안 정한 채 학습되면 표시한 의미가 없다. 그래서 **미결이 영향을 주는 자리마다**
알리고, 학습 시작에서는 지나칠 수 없게 한다.

| 자리 | 모양 |
|---|---|
| 녹화 정지 직후 ☑ | 요약 카드: "실패로 표시한 에피소드 3개 — 학습에 넣을지 아직 안 정했습니다" + [지금 정하기] (→ 에피소드 화면, 미결만) |
| 데이터셋 목록 ☑ | 배지 `미결 3` (목록·학습/에피소드의 데이터셋 고르기 창 모두 — 같은 `DatasetBrowser`) |
| 에피소드 화면 ☑ | 필터 "미결 실패만", 목록에 미결/포함/제외 배지, 고른 에피소드 [학습에 포함] [학습에서 제외], 미결 전부 포함·제외 |
| **학습 시작** ☑ | 고른 데이터셋에 미결이 있으면 시작 버튼 자리에 선택 패널: **[제외하고 계속] [포함하고 계속] [에피소드 보기]** (계속 = 설정 확인 창으로). 고른 것이 사이드카에 결정으로 남는다 — 다음 학습에서 다시 묻지 않는다. 화면을 거치지 않은 시작은 서버가 409 로 거절한다(로컬·임대 같은 조립기 `train_cli_params`) |
| 허브 업로드 ☑ | 확인 창에 경고만. 사이드카가 같이 올라가므로 받는 쪽도 미결을 본다 |
| split·merge | 화면에 이 기능이 없다. [edit_dataset.py](../wrapper/edit_dataset.py) 가 이 둘에서는 사이드카를 **안 가져간다**는 경고를 로그에 남긴다 |
| 사본 만들기(굽기·`_delta`) ☑ | 따로 할 것이 없었다 — 둘 다 `meta/` 를 통째로 복사하고 에피소드 번호를 안 바꾼다 |
| 에피소드 지우기 ☑ | 로그 번호를 당긴다 — 지운 에피소드의 줄은 버린다(그 시도는 이어 찍을 때 다시 나온다). [piper_phase/sidecar.py](../phase/piper_phase/sidecar.py) `remap_after_delete` |

- 선택 패널은 React 모달이다 — `window.confirm` 은 heartbeat 를 막는다(추론 중 confirm 금지와 같은 이유).
- **제외는 지우지 않는다.** 학습 명령에 `--dataset.episodes=[포함 목록]` 을 넘긴다 — 결정을 나중에
  뒤집을 수 있다. 지금 학습 경로가 이 인자를 안 넘기므로 [cli_mapping.py](../backend/app/core/cli_mapping.py)
  에 한 줄이 필요하다.
- ⚠ 정규화 통계(`meta/stats.json`)는 전체 에피소드로 계산된 것을 그대로 쓴다. 실패 몇 개로 크게
  흔들리지는 않지만, 절반 가까이 빼면 통계를 다시 계산하라고 알린다.

계획된 변형(회복·교란)은 `outcome: recovered` 등으로 남고 미결이 아니다 — 그건 처음부터 의도한 데이터다.

## 9. 수집 도우미 — 화면

### 9-1. 자리

- 수집 페이지 제목 옆 탭 **[수집 | 시나리오]** (탭은 h1 바로 옆). 시나리오 탭은 **설계**하는 곳이다.
- 녹화는 수집 탭의 **[시나리오 계획 따르기]** 로 시작한다 — 시나리오 탭의 마지막 설계(브라우저에
  기억된 것)를 게이트웨이가 다시 계획으로 만든다. task·에피소드 수는 계획이 정한다.
- **안내** ☑ — 녹화 중 수집 탭의 미리보기 아래 (구현: 시나리오 탭이 아니라 녹화 화면 옆이다 —
  시연자는 미리보기와 ←/→ 를 보고 있으므로). [안내 창 열기 ↗]로 같은 것을 새 창(`/scenario-guide`)에
  크게. 테이블 옆 모니터·태블릿용이고, E-stop heartbeat 를 안 보낸다 — 이 창이 닫혀도 녹화에는
  영향이 없다(녹화를 지키는 것은 수집 화면이다).

### 9-2. 보여 줄 것

```
┌ 지금 ── 시도 37/120 · 블록 2/6 ───────────┐ ┌ 다음 (리셋 중엔 이쪽이 크게) ────────┐
│  작업판 그림: 칸 위에 색 원, 목표는 굵게  │ │  옮길 것만 강조:                    │
│  → 화살표: 목표 → 왼쪽 상자               │ │   · 노란 사과 B3 → D1               │
│  task: 빨간 사과를 왼쪽 상자에 넣어       │ │   · 빨간 사과 새로 C2               │
│  변형: 정상                               │ │  (연쇄 중이면 "그대로 — 놓을 것 없음")│
└───────────────────────────────────────────┘ └──────────────────────────────────────┘
 [실패로 표시]  [다음 배치 미루기]                         (음성은 수집 화면의 "음성 안내" 를 따른다)
```

- **이전 배치와의 차이**만 강조한다. 하나씩 모드에서는 라운드 사이 외에는 놓을 것이 없다.
- **음성 안내** — 리셋이 시작되면 브라우저 `speechSynthesis` 로 "다음: 빨간 사과 B3, 노란 사과
  D1". 시연자는 리더 팔을 잡고 있어 화면을 볼 손이 없다. 문장은 `t()` 로 — 화면 언어를 따른다.
- **카메라 겹쳐보기**(§16 단계 4) — 탑 카메라 프리뷰 위에 격자와 놓을 자리 유령 원. 흐린 판은
  카메라 영상에 안 보이므로 이 겹쳐보기가 화면 쪽 짝이다.
- **배치 확인**(선택) — 검출 + 색·크기 등급으로 계획 칸과 대조, 칸마다 ✓/✗. **자동 진행은
  하지 않는다** — 시작은 늘 사람이 한다.

### 9-3. task 와 시도를 한 몸으로 넘긴다

LeRobot 녹화 순서는 `에피소드 → 리셋 → (재녹화면 버퍼 비움 : 저장)` 이다(실측, `lerobot_record.record`).
재녹화 여부는 리셋이 **끝나야** 정해진다. 그래서 게이트웨이가 "지금이 몇 번째 시도" 를 추측하면
←/→ 와 경합한다.

**구현 (기획의 "게이트웨이가 미리 올림" 대신): 어느 시도를 찍는지는 wrapper 가 정한다.**
wrapper 는 에피소드 진입·저장·버림을 직접 보므로 틀릴 수가 없고, 녹화는 유닛이라 게이트웨이가
재시작돼도 그대로다. 게이트웨이는 진행을 **읽기만** 한다.

1. 시작 때 게이트웨이가 계획을 다시 만들고(결정적이라 화면과 같다), 같은 데이터셋에 이미 성공으로
   찍은 시도를 빼서 버스 키 `record:scenario:plan` 에 `{plan_id, plan, done}` 으로 올린다 — 파일이
   아니라 키인 것은 컨테이너 배포에서 게이트웨이와 녹화 유닛의 경로가 달라서다.
2. wrapper([start_record.py](../wrapper/start_record.py) + 순수 커서
   [scenario_cursor.py](../wrapper/scenario_cursor.py))가 기동 때 읽고,
   - 에피소드 진입(`record_loop` 에 dataset 이 붙은 호출) — 큐 맨 앞 시도를 꺼내 그 task 로 덮는다
   - `save_episode()` 직후 — `(episode_index, trial, outcome)` 를 로그에 덧붙인다. **이 줄이 진실이다**
   - ← 로 버퍼를 비우면 — 같은 시도를 큐 맨 앞에 되돌린다. ⚠ `save_episode` 가 끝에서
     `clear_episode_buffer` 를 부르므로, 저장 중의 비우기는 버림으로 세지 않는다
   - 계획을 다 찍으면 스스로 `stop_recording` — LeRobot 상한은 남은 시도 × 2(실패가 블록 끝에 다시
     들어가므로 넉넉히), 화면 진행률은 남은 시도 수 기준
3. 진행은 버스 키 `record:scenario:state` 로 낸다(지금·다음·마지막 성공 시도·이번 수집 횟수).
   `GET /api/recording/scenario` 가 계획과 합쳐 **옮길 것**을 낸다([progress.py](../backend/app/services/scenario/progress.py)):
   앞 시도가 성공했다고 보고 그 직후 판과 다음 배치의 차이(연쇄면 "그대로"). 앞이 실패·미루기라
   판을 모르면 "판 전체를 그림대로". ← 를 받은 리셋 동안의 다음은 같은 시도다.

[실패로 표시]·[다음 배치 미루기]도 같은 제어 큐(`scenario_fail`·`scenario_unfail`·`scenario_defer`)로
간다 — ←/→ 와 순서가 섞이면 안 되기 때문이다. 실패는 저장 순간 줄에 실린다. 계획을 따르는 녹화에서는
수동 task 변경(`/recording/task`)을 막는다.

실측(2026-10-29, 실제 `LeRobotDataset`·버스, 팔 없이 record() 순서를 흉내): ← 1회·실패 1회·미루기 1회를
섞은 4시도 계획이 에피소드 5개로 끝났고, 에피소드마다 task 가 그 시도의 것, 재녹화는 줄을 안 남김,
실패한 시도는 블록 끝에서 다시 찍혀 성공, 계획이 끝나자 스스로 멈췄다.

⚠ **task 문구는 데이터다 — `t()` 에 넣지 않는다.** 화면 언어를 바꿨다고 데이터셋의 task 가
바뀌면 안 된다. 문구는 규칙 줄마다 사람이 적은 문자열 그대로 쓴다(조사도 사람이 맞춘다).

## 10. 인쇄 — A4 분할

### 10-1. 만드는 법

백엔드에서 PDF 로 굽는다. `matplotlib` `PdfPages` — 그림 크기를 `210/25.4 × 297/25.4` 인치로
주면 mm 가 그대로 나오는 벡터 PDF 다. 태그 비트맵은 `cv2.aruco.generateImageMarker`(36h11,
[tags.py](../cam/piper_cam/tags.py) 와 같은 사전). **새 의존성 없음.**

브라우저 인쇄(SVG + `@page`)는 쓰지 않는다 — 브라우저마다 여백·축소 처리가 달라 mm 를 장담 못 한다.

### 10-2. 모드 — 고른다, 기본은 흐린 판

| 모드 | 선·글자 | 판을 배포 때 | 언제 |
|---|---|---|---|
| **흐린 (기본)** | 가는 연회색 선, 칸 이름은 가장자리 | 깐다 | 사람은 보고 카메라엔 안 보이게 |
| 진한 | 0.5mm 검정, 칸 이름은 칸 안 | 깐다 | 배치 속도 우선, 판이 환경의 일부여도 될 때 |
| 겹쳐보기 전용 | 보정 카드만 찍는다 | 치운다 | 판을 남길 수 없을 때. 카메라가 움직이면 다시 보정 |

**흐린 판의 원리는 해상도다.** 탑 카메라 한 픽셀은 바닥에서 1mm 가까이를 덮는다(640px 가 600mm 를
보면 ≈0.94mm/px). 선을 그 1/3 이하(기본 0.25mm)의 연회색으로 찍으면 한 픽셀 안에서 바탕과 섞여
대비가 몇 % 로 떨어지고, 영상 압축이 그것마저 지운다. 사람 눈은 50cm 에서 0.25mm 선을 쉽게 본다.

- 칸 중심은 팔 3mm 짜리 작은 십자, 칸 이름은 판 가장자리(화각 밖이면 더 좋다)에만.
- **태그는 흐리게 찍을 수 없다** — 대비가 있어야 검출된다. 그래서 잘라 내거나 접어 넣는 띠에 찍고,
  보정·가시성 검사 때만 펼친다.
- 무광 종이 — 광택지 반사는 카메라에 잡힌다.
- ⚠ **흐린 판은 선을 숨길 뿐 종이를 숨기지 못한다.** 흰 사각형과 장 사이 이음매는 보인다. 그래서
  흐린 판의 짝은 "배포 때도 깐다" 다. 테이블이 흰색이면 종이도 거의 안 보인다.

**가시성 검사** — 판을 깐 뒤 버튼 하나. 태그로 호모그래피를 구해 격자선이 있어야 할 픽셀과
옆 픽셀의 밝기 차를 잰다: "선 대비 1.8% — 카메라에 거의 안 보입니다 ✓" / "6% — 0.2mm 로 다시
찍으세요". 같은 측정에서 mm/px 이 나오므로 **이 카메라 기준 권장 굵기**를 바로 알려 주고 다음
인쇄에 쓴다. shm 원본 프레임으로 재므로 학습 영상(압축 후)보다 엄격한 쪽이다.

### 10-3. 장 나누기

- 인쇄 안전 여백 5mm, 장 사이 **겹침 띠 10mm**. 세로·가로 중 장수가 적은 쪽을 고른다.
- 장 수는 판 + 둘레 띠(30mm)로 센다. 예: 칸 80mm × 5열 4행 = 판 400 × 320 → 460 × 380mm → A4 가로 **2×2 = 4장**.
  분류 기본(7열 — 양옆 열이 상자 자리)은 620 × 380mm 라 A4 가로 3×2 = 6장, A3 면 4장이다.
- A3 선택지. 큰 판은 A3 가 이음매가 적다 — 흐린 판에서는 이음매가 가장 잘 보이는 흔적이라 더 그렇다.

### 10-4. 한 장에 찍히는 것

| 요소 | 왜 |
|---|---|
| 격자선 · 칸 중심 십자 · 칸 이름(A1…) | 놓는 기준. 이름은 안내 화면·음성과 같은 이름 |
| 장 번호 + 조립 미니맵 "2/4 (1행 2열)" | 순서 헷갈림 방지 |
| 겹침 띠(점선 "여기에 맞춰 겹치세요") + 맞춤 십자 | 장 사이 어긋남을 눈으로 맞춘다 |
| **100mm 자** + "실제 크기(100%)로 인쇄 — '페이지에 맞춤' 끄기" | 프린터 기본이 맞춤 축소(97% 등)인 경우가 많다 |
| 구역 윤곽(상자·지그) · 로봇 쪽 표시(그 변의 띠에 ▲ + 거리, 가운데 눈금) | 판을 매번 같은 자리에 깐다 |
| 등록 십자 3개 | §12 로봇 좌표 등록용 |
| AprilTag — 둘레 띠의 네 모서리 (id 0~3, 시계 방향, 20mm) | 카메라 겹쳐보기·가시성 검사. 처음엔 장마다 하나씩 두려 했지만 그러면 태그가 작업 영역 안에 들어와 흐린 판의 뜻이 없어진다 — 띠에만 둔다. 자리는 판 크기만으로 정해진다(`printing.tag_centers`) |
| 템플릿별 표시 (조립: 공급 칸 방위 눈금) | 템플릿이 선언한다 |

흐린 모드에서는 자·장 번호·안내 문구도 가장자리 띠로 몬다. **계획표 인쇄**도 같은 자리에서 —
시도 목록 + 작은 배치도 + 체크 칸. 화면 없이 수집할 때.

## 11. 대조 — 계획 vs 실제

### 11-1. 사이드카

```
<dataset>/meta/piper_scenario.json        계획 (wrapper 가 첫 저장 때 한 번 쓴다 — 데이터셋 폴더는 그때 생긴다)
<dataset>/meta/piper_scenario_log.jsonl   바인딩·결과·결정 (wrapper 가 저장 때 덧붙임, 결정은 게이트웨이)
```

쓰는 쪽이 둘이라 파일을 둘로 나눈다. `meta/` 에 두므로 허브 업로드에 같이 실려 간다
(notes_sidecar 관례). 에피소드를 지우면 번호가 당겨지므로 `remap_after_delete` 자리에 이 로그도 넣는다.

- 계획의 이름은 입력의 지문(`plan_id` — 템플릿·시드·판·물체·값의 해시)이다. 같은 데이터셋에 **다른 계획**으로
  녹화를 시작하면 거절한다 — 같은 시도 번호(`b1-r1-1`)가 다른 배치를 뜻하게 되면 대조가 거짓말을 한다.
- 이어 찍기의 "이미 찍은 시도" 는 같은 계획으로 **성공** 저장된 것뿐이다. 실패만 있는 시도는 다시 나온다.
- 결과 `outcome` 은 `success`·`failed` 둘. 계획된 변형(회복·교란)도 `success` 다 — 변형은 계획에 있다.

```jsonc
// piper_scenario.json (요지)
{
  "version": 1,
  "template": "sort",
  "values": { "episode_unit": "one", "target_by": "instruction", ... },
  "seed": 42,
  "trials": [
    { "id": "b02-r07-3", "block": 2, "round": 7,
      "layout": [{"obj": "red", "cell": "B3"}, {"obj": "yellow", "cell": "D1"}],
      "target": {"obj": "red", "cell": "B3", "dest": "bin_left"},
      "task": "빨간 사과를 왼쪽 상자에 넣어", "variant": "normal", "start_hint": "" }
  ]
}
// piper_scenario_log.jsonl — 한 줄이 한 사건, 같은 에피소드는 나중 줄이 이긴다
{ "trial": "b02-r07-3", "episode_index": 42, "saved_at": "...", "outcome": "success", "operator": "..." }
{ "episode_index": 43, "outcome": "failed", "decision": "pending", "at": "..." }
{ "episode_index": 43, "decision": "exclude", "by": "training-start", "at": "..." }
```

### 11-2. 쓰는 곳

- **POS분석** — 파지 말단(로봇 좌표)을 작업판 칸으로 바꿔(§12 등록 필요) 계획 칸과 다르면
  "배치 오류 의심" 목록. 커버리지 그림에 계획 히트맵을 겹친다.
- **B1 구성 탭** — 템플릿·목표 종류·물체 수·변형·결과·결정별 에피소드 수의 데이터 출처가 된다.
- **보충 계획** — §14-1.

## 12. 작업판 ↔ 로봇 좌표 (선택)

없어도 설계·인쇄·안내·카메라 겹쳐보기는 다 된다. 없어서 못 하는 것은 **도달 가능 칸 판정**과
**POS 대조** 둘이다.

- **등록** — 판의 등록 십자 3곳에 그리퍼 끝을 대고(조그 또는 리더) FK 값을 찍는다 → 2D 강체
  변환 + 판 높이. [정렬 검사](alignment-check.md)의 "현재 자세를 찍어서 만든다" 원칙 그대로 —
  좌표를 손으로 적게 하지 않는다. 잔차(mm)를 보여 주고 크면 거절.
- **도달 판정** — 칸 중심마다 작업공간 검사 → 못 가는 칸은 설계 화면에서 회색, 생성기가 뺀다.
- 판을 로봇 기준선에 맞춰 깔면(바닥 테이프) 등록은 한 번이면 된다.

## 13. 평가에도 같은 설계기

- **보류 칸** — 설계 때 몇 칸을 학습에서 뺀다. 평가 계획은 학습 칸 + 보류 칸으로 짠다 →
  "처음 보는 자리" 일반화를 숫자로.
- 추론 화면에 "다음 평가 배치" 패널, 성공/실패 버튼이 `eval_log` 에 `scenario`·`trial` 을
  함께 남긴다(`EvalEntry` 필드 둘 추가). → **칸별 성공률 히트맵**, 종류별 성공률, 체크포인트 비교.
- 알약 사례 C3("체크포인트는 실기로 고른다")를 칸 단위로 할 수 있게 된다.

## 15. API 스케치

| 경로 | 하는 일 |
|---|---|
| `GET /api/scenario/templates` ☑ | 템플릿 목록과 선언(필드·에피소드 단위·변형) |
| `GET`·`PUT`·`DELETE /api/presets/scenario/{name}` | 저장한 설정 — 프리셋 스토어 도메인 `scenario`, scope `shared` |
| `POST /api/scenario/generate` ☑ | `{template, seed, board, catalog, values}` → 계획 + 균형 요약(히트맵·총량·교차표·경고·예상 시간). 저장 안 함 |
| `POST /api/scenario/print` ☑ | `{board, paper, mode, line_mm, title, labels}` → PDF (작업판). 문구(`labels`)는 화면이 옮겨 넘긴다. 계획표 인쇄는 아직 |
| `POST /api/scenario/print/layout` ☑ | 같은 본문 → 몇 장으로 나뉘나 (인쇄 전에 화면이 보여 준다) |
| `POST /api/scenario/visibility` | 탑 카메라 한 장으로 가시성 검사 → 선 대비 %, mm/px, 권장 굵기 |
| `POST /api/recording/start` ☑ | 기존 본문에 `scenario: {template, seed, board, catalog, values}` 추가 → 계획을 다시 만들어 버스에. 응답 `scenario: {remaining, done}` |
| `GET /api/recording/scenario` ☑ | 진행 — 지금·다음 시도(옮길 것 포함), 블록, 완료 수, 이번 수집 횟수. 정지 뒤에도 마지막 세션의 것(`recording=false`) |
| `POST /api/recording/scenario/defer` ☑ | 다음 시도를 블록 끝으로 (기획은 "리셋 중에만" 이었으나 언제든 — 늘 **다음** 시도에 건다) |
| `POST /api/recording/scenario/fail` ☑ | `{failed}` — 지금 에피소드에 실패 표시·취소 (저장 때 바인딩과 함께 쓰인다) |
| `GET /api/datasets/{id}/scenario` ☑ | 계획 요약·에피소드별 결과·미결·제외·총 에피소드 수 (기획의 `/scenario/pending` 을 넓혔다). 목록 배지는 `GET /api/datasets` 의 `scenario` 필드 |
| `POST /api/datasets/{id}/scenario/decision` ☑ | `{episodes, decision, by}` — 포함·제외. 실패 표시가 있는 에피소드에만 붙는다 |

WS 는 기존 녹화 상태 메시지에 `scenario` 필드를 더한다.

## 16. 단계

| 단계 | 내용 | 전제 |
|---|---|---|
| 1 ☑ | **템플릿 틀 + 분류** — YAML 로더, 공통 균형기(순수 함수)와 균형 테스트, 분류 생성기(하나씩·연속), 설계 화면, 저장한 설정, PDF(세 모드) | 없음 — 장치 무관 |
| 2 ☑ | **수집 연결** — 사이드카, wrapper 바인딩(§9-3), task 자동, 녹화 화면 안내·안내 창, 음성, **실패 표시와 미결 알림 전부(§8-3)** + 학습 제외(`--dataset.episodes`). 기획의 [계획 일시정지(자유 녹화)]는 안 했다 — 계획 없이 찍으려면 체크를 끄고 녹화한다 | 1 |
| 3 | **대조** — B1 구성 탭, 재번호, 보충 계획, 옮기기 템플릿 | 2 |
| 4 | **카메라** — 태그 호모그래피 겹쳐보기, 배치 확인, 가시성 검사 | 2, 탑 카메라 |
| 5 | **조립 템플릿** — 단계·선행 관계 편집기, 방위 균형, 방위 눈금 인쇄 | 1 |
| 6 | **로봇 좌표** — 등록, 도달 판정, POS 대조 | 1 |
| 7 | **평가** — 보류 칸, 추론 화면 패널, eval_log 필드 | 2 |
| 8 | **시뮬** — 자동 배치 | 가상환경 다물체화 |

⚠ **실패 표시와 미결 알림은 같은 단계에 나간다.** 표시만 먼저 나가면 알림 없는 미결이 쌓이고,
그 데이터셋은 미결인 채로 학습된다 — "꼭 알린다" 는 결정이 첫날부터 깨진다.

**인수 기준(1~2):**
- ☑ 사과 3종으로 120시도를 생성해 종류 × 칸 목표 횟수의 최대−최소가 1 이하, 블록마다도 같은 조건.
  하나씩·연속 두 모드 모두. 모든 등록 템플릿이 기본값으로 같은 검사를 통과한다.
- ☑ ACT 를 고르면 `지시문` 이 막힌다 (화면은 순서 규칙으로 돌리고, API 는 400).
- ◐ (2단계) 실기에서 한 블록을 찍는 동안 ← 재녹화 2회와 실패 표시 1회를 섞어도 사이드카 로그의 시도와
  에피소드가 1:1 로 맞는다. — 실제 `LeRobotDataset`·버스로 녹화 순서를 흉내 낸 시험은 ☑(§9-3 실측), **실기 녹화는 아직**.
- ☑ (2단계) 미결 실패가 있는 데이터셋으로 학습을 시작하면 선택 패널이 반드시 뜨고, [제외하고 계속]이
  `--dataset.episodes` 에 그 에피소드를 빼고 넘긴다. 화면을 거치지 않은 시작은 서버가 409.

## 17. 결정 기록 (2026-10-29)

| # | 물음 | 결정 |
|---|---|---|
| 1 | 시나리오 종류를 어떻게 다루나 | **템플릿** — 분류·조립 먼저, 옮기기·쌓기·양팔 건네기는 후보. 템플릿 = YAML 선언 + Python 생성기 |
