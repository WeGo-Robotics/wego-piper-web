# 가중치 분석기 — 체크포인트를 실기 전에 진단한다

> 상태: ◐ 1단계 ☑ (2026-10-21 — W1 체크포인트 개요 · W2 오프라인 평가 · §5 편집 장면 반응) · 5단계(W6) ☑ (2026-10-22) · 2~4단계 ☐
> 자리: **추론 분석** 화면(`/debug`, [DebugLogsPage.tsx](../frontend/src/pages/DebugLogsPage.tsx))의 탭
> 짝: [에피소드 분석기](episode-analyzer.md) — 저쪽은 데이터를, 이쪽은 가중치를 본다

## 1. 왜

체크포인트를 고르는 근거가 지금은 **학습 손실과 실기 몇 번**뿐이다. 손실은 다음 학습을 시작하면
지워지고(`train_manager.start` 가 레코드를 지운다), 실기 성공 기록은 체크포인트별 집계 API 가 있는데
화면에 안 나온다. 그 사이를 메울 오프라인 진단이 하나도 없다 — 데이터셋 에피소드에 정책을 돌려
예측과 실제를 견주는 코드가 저장소 어디에도 없다.

참고 사례 [알약 조제 로봇](https://jongky.site/projects/pill-robot) 의 교훈 셋이 설계를 정한다:

- **오프라인 1위 ≠ 실기 1위** (두 번 있었다) — 오프라인 지표는 **진단**이고 판정은 실기다. 그래서 화면에서
  오프라인 지표는 늘 실기 성공률 **옆에** 둔다.
- **측정 시점의 함정** — "목표를 완벽히 본다(상관 1.00)" 가 파지 직전에 잰 값이었다(진행률 30% 에선 0.01).
  오차는 **페이즈별로** 쪼개 본다.
- **8시간 재학습 → 분 단위 진단** — 체크포인트를 그대로 두고 입력을 바꿔 반응을 잰다.

## 2. 자리 — 추론 분석 화면의 탭

`추론 분석 [추론 기록 | 체크포인트 | 오프라인 평가]` — 탭은 제목 바로 옆. 지금 화면의 내용(`--debug`
추론 기록 재생)은 **추론 기록** 탭이 된다. 추론 기록(실기에서 정책이 본 것)과 오프라인 평가(데이터에서
정책이 낸 것)가 한 화면에 있어야 "실기에서는 왜 다르게 했나" 로 오간다.

## 3. W1 — 체크포인트 개요 (GPU 불필요)

한 학습 실행의 체크포인트들을 **step 축 하나**에 겹친다.

| 줄 | 출처 | 지금 |
|---|---|---|
| 학습 손실 | 학습 로그 파싱(`training/metrics.py`) | ⚠ 다음 학습 시작 때 지워진다 → **실행 폴더에 저장**(`piper_train_metrics.json`) |
| 오프라인 오차 | W2 결과 캐시 | 새로 |
| 실기 성공 | 평가 기록 `by_checkpoint`(`/api/eval/stats`) | 집계는 있고 화면이 없다 |

표: step · 손실 · 오프라인 오차(학습 데이터) · 그리퍼 시점 오차 · 실기 성공 n/N. 학습 데이터셋은
`train_config.json` 의 `dataset.repo_id`·`episodes`(None = 전부)에서 읽는다. 이전 학습은 곡선이 없다 —
저장을 시작한 뒤부터 쌓인다.

## 4. W2 — 오프라인 평가

데이터셋 에피소드를 프레임마다 정책에 넣고 **예측 행동 대 녹화 행동**을 견준다(open-loop).

- 표본: 고른 에피소드를 `stride` 프레임 간격으로. 프레임마다 청크 하나를 예측해 **첫 동작**(그 순간의 지령)과
  **청크 전체**(앞으로 chunk 만큼의 계획)를 녹화와 비교한다.
- 오차는 관절(도)·그리퍼(정규화 단위)로, **페이즈별**로 쪼갠다(사이드카 `phase_signals.parquet`).
- 그리퍼 닫기 시점: 예측 그리퍼가 닫힘으로 넘어가는 프레임 대 녹화 — 늦게/일찍 닫나.
- 결과는 체크포인트·데이터셋·표본 설정별로 캐시 — 같은 조합은 다시 계산하지 않는다.

⚠ open-loop 오차는 **폐루프 성공과 다르다** — 정책은 자기 실수를 바로잡으며 가는데 여기선 늘 녹화된
정답 상태에서 다시 시작한다. 그래서 판정이 아니라 진단이다(§1).

## 5. 처음 보는 장면 — 편집한 한 프레임의 반응

데이터셋은 통째로 학습하므로(`episodes: None`) 같은 데이터 안에 "처음 보는 장면" 이 없다. **학습 데이터
프레임을 캡처해 고친다** — 물체를 옆 배경으로 덮어 지우는 **복제 도장(클론 스탬프)** 도구로.

- 원본 프레임과 편집 프레임을 **같은 관절 상태**로 정책에 넣고, 두 예측 청크를 견준다. 정답 행동이 필요
  없다 — 3D 에 두 예측 궤적(말단, FK)을 겹쳐 그린다.
- 편집 종류를 사람이 고른다: **배경·방해물을 지웠다**(두 예측이 같아야 정상 — 다르면 배경에 기대고 있다) /
  **목표 물체를 지웠다**(달라야 정상 — 같으면 화면을 안 보고 궤적을 외웠다).
- 결과: 두 궤적 사이 거리(mm), 그리퍼 닫기 시점 차.
- 도구: 브러시 크기, Alt+클릭으로 원본 위치 지정 후 칠하면 그만큼 떨어진 곳을 베껴 덮는다(포토샵의 그것).
  카메라마다 따로 고친다. 고친 카메라만 바뀌고 나머지는 원본 그대로 들어간다.

## 6. 실행 구조

- LeRobot 을 직접 부르는 자리다 — `wrapper/offline_eval.py`(엔코더 프로브 `wrapper/encoder_probe.py` 옆).
  인터프리터는 `settings.grpc_python`. 정책 로드·전처리·`predict_action_chunk`·후처리는 추론 wrapper 와 같은 길.
- 에피소드 평가는 수 분 → **systemd 유닛** `piper-weval`(게이트웨이를 재시작해도 산다, 기동 시 재부착).
  한 프레임 반응은 수 초라 엔코더 프로브처럼 블로킹 subprocess.
- **GPU 배타**: 학습·추론·검출 학습과 서로 막는다(`exclusivity.BLOCKED_BY`, 상태 있는 활동이라 대칭).
  로봇을 안 움직이므로 E-stop 대상이 아니다.
- 결과 캐시: `log_dir/weight_eval/<키>/` — `meta.json` · `progress.json` · `result.parquet`.

## 8. 실측 (2026-10-21, `2026-10-20/14-28-18_act` · dualarm_cube_4point 에피소드 0~3 · 5프레임 간격)

| step | 관절 오차 | 그리퍼 닫기 시점 | 걸린 시간 |
|---|---|---|---|
| 5k | 3.01° | ±0.21초 | 376프레임 약 15초 (RTX 5090) |
| 10k | 2.22° | ±0.08초 | |
| 15k | 1.80° | ±0.04초 | |
| 20k | 1.74° | ±0.08초 | |

- 15k 이후 거의 안 준다 — W1 의 "정체" 를 보여주는 첫 사례. 학습 데이터 위의 open-loop 라 낮은 것이 당연하고,
  **처음 보는 장면**은 §5 로 본다.
- 페이즈별로는 PARKING·IDLE 이 크고 GRASP 가 작다(5k: 3.78° · 3.49° 대 2.03°) — 정지 구간의 미세 지터를
  정책이 안 따라 하는 것이 섞인다. 큰 값이 곧 나쁜 값은 아니다.
- **반응**: 위 카메라(`left_top`)를 회색 판으로 가리면 왼팔 계획이 평균 54mm(최대 137mm) 갈라지고 오른팔은
  4.7mm — 왼팔이 그 카메라에 기댄다. 고치지 않은 PNG 를 그대로 넣으면 **정확히 0.0mm**(같은 디코더에서 꺼낸
  바탕이라 편집 말고는 아무것도 안 바뀐다 — `frames` 모드를 둔 이유).
- 체크포인트를 잇달아 돌릴 때 앞 유닛이 결과를 다 쓰고 내려가는 2초 틈에 다음 시작이 409 로 막혔다 →
  `weight_eval._settle()` 이 기다린다.

## 9. W6 — 엔코더 프로브에 에피소드 프레임 (2026-10-22)

엔코더 프로브 슬롯의 세 번째 소스. 카메라 캡처는 "지금" 장면뿐이고 파일 추가는 손으로 뽑아 와야 해서,
**정책이 실제로 배운 프레임**을 넣을 길이 없었다.

- 슬롯의 [에피소드 프레임 추가] → 데이터셋 · 에피소드 · 프레임 · 카메라(또는 모든 카메라). 에피소드·프레임은
  `0, 3, 5-7` 처럼 여러 개, 조합 전부를 한 번에 꺼낸다 — 데이터셋을 여는 것이 수 초라 한 장씩 부르지 않는다.
- 이미지는 §5 와 같은 `/weval/frames`(학습과 같은 디코더). `frames` 모드가 에피소드 × 프레임을 받아
  `e{에피소드}_f{프레임}/{카메라}.png` 로 낸다 — 장면 편집기도 같은 응답(`items[0].dir`)을 쓴다.
- 한 슬롯은 한 번에 24장까지 인코딩한다(`encoder_probe.MAX_BATCH`) — 고르는 단계에서 넘으면 막는다.
  꺼내기는 한 번에 48장까지(`weight_eval.MAX_FRAME_ITEMS`). 없는 프레임은 그 항목만 사유를 달고 건너뛴다.
