# 텔레오퍼레이션 — 세 가지 방식으로 팔을 움직인다

추론도 녹화도 아닌 **그냥 팔을 움직이는** 기능. 셋을 한 화면에서 한다:

| 모드 | 입력 | 누가 관절을 정하나 | 움직이는 팔 |
|---|---|---|---|
| **A. 리더암** | 사람이 리더 팔을 손으로 끈다 | 리더의 관절값을 그대로 복사 | 팔로워 |
| **B. 관절 조그** | 화면 슬라이더/버튼 | 사람이 관절마다 직접 | 팔로워 |
| **C. 엔드포인트** | 화면에서 X/Y/Z·RX/RY/RZ | **팔의 온보드 IK** (우리는 안 푼다) | 팔로워 |

> ⚠ **셋 다 움직이는 것은 팔로워다. 리더는 화면에서 조작할 수 없다.**
> 마스터(示教输入臂)로 설정된 팔은 **외부 제어 명령을 무시한다** — 이건 추정이
> 아니라 측정한 사실이다. 마스터/슬레이브 판별 기능이 정확히 그 성질을 이용한다:
> 이동 명령을 넣고 안 움직이면 마스터다.
>
> 그래서 B·C 는 **대상 팔이 슬레이브일 때만** 뜻이 있다. 리더에게 보내면 명령이
> 조용히 사라지고, 화면만 움직인 척한다.

---

## 1. 지금 있는 것 — 절반은 이미 깔려 있다

| | 상태 |
|---|---|
| shm 명령 경로 (`ActionWriter` → robotd → `filter_goal` → `JointCtrl`) | ☑ 있다. **소비자만 없다** |
| 안전 필터 [`filter_goal`](../robot/piper_robot/safety.py#L112) | ☑ 관절 범위·변화율·데드맨 |
| 웹 조그 설계 (= 모드 B) | ☑ [manual-control.md §2](manual-control.md) 에 이미 있다 — **다시 설계하지 않는다** |
| 마스터/슬레이브 전환 · 판별 | ☑ `MasterSlaveConfig`, 명령 반응 판별 |
| 리더 → 팔로워 릴레이 | ✗ 녹화(`lerobot-record`) 안에만 있다. 독립 실행 없음 |
| 엔드포인트 제어 | ✗ 코드베이스에 `EndPoseCtrl` 호출이 하나도 없다 |
| 배타 활동 `TELEOP` | ✗ 없다. E-stop 대상도 아니다 |

즉 **B 는 문서대로 구현만, A 는 녹화에서 떼어내기, C 는 새것**이다.

## 2. SDK 가 주는 것 (실측)

```python
ModeCtrl(ctrl_mode=0x01, move_mode, speed, is_mit=0x00)
#   move_mode  0x00 MOVE P(점대점)  0x01 MOVE J(관절)  0x02 MOVE L(직선)
JointCtrl(j1..j6)                 # 관절, 0.001°
EndPoseCtrl(X, Y, Z, RX, RY, RZ)  # 말단, 0.001mm / 0.001° — **온보드 IK**
GetArmEndPoseMsgs()               # 현재 말단 자세 (상대 조그의 기준점)
```

역기구학을 우리가 풀지 않는다는 요구는 그대로 만족한다 — `EndPoseCtrl` 을 쓰면
관절을 정하는 것은 팔의 컨트롤러다. **그게 이 기능의 가장 큰 위험이기도 하다(§4).**

## 3. 모드별 설계

### A. 리더암 구동 — 릴레이 루프 (☑ 구현됨)

**게이트웨이가 shm 만으로 한다.** 리더의 관절값은 robotd 가 이미 shm 에 발행하고
있으므로 읽는 쪽이 하나 더 붙을 뿐이고, 팔로워의 명령 경로도 조그가 쓰는 그것이다 —
**robotd 변경 0줄.** RPC 로 읽으면 초당 30번 왕복이 생긴다.

⚠ 리더 상태가 0.5초 넘게 낡으면 **보내지 않는다.** 얼어붙은 자세를 계속 밀면
팔로워는 그게 사람의 의도인 줄 알고 거기 서 있는다. 안 보내면 robotd 의 데드맨이
팔을 그 자리에 세운다 — 그쪽이 정직하다.

⚠ 시작 전에 리더를 **한 번 읽어 본다.** 발행 없는 리더로 열면 릴레이는 조용히
아무것도 안 하고, 사용자는 팔이 고장난 줄 안다.


리더는 **손으로만** 움직인다. 이 모드에서 소프트웨어가 리더에게 보내는 명령은
없고, 있어도 무시당한다 — 읽기만 한다.

⚠ **펌웨어 연동이 아니다.** `can0`·`can1` 이 서로 다른 USB-CAN 어댑터에 물려 있다
(`3-11.2` / `3-11.1`). 물리 버스가 달라 리더가 팔로워에게 직접 못 보낸다 —
**소프트웨어가 읽어서 써야 한다.**

```
robotd: 리더 관절 읽기(0x15x 지령) ─→ filter_goal ─→ 팔로워 JointCtrl
```

이미 `lerobot-record` 가 하는 일이라 새 알고리즘이 아니다. 떼어내서 **녹화 없이**
돌리는 것이 이 모드다. 리더는 `MasterSlaveConfig(0xFA)` 로 교시 입력 모드가 되어
토크가 풀리고, 피드백 대신 지령(0x15x)으로 자기 자세를 알린다
([arm.py](../robot/piper_robot/arm.py) `_CTRL_FRESHER_S` 주석 참고).

### 대상 팔 고르기 — B·C 의 전제

```
role == follower  →  조작 가능
role == leader    →  막는다. "마스터는 외부 명령을 무시합니다"
role == unknown   →  막는다. "먼저 [찾기] 로 판별하세요"
```

⚠ **역할이 unknown 이면 시도하지 않는다.** 마스터에게 보낸 명령은 에러도 안 나고
그냥 사라진다 — 사용자는 팔이 고장 났다고 생각하게 된다. 모르는 상태에서
보내느니 판별부터 시키는 편이 낫다. 판별은 이미 버튼 하나다.

리더를 굳이 조작하고 싶다면 슬레이브로 바꿔야 하는데(`MasterSlaveConfig(0xFC)`),
그러면 **텔레오퍼레이션 짝이 깨진다.** 화면이 그걸 대신 결정하지 않는다 —
막고 이유를 말한 뒤, 바꾸는 것은 기존 마스터/슬레이브 버튼으로 사용자가 한다.

### B. 관절 조그 — [manual-control.md §2](manual-control.md) 그대로

깔린 shm 경로에 소비자를 붙인다. 그 문서가 데드맨·이중 열기·배타 가드까지
다뤄 뒀으므로 **여기서 다시 쓰지 않는다.** 이 문서는 그것을 텔레오퍼레이션
화면 안에 넣는 것만 맡는다.

### C. 엔드포인트 — 온보드 IK (☑ 구현됨)

**여기만 robotd 를 고쳤다.** `EndPoseCtrl` 은 shm 관절 경로를 안 타므로 CAN 을 쥔
쪽이 직접 보내야 한다. 조그·릴레이가 robotd 변경 0줄이었던 것과 갈리는 지점이다.

거절은 **클램프가 아니다.** 상자 모서리로 미끄러져 들어가면 사용자는 자기가 시킨
것과 다른 곳으로 간 이유를 모른다 — 안 보내고 말한다. 도달 못 하면 그것도 말하고
**더 보내지 않는다**(IK 해가 없는 곳을 계속 밀면 특이점에서 튄다).

```
[화면 X/Y/Z·RX/RY/RZ] ─RPC→ robotd ─→ ModeCtrl(0x01, MOVE P) → EndPoseCtrl(…)
```

**상대 조그로 만든다.** 절대 좌표를 입력하게 하면 사람이 팔의 좌표계를 알아야
하고, 오타 하나가 큰 이동이 된다. `GetArmEndPoseMsgs()` 로 현재 자세를 읽고
거기에 `±5mm` / `±1°` 씩 더한다 — 버튼을 누른 만큼만 움직인다.

## 4. ⚠ 안전 — 여기가 이 기능의 핵심이다

**`filter_goal` 은 관절 공간에서만 동작한다.** 범위 클램프도 변화율 제한도
`JOINT_ORDER` 를 훑는다. 모드 C 는 관절을 우리가 안 정하므로 **그 필터가 한 개도
안 걸린다** — MIT 모드가 같은 문제를 갖는다고 manual-control §3 이 이미 적었다.

그래서 C 에는 **다른 층의 제한**이 필요하다:

| 제한 | 어떻게 |
|---|---|
| 한 번에 가는 거리 | 상대 조그라 구조적으로 제한된다 (5mm/1°) |
| 작업 공간 상자 | X/Y/Z 최소·최대. 목표가 밖이면 **보내지 않는다** |
| 속도 | `ModeCtrl` 의 `move_spd_rate_ctrl` 을 낮게 고정 |
| 데드맨 | 명령이 끊기면 멈춘다 — 마지막 자세를 계속 보내지 않는다 |
| 도달 실패 | 명령 후 `GetArmEndPoseMsgs` 가 안 따라오면 **더 보내지 않고 멈춘다.** IK 해가 없는 곳을 계속 밀면 팔이 떨거나 특이점에서 튄다 |

> 관절 한계는 팔 컨트롤러가 자체로 갖고 있다고 **가정하지 않는다.** 확인 전까지
> 작업 공간 상자를 좁게 잡는다. 브링업에서 넓혀 간다.

## 5. 배타와 E-stop — 지금 빠져 있다

`Activity.TELEOP` 를 새로 만든다.

```python
Activity.TELEOP: [TRAINING?, INFERENCE, RECORDING, DATASET_EDIT]
```

- **추론·녹화와 배타** — 같은 팔을 둘이 밀면 안 된다
- **`ESTOP_TARGETS` 에 넣는다** — 팔이 움직이는 활동은 전부 대상이라는 refactor #10
  의 규칙 그대로다. 릴레이도 조그도 게이트웨이/robotd 안의 루프라 PID 로 죽일 수 있다
- 학습과는? GPU 를 안 쓰므로 **막지 않는다**

### E-stop 은 토크도 끊는다 (결정됨)

릴레이만 멈추면 팔로워는 마지막 명령 자세에 **선 채로 힘을 준다.** 사람이 팔에
끼었을 때 그 상태로는 손으로 빼낼 수 없다. E-stop 은 사람이 일부러 누르는
것이고, 그때 원하는 것은 "팔이 위험하지 않게" 다 — 그래서 토크를 끊는다.

> ⚠ **팔이 중력으로 떨어진다.** 이건 대가지 부작용이 아니다. 높이 든 자세에서
> 누르면 그대로 내려앉으므로, 아래에 뭐가 있는지가 중요해진다.

⚠ **데드맨은 반대로 정해져 있다.** [`filter_goal`](../robot/piper_robot/safety.py#L117)
이 *"토크를 끊지 않는 이유는 그게 더 위험하기 때문이다 — 팔이 중력으로 떨어진다.
정지 = 그 자리에 서기다"* 라고 적어 뒀다. 둘이 갈리는 것은 **의도한 것으로 본다**:

| | 상황 | 멈추는 방식 |
|---|---|---|
| 데드맨 | 브라우저가 닫혔다·heartbeat 가 끊겼다 | 그 자리에 **선다** |
| E-stop | 사람이 버튼을 눌렀다 | 토크를 **끊는다** |

앞은 사고(연결 끊김)라 사람이 옆에 있는지 모른다 — 떨어뜨리면 안 된다.
뒤는 사람이 보고 눌렀다 — 손으로 치울 수 있어야 한다.

### 누가 토크를 끊나 — estopd 가 아니라 robotd

estopd 는 **PID 를 SIGKILL 할 뿐**이다. 토크 차단은 CAN 명령이라 팔을 쥔
프로세스만 할 수 있는데, 그게 robotd 다.

> ⚠ estopd 가 robotd 에게 RPC 를 보내게 만들면 안 된다. estopd 는 *"게이트웨이가
> 응답 못 하는 상황"* 을 위해 존재하는데, 남에게 부탁하는 순간 그 남도 응답
> 못 할 수 있다. **robotd 가 E-stop 알림(`CH_ESTOP`)을 직접 구독**해 자기 팔의
> 토크를 끊는다 — 이미 버스에 붙어 있으므로 새 의존이 아니다.

이러면 텔레오퍼레이션뿐 아니라 **추론·녹화 E-stop 에서도** 토크가 끊긴다.
그게 일관돼서 낫다 — 같은 빨간 버튼이 활동마다 다르게 동작하면 아무도 못 믿는다.
다만 **동작이 바뀌는 것**이므로 실기 확인이 필요하다 (§7).

## 6. 순서

| # | 작업 | 왜 이 순서 |
|---|---|---|
| **1 ☑** | `Activity.TELEOP` + `ESTOP_TARGETS` + 배타 가드 + **robotd 토크 차단** | **먼저 한다.** 팔을 움직이는 코드를 넣기 전에 멈추는 길부터. 토크 차단은 여기서 한 번 만들면 모든 활동이 쓴다 |
| **2 ☑** | B 관절 조그 — `JogSession` + 역할 가드 + 화면 | robotd 변경 0줄 |
| **3 ☑** | A 리더 릴레이 — `RelaySession` (shm 상태 → shm 명령) | robotd 변경 0줄 |
| **4 ☑** | C 엔드포인트 + 작업 공간 상자 | 필터가 안 걸리는 유일한 모드라 맨 뒤에 했다 |
| **5 ☑** | 한 화면에 셋 묶기 (로봇 페이지, 팔 펼치면) | 앞이 다 되니 UI 는 얇았다 |

각 단계가 독립으로 쓸 만하다 — 2까지만 해도 "추론 없이 팔을 움직인다"가 된다.

## 7. 정해야 할 것

- ~~리더 모드에서 E-stop 이 무엇을 해야 하나~~ — ☑ **토크도 끊는다** (§5).
  남은 것은 실기 확인이다: 팔을 든 자세에서 눌러 **얼마나 내려앉는지**, 그리고
  기존 추론·녹화 E-stop 의 동작이 바뀌는 것을 받아들일지
- **작업 공간 상자의 초기값** — 팔 컨트롤러가 자체 한계를 갖는지 실측 전까지는
  좁게. 실기에서 넓혀야 한다
- **C 의 좌표계** — `EndPoseCtrl` 의 원점과 축 방향이 베이스 기준인지 확인 필요.
  화면의 "앞으로"가 팔의 어느 축인지가 여기서 정해진다
- **양팔** — [bimanual](bimanual.md) 과 겹친다. 지금은 한 팔씩만 다루고,
  양팔 동시 조작은 그 문서가 서면 붙인다
