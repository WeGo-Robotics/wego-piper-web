# 텔레오퍼레이션 — 세 가지 방식으로 팔을 움직인다

추론도 녹화도 아닌 **그냥 팔을 움직이는** 기능. 셋을 한 화면에서 한다:

| 모드 | 입력 | 누가 관절을 정하나 |
|---|---|---|
| **A. 리더암** | 사람이 리더 팔을 손으로 끈다 | 리더의 관절값을 그대로 복사 |
| **B. 관절 조그** | 화면 슬라이더/버튼 | 사람이 관절마다 직접 |
| **C. 엔드포인트** | 화면에서 X/Y/Z·RX/RY/RZ | **팔의 온보드 IK** (우리는 안 푼다) |

---

## 1. 지금 있는 것 — 절반은 이미 깔려 있다

| | 상태 |
|---|---|
| shm 명령 경로 (`ActionWriter` → robotd → `filter_goal` → `JointCtrl`) | ☑ 있다. **소비자만 없다** |
| 안전 필터 [`filter_goal`](../robot/piper_robot/safety.py#L112) | ☑ 관절 범위·변화율·데드맨 |
| 웹 조그 설계 (= 모드 B) | ☑ [manual-control.md §2](manual-control.md) 에 이미 있다 — **다시 설계하지 않는다** |
| 마스터/슬레이브 전환 · 판별 | ☑ `MasterSlaveConfig`, 명령 반응 판별 |
| 리더 → 팔로워 릴레이 | ✗ 녹화(`lerobot-record`) 안에만 있다. 독립 실행 없음 |
| 엔드포인트 제어 | ✗ 코드베이스에 `EndPoseCtrl` 호출이 하나도 없다 |
| 배타 활동 `TELEOP` | ✗ 없다. E-stop 대상도 아니다 |

즉 **B 는 문서대로 구현만, A 는 녹화에서 떼어내기, C 는 새것**이다.

---

## 2. SDK 가 주는 것 (실측)

```python
ModeCtrl(ctrl_mode=0x01, move_mode, speed, is_mit=0x00)
#   move_mode  0x00 MOVE P(점대점)  0x01 MOVE J(관절)  0x02 MOVE L(직선)
JointCtrl(j1..j6)                 # 관절, 0.001°
EndPoseCtrl(X, Y, Z, RX, RY, RZ)  # 말단, 0.001mm / 0.001° — **온보드 IK**
GetArmEndPoseMsgs()               # 현재 말단 자세 (상대 조그의 기준점)
```

역기구학을 우리가 풀지 않는다는 요구는 그대로 만족한다 — `EndPoseCtrl` 을 쓰면
관절을 정하는 것은 팔의 컨트롤러다. **그게 이 기능의 가장 큰 위험이기도 하다(§4).**

---

## 3. 모드별 설계

### A. 리더암 구동 — 릴레이 루프

⚠ **펌웨어 연동이 아니다.** `can0`·`can1` 이 서로 다른 USB-CAN 어댑터에 물려 있다
(`3-11.2` / `3-11.1`). 물리 버스가 달라 리더가 팔로워에게 직접 못 보낸다 —
**소프트웨어가 읽어서 써야 한다.**

```
robotd: 리더 관절 읽기(0x15x 지령) ─→ filter_goal ─→ 팔로워 JointCtrl
```

이미 `lerobot-record` 가 하는 일이라 새 알고리즘이 아니다. 떼어내서 **녹화 없이**
돌리는 것이 이 모드다. 리더는 `MasterSlaveConfig(0xFA)` 로 교시 입력 모드가 되어
토크가 풀리고, 피드백 대신 지령(0x15x)으로 자기 자세를 알린다
([arm.py](../robot/piper_robot/arm.py) `_CTRL_FRESHER_S` 주석 참고).

### B. 관절 조그 — [manual-control.md §2](manual-control.md) 그대로

깔린 shm 경로에 소비자를 붙인다. 그 문서가 데드맨·이중 열기·배타 가드까지
다뤄 뒀으므로 **여기서 다시 쓰지 않는다.** 이 문서는 그것을 텔레오퍼레이션
화면 안에 넣는 것만 맡는다.

### C. 엔드포인트 — 온보드 IK

```
[화면 X/Y/Z·RX/RY/RZ] ─RPC→ robotd ─→ ModeCtrl(0x01, MOVE P) → EndPoseCtrl(…)
```

**상대 조그로 만든다.** 절대 좌표를 입력하게 하면 사람이 팔의 좌표계를 알아야
하고, 오타 하나가 큰 이동이 된다. `GetArmEndPoseMsgs()` 로 현재 자세를 읽고
거기에 `±5mm` / `±1°` 씩 더한다 — 버튼을 누른 만큼만 움직인다.

---

## 4. ⚠ 안전 — 여기가 이 기능의 핵심이다

**`filter_goal` 은 관절 공간에서만 동작한다.** 범위 클램프도 변화율 제한도
`JOINT_ORDER` 를 훑는다. 모드 C 는 관절을 우리가 안 정하므로 **그 필터가 한 개도
안 걸린다** — MIT 모드가 같은 문제를 갖는다고 manual-control §3 이 이미 적었다.

그래서 C 에는 **다른 층의 제한**이 필요하다:

| 제한 | 어떻게 |
|---|---|
| 한 번에 가는 거리 | 상대 조그라 구조적으로 제한된다 (5mm/1°) |
| 작업 공간 상자 | X/Y/Z 최소·최대. 목표가 밖이면 **보내지 않는다** |
| 속도 | `ModeCtrl` 의 `move_spd_rate_ctrl` 을 낮게 고정 |
| 데드맨 | 명령이 끊기면 멈춘다 — 마지막 자세를 계속 보내지 않는다 |
| 도달 실패 | 명령 후 `GetArmEndPoseMsgs` 가 안 따라오면 **더 보내지 않고 멈춘다.** IK 해가 없는 곳을 계속 밀면 팔이 떨거나 특이점에서 튄다 |

> 관절 한계는 팔 컨트롤러가 자체로 갖고 있다고 **가정하지 않는다.** 확인 전까지
> 작업 공간 상자를 좁게 잡는다. 브링업에서 넓혀 간다.

## 5. 배타와 E-stop — 지금 빠져 있다

`Activity.TELEOP` 를 새로 만든다.

```python
Activity.TELEOP: [TRAINING?, INFERENCE, RECORDING, DATASET_EDIT]
```

- **추론·녹화와 배타** — 같은 팔을 둘이 밀면 안 된다
- **`ESTOP_TARGETS` 에 넣는다** — 팔이 움직이는 활동은 전부 대상이라는 refactor #10
  의 규칙 그대로다. 릴레이도 조그도 게이트웨이/robotd 안의 루프라 PID 로 죽일 수 있다
- 학습과는? GPU 를 안 쓰므로 **막지 않는다**

> ⚠ 리더암 모드에서 E-stop 이 걸리면 **릴레이만 멈춘다.** 리더는 여전히 손에
> 끌리는 대로 움직이고, 팔로워는 마지막 명령 자세에 선다. 그게 맞는 동작인지
> (아니면 토크도 끊어야 하는지) 사람이 정해야 한다 — §7.

## 6. 순서

| # | 작업 | 왜 이 순서 |
|---|---|---|
| 1 | `Activity.TELEOP` + `ESTOP_TARGETS` + 배타 가드 | **먼저 한다.** 팔을 움직이는 코드를 넣기 전에 멈추는 길부터 |
| 2 | B 관절 조그 (manual-control §2 구현) | 깔린 길에 소비자 하나. 가장 싸고, 셋 중 가장 안전 |
| 3 | A 리더 릴레이 (녹화에서 떼어내기) | 알고리즘이 이미 검증돼 있다 |
| 4 | C 엔드포인트 + 작업 공간 상자 | 필터가 안 걸리는 유일한 모드라 **맨 뒤** |
| 5 | 한 화면에 셋 묶기 | 앞이 다 되면 UI 는 얇다 |

각 단계가 독립으로 쓸 만하다 — 2까지만 해도 "추론 없이 팔을 움직인다"가 된다.

## 7. 정해야 할 것

- **리더 모드에서 E-stop 이 무엇을 해야 하나** — 릴레이만 멈출까, 팔로워 토크도
  끊을까(끊으면 중력으로 처진다), 리더를 슬레이브로 되돌릴까
- **작업 공간 상자의 초기값** — 팔 컨트롤러가 자체 한계를 갖는지 실측 전까지는
  좁게. 실기에서 넓혀야 한다
- **C 의 좌표계** — `EndPoseCtrl` 의 원점과 축 방향이 베이스 기준인지 확인 필요.
  화면의 "앞으로"가 팔의 어느 축인지가 여기서 정해진다
- **양팔** — [bimanual](bimanual.md) 과 겹친다. 지금은 한 팔씩만 다루고,
  양팔 동시 조작은 그 문서가 서면 붙인다
