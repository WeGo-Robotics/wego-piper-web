# robotd 안전 층 — 기구학 기반 충돌 방지

[robot-transport.md](robot-transport.md)의 부속 문서. robotd 안에 FK와 충돌 필터를 넣는다.

## 결론 먼저 — `MotorsBusBase` 이음매는 그대로 맞다

기구학은 **robotd의 내부 관심사**이지 이음매의 위치를 바꾸지 않는다.

LeRobot 입장에서 "바닥으로 내려가지 않는 팔"은 **"관절 리밋이 있는 팔"과 구별되지 않는다.**
목표를 주면 실제 도달값을 돌려주는 인터페이스가 이미 그 의미론이고,
LeRobot 자체도 [`ensure_safe_goal_position`](../vendor/lerobot_robot_piper/lerobot_robot_piper/piper_follower.py#L148)으로
거친 버전의 같은 일을 한다. `Robot` 층으로 올려도 얻는 게 없다.

**단, 명령 경로가 fire-and-forget으로 끝나지 않는다.** 필터가 명령을 바꾸므로
"실제로 적용된 값"이 돌아와야 한다. [robot-transport.md](robot-transport.md)의 해당 서술을 수정한다.

---

## 왜 robotd인가 — 명령자가 넷이다

지금 팔에 목표를 주는 주체가 넷이다: 정책 추론, 텔레오퍼레이션 녹화, 웹 수동 제어, 파킹.
필터를 프록시 드라이버에 두면 **LeRobot 경로만 보호되고 나머지 셋은 무방비**다.

robotd에 두면 CAN으로 나가는 모든 명령이 한 곳을 통과한다. 구현도 하나다.
이 폴더의 판단 기준("한 사실이 두 곳 이상에 적혀 있으면 어긋난다")이 그대로 적용된다.

---

## 내부 구조

```
piper-robotd/
  ipc/          shm(state / action / applied), Redis 제어·텔레메트리
  safety/       ← filter(q_now, q_goal, cfg) → (q_applied, reason)   ※ 순수 함수
  kinematics/   ← URDF → FK, 링크별 충돌 지오메트리
  can/          piper_sdk 래핑
  daemon.py     루프
```

### 핵심 설계 속성 — 필터는 순수 함수여야 한다

```python
def filter(q_now: np.ndarray, q_goal: np.ndarray, cfg: SafetyConfig)
        -> tuple[np.ndarray, FilterReason]:
    """하드웨어 없이 호출 가능. 부작용 없음."""
```

이렇게 두면 두 가지가 가능해진다:

1. **하드웨어 없이 단위 테스트** — 경계 조건을 마음껏 만든다
2. **기존 데이터셋에 리플레이** — 이미 녹화한 에피소드를 필터에 통과시켜
   **"켰다면 몇 %의 프레임에서 발동했을까"를 로봇을 켜기 전에 측정**할 수 있다

2번이 특히 중요하다. 발동률이 높으면 필터가 아니라 캘리브레이션이나 지오메트리가 틀린 것이고,
그걸 실제 팔로 알아내면 위험하다.

## 기구학

### 선결 조건 — URDF가 없다

저장소를 뒤졌지만 URDF·xacro·메시가 하나도 없다
(`vendor/lerobot_robot_piper/asset/`은 PNG 3장뿐).
AgileX의 `piper_description` 패키지를 가져오거나 DH 파라미터를 직접 확정해야 한다.
**이게 1순위 작업이다.**

### 연산량은 문제가 아니다

- 6링크 FK: 4×4 행렬 곱 6회. numpy로 수십 µs
- 링크를 캡슐로 근사 → 평면과의 거리: 링크당 선분-평면 거리 하나
- **메시 단위 충돌은 하지 않는다.** 바닥면 방지에는 과하고, 1kHz에 안 맞는다

robotd를 **호스트 배포 + 가벼운 의존**으로 유지하려면 pinocchio 같은 무거운 것보다
**numpy 손구현 FK**가 낫다. 바닥 평면 하나면 그걸로 충분하다.

### 반드시 경로를 봐야 한다 — 끝점만으로는 부족

정책은 30fps로 **33ms 간격의 웨이포인트**를 준다. 그 사이는 팔이 내부적으로 보간한다.
목표 자세만 검사하면 **중간 경로가 바닥을 뚫고 지나가도 통과**한다.

두 가지 중 택일:

| | 방식 | 장단 |
|---|---|---|
| (a) **스윕 검사** | `q_now → q_goal` 구간을 N등분해 전부 검사, 걸리면 접촉 직전까지만 허용 | 구현 간단. 팔의 실제 보간 궤적과 다를 수 있음 |
| (b) **robotd가 보간을 인수** | 목표를 받아 robotd가 1kHz로 미세 웨이포인트를 직접 발행, 매 스텝 필터 | 실시간 개입 가능(엄밀히 우수). 작업량 큼 |

**(a)로 시작한다.** (b)는 (a)가 부족하다고 판명될 때 간다.

### 걸렸을 때 무엇을 할 것인가

거부(정지)는 정책이 계속 바닥을 향해 명령하는 동안 팔이 굳는다.
**접촉 직전까지 이동**(스윕에서 찾은 마지막 안전 지점)이 낫다 — 불연속이 없고 자연히 감속한다.

## 제약 — 필터가 켜진 채 녹화하면 데이터셋이 거짓이 된다

이 제약이 아래 "녹화 중 필터 오프" 설계를 강제한다.
LeRobot의 `lerobot_record.py`를 확인한 결과:

```python
# Action can eventually be clipped using `max_relative_target`,
# so action actually sent is saved in the dataset.        ← 주석의 주장
# TODO(steven, pepijn, adil): we should use a pipeline step to clip the action,
#                             so the sent action is the action that we input to the robot.
_sent_action = robot.send_action(robot_action_to_send)    ← 반환값을 버린다

if dataset is not None:
    action_frame = build_dataset_frame(dataset.features, action_values, prefix=ACTION)
                                                          ↑ 필터 이전 값을 기록
```

주석은 "실제 전송된 값이 저장된다"고 하지만 **코드는 필터 이전 값을 기록하고 `_sent_action`을 버린다.**
LeRobot 자체 TODO가 이 불일치를 인정하고 있다.

즉 **필터가 발동한 채로 녹화하면 실행되지 않은 동작이 데이터셋에 들어간다.**
그 데이터로 학습한 정책은 존재하지 않았던 궤적을 모방한다. 조용한 데이터 오염이다.

### 대응 — 녹화 중에는 필터를 끈다

wrapper는 이미 [`lerobot_record`를 몽키패치](../wrapper/start_record.py#L188)하고 있으므로
기록 라인을 패치하는 것도 기술적으로는 가능하다. 하지만 `record_loop` 내부라 패치 표면이 넓고,
LeRobot 업그레이드마다 깨진다. **권장하지 않는다.**

대신 **녹화 중에는 필터를 끌 수 있게 한다.** 녹화는 사람이 텔레오퍼레이션으로 하는 작업이고,
조작자가 안전 판단의 주체다. 그리고 실용적인 이유가 더 크다 — **작업 자체가 바닥·작업면에
접근해야 하는 경우가 많다.** 물건을 내려놓거나 집는 태스크에서 바닥면 필터가 계속 걸리면
데이터를 아예 못 딴다.

**이렇게 하면 위 버그가 무해해진다.** 변형이 없으므로 기록값 == 실행값이다.
LeRobot의 `_sent_action` 문제는 필터가 켜져 있을 때만 발생하는데, 녹화 중에는 꺼져 있다.

| 명령자 | 바닥면 필터 | 자기충돌 | 데드맨 | 하드 관절 리밋 |
|---|---|---|---|---|
| 추론 | ON | ON | ON | ON |
| **녹화(텔레오퍼레이션)** | **끌 수 있음** (기본 ON) | **끌 수 있음** (기본 ON) | **ON, 못 끔** | **ON, 못 끔** |
| 웹 수동 제어 | ON, 못 끔 | ON, 못 끔 | ON | ON |
| 파킹 | ON | ON | ON | ON |

**웹 수동 제어에는 오버라이드를 주지 않는다.** 조작자가 팔에서 떨어져 브라우저로 조그하는
상황이라 물리적 피드백이 전혀 없다 — 가장 위험한 경우다.
텔레오퍼레이션은 조작자가 leader 팔을 손으로 잡고 있어 사정이 다르다.

**데드맨과 하드 관절 리밋은 오버라이드 대상이 아니다.** "충돌 감지를 끈다"는
"소비자가 죽어도 팔이 계속 간다"나 "관절을 범위 밖으로 민다"와 다른 이야기다.

### 오버라이드는 만료되어야 한다

설정 파일에 한 번 적어두고 잊는 형태면 안 된다. robotd가 **TTL이 있는 명시적 오버라이드 리스**로
관리한다:

- 녹화 세션 시작 시 UI에서 명시적으로 켠다 (기본값은 꺼짐 = 필터 ON)
- TTL이 지나면 자동으로 필터가 다시 켜진다 (녹화 세션 길이에 맞춰 갱신)
- **robotd 재시작 시 살아남지 않는다**
- 오버라이드 중임을 UI에 상시 표시한다

## ⚠ 진짜 위험은 여기로 옮겨간다 — 녹화 범위 ≠ 추론 범위

필터를 끄고 녹화하면 데이터셋은 정직해진다. 대신 **새 문제가 생긴다.**

조작자가 필터 없이 바닥까지 내려가는 궤적을 녹화하면, 그 데이터로 학습한 정책은
**추론 시에 정확히 그 궤적을 재현하려 한다.** 그런데 추론에서는 필터가 켜져 있다.
→ 정책이 필터에 막혀 태스크를 완수하지 못한다. 그것도 조용히.

**즉 필터 설정이 데이터셋 계약의 일부가 된다.**

### 대응 — 리플레이 검사를 데이터셋 검증 단계로 승격

[위](#핵심-설계-속성--필터는-순수-함수여야-한다)에서 필터를 순수 함수로 두자고 한 이유가
여기서 두 번째 값어치를 한다. 녹화가 끝나면 **그 데이터셋을 추론 시 필터에 통과시켜 본다:**

```
데이터셋 검증 리포트
  총 프레임          12,400
  필터 발동 프레임      312 (2.5%)
  발동 에피소드        7 / 50
  주 원인            link5 바닥 여유 1.2cm 미달
```

발동률이 유의미하면 셋 중 하나다:
1. **필터가 과하다** — 바닥 여유를 실제 태스크에 맞게 줄인다
2. **녹화가 과하다** — 조작자가 불필요하게 깊게 들어갔다. 해당 에피소드를 뺀다
3. **캘리브레이션·지오메트리가 틀렸다** — 가장 위험한 경우

어느 쪽이든 **정책을 학습시키기 전에** 알아야 한다. 이 검사를 학습 시작 전 게이트로 두는 게 좋다.

> 이게 원래 계획했던 "로봇 켜기 전 발동률 측정"과 같은 도구다.
> 한 번 만들면 필터 튜닝과 데이터셋 검증 양쪽에 쓴다.

## 나머지 위험

### 정책 분포가 어긋난다

필터가 자주 걸리면 정책이 학습 때 못 본 상태로 끌려간다.
**발동률을 반드시 텔레메트리로 낸다** (프레임 대비 %, 어느 링크가 걸렸는지).
발동률이 유의미하게 높으면 정책이나 태스크 설정을 고칠 신호이지 필터를 느슨하게 할 신호가 아니다.

### 캘리브레이션이 틀리면 필터도 틀린다

FK는 관절 0점과 방향에 전적으로 의존한다. 캘리브레이션이 어긋나면
**안전하다고 판단하고 바닥을 친다.** [robot-transport.md](robot-transport.md)에서
robotd를 캘리브레이션 단일 소유자로 정한 것이 여기서도 맞는 이유다 —
FK와 캘리브레이션이 같은 프로세스에 있어야 한다.

기동 시 자체 점검을 둔다: 알려진 자세(파킹)에서 FK가 예상 좌표를 내는지.

### 텔레오퍼레이션에서 조작자가 못 느낀다

필터를 켠 채 녹화하면 leader 팔은 자유롭게 움직이는데 follower만 걸린다.
조작자는 발산을 손으로 느낄 수 없다 (Piper leader에 힘 피드백이 없다면).
**이것도 "녹화 중에는 끈다"의 근거 중 하나다.** 켜고 녹화할 때는 UI 경고가 유일한 피드백이므로
눈에 띄게 해야 한다.

주의할 점 하나 — leader와 follower의 **베이스 높이가 다르면** 조작자가 leader에서
느끼는 여유와 follower의 실제 바닥 여유가 다르다. 필터를 끄고 녹화한다면
조작자가 follower 쪽을 직접 볼 수 있는 배치여야 한다.

### 필터가 유일한 방어선이 아니다

관절 범위는 하드웨어에도 걸려 있어야 한다. robotd 필터는 **추가** 층이지 대체가 아니다.

## 명령 경로 수정 — applied ack

[robot-transport.md](robot-transport.md)에 "명령은 fire-and-forget, 왕복 없음"이라고 썼는데
필터가 들어가면 **적용값이 돌아와야 한다.** 세그먼트를 하나 늘린다.

```
piper.arm.<iface>.action     소비자 → robotd    goal_q, seq, issued_ns
piper.arm.<iface>.applied    robotd → 소비자    applied_q, ack_seq, reason, filtered_flag
```

프록시의 `set_action()`은 `ack_seq >= 자기 seq`가 될 때까지 기다렸다가 `applied_q`를 반환한다.
robotd 폴링이 1kHz면 최대 +1ms — 30fps 제어(33ms)의 3%다.

**타임아웃이 필수다.** robotd가 죽으면 프록시가 영원히 기다리면 안 된다 →
타임아웃 시 `DeviceNotConnectedError`로 깨끗하게 죽는다.

## 곁다리 — 나중에 EEF 액션 공간을 쓴다면

robotd에 FK가 들어가면 IK도 같은 자리에 놓기 자연스럽다.
LeRobot 정책이 관절 공간 대신 엔드이펙터 공간으로 액션을 낼 때
프록시 버스가 그 변환을 robotd에 위임하면 된다. **지금 할 일은 아니지만 구조가 막지 않는다.**

## 착수 순서

1. **URDF 확보** — AgileX `piper_description` 또는 DH 파라미터 확정. 선결 조건
2. `kinematics/` FK 구현 + **파킹 자세로 검증** (알려진 좌표와 대조)
3. `safety/` 순수 함수 필터 (스윕 검사, 바닥 평면 + 관절 범위)
4. **기존 데이터셋에 리플레이해 발동률 측정** — 로봇을 켜기 전에.
   여기서 바닥 여유 같은 파라미터를 실제 태스크에 맞게 조정한다
5. shm `applied` 세그먼트 추가, 프록시 `set_action`을 ack 대기로
6. robotd에 통합, **추론에서만 먼저 활성화**
7. 오버라이드 리스(TTL) + 녹화 UI 토글. 기본값 ON, 오버라이드 중 상시 표시
8. 데이터셋 검증 리포트를 학습 시작 전 게이트로 연결

4단계 전에는 실제 팔에 필터를 걸지 않는다.
6단계에서 추론만 먼저 켜는 이유는, 녹화는 어차피 끌 수 있으므로 급하지 않고
**추론이 필터가 실제로 필요한 유일한 경로**이기 때문이다 (사람이 안 보고 있다).

## 검증

- **FK 정확도**: 파킹 및 알려진 자세 3개 이상에서 계산 좌표 vs 실측 (줄자면 충분)
- **리플레이 발동률**: 기존 정상 에피소드에서 발동률이 0에 가까운지.
  0이 아니면 지오메트리나 캘리브레이션을 의심한다
- **의도적 침범**: 바닥 아래를 목표로 주고 접촉 직전에 멈추는지 (여유 거리 실측)
- **스윕 검사**: 시작·끝은 안전하지만 중간이 바닥을 지나는 목표를 주고 걸리는지
  — 끝점만 검사하는 구현이면 여기서 통과해버린다
- **지연**: ack 대기 도입 후 제어 루프 사이클 시간 변화
- **타임아웃**: robotd를 `SIGKILL` → 프록시가 매달리지 않고 죽는지
- **하드 리밋 독립성**: 프록시를 우회해 shm에 직접 위험한 값을 써도 robotd가 막는지

오버라이드 관련:

- **기본값이 ON인지** — 아무 설정 없이 녹화를 시작하면 필터가 켜져 있어야 한다
- **TTL 만료**: 오버라이드를 켠 채 방치 → 시간이 지나면 필터가 자동으로 돌아오는지
- **재시작 후 소멸**: 오버라이드 상태에서 robotd 재시작 → 필터가 켜진 상태로 올라오는지
- **범위 격리**: 녹화 오버라이드가 켜진 동안 **웹 수동 제어에는 적용되지 않는지**
- **데드맨 불변**: 오버라이드 중에도 소비자를 `SIGKILL` 하면 팔이 서는지
- **하드 리밋 불변**: 오버라이드 중에도 관절 범위 밖 명령이 막히는지
- **데이터셋 검증 리포트**: 필터를 끄고 녹화한 데이터셋에 리플레이했을 때
  발동 프레임·에피소드가 정확히 집계되는지
