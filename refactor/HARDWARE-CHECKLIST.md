# 실기 검증 체크리스트

`58c84b1` 이후 리팩터링(#1~#13 + 파라미터 프리셋 + 페이즈 라벨)에서 **하드웨어 없이는
확인할 수 없는 것**만 모았다. 자동 테스트 188개와 `npm run build` 는 통과한 상태이므로,
여기 있는 것은 "코드가 맞는지"가 아니라 **"실제 장치에서 같은 동작이 나오는지"** 다.

## 순서가 있다

**A → B** 를 먼저 통과해야 나머지가 의미 있다. B(wrapper) 가 깨져 있으면 C·E·F 는
전부 "시작이 안 됨"으로 똑같이 실패해서 원인을 구분할 수 없다.

| 단계 | 필요한 것 |
|---|---|
| A. E-stop | 팔 + Redis + 브라우저 |
| B. wrapper 3경로 | 팔 + 카메라 + 체크포인트 |
| C~I | 위가 통과한 뒤 |

## A. E-stop — 안전, 최우선

**이번에 구조가 통째로 바뀌었다.** 백엔드 asyncio 태스크였던
`services/estop_watchdog.py`(삭제)가 독립 프로세스 [`daemons/estopd.py`](../daemons/estopd.py) +
Redis 발행 [`estop_bridge.py`](../backend/app/services/estop_bridge.py) 로 갈렸다.
**백엔드가 죽어도 팔이 서야 한다**는 것이 이 변경의 전부이므로 실기 확인 없이는 신뢰할 수 없다.

기본값: heartbeat 500ms 주기, 타임아웃 **2000ms** ([config.py:101](../backend/app/core/config.py#L101)).

- [ ] **A1** `./dev.sh` 실행 → `Starting E-stop watchdog (estopd)...` 가 찍히고
      `ps aux | grep estopd` 로 프로세스가 보이는지
- [ ] **A2** Redis 를 내린 채 `./dev.sh` → `⚠ Redis 미실행` 경고가 뜨고 **추론이 시작은 되는지**
      (경고만 하고 막지는 않는 설계 — 의도대로인지 눈으로 확인)
- [ ] **A3** 추론 중 `redis-cli hgetall piper:activity:pid` 에 추론 PID 가 올라와 있는지
- [ ] **A4** **추론 중 브라우저 탭 강제 종료 → 2초 내 팔 정지.** 가장 중요하다
- [ ] **A5** **녹화 중 브라우저 탭 강제 종료 → 2초 내 정지.** 신규 동작 —
      예전 워치독은 추론만 죽였다 (`ESTOP_TARGETS = [INFERENCE, RECORDING]`)
- [ ] **A6** 추론+녹화가 아닌 상태(학습만)에서 탭을 닫아도 **학습은 안 죽는지**
      (E-stop 은 로봇을 움직이는 것만 대상)
- [ ] **A7** UI E-stop 버튼 → 추론·녹화 즉시 정지
- [ ] **A8** **백엔드(uvicorn)를 `kill -9` 한 뒤 추론 프로세스가 남아 있을 때 2초 내 정지되는지.**
      이 시나리오가 구조 변경의 존재 이유다
- [ ] **A9** heartbeat 가 끊겼다가 다시 붙으면 정상 복귀하는지 (오탐으로 계속 죽이지 않는지)

## J. 버스 전송 교체 — 3b-3 (신규)

ZMQ 소켓 3개를 Redis 로 바꿨다. 게이트웨이↔wrapper 왕복은 2프로세스 시뮬레이션으로
확인했지만, **실제 wrapper(LeRobot in-process) 안에서는 미확인**이다.

- [ ] **J1** 녹화 중 **건너뛰기 / 재녹화 / 정지** 버튼이 동작하는지.
      헤드리스라 이게 유일한 에피소드 제어 경로다 — 안 되면 녹화를 못 끝낸다
- [ ] **J2** 녹화 **웹 미리보기**에 프레임이 뜨는지 (카메라 여러 대 전부)
- [ ] **J3** 추론 중 슬라이더 → 즉시 반영 (로컬 · gRPC 두 모드)
- [ ] **J4** **세션 격리**: 녹화 A 끝에 정지를 누르고 곧바로 녹화 B 시작 →
      B의 첫 에피소드가 즉시 끝나지 **않는지**. Redis 리스트는 ZMQ 와 달리 살아남는다
- [ ] **J5** 추론 A 에서 슬라이더를 밀고 종료 → 추론 B 시작 시 그 값이 **안 새는지**
- [ ] **J6** `redis-server` 를 내린 채 녹화·추론 시작 → 시작은 되고 제어만 안 되는지

> **J6 의 안전 여부는 코드로 확인했다** — 버스가 죽어도 팔을 세우는 두 경로는 살아 있다:
> 수동 E-stop 은 [`estop_bridge.trigger_manual()`](../backend/app/services/estop_bridge.py#L101)
> 이 버스 왕복 없이 **먼저 직접 kill** 하고, 녹화 정지는
> [`recording.py:/stop`](../backend/app/routers/recording.py#L120) 이 `escape` 를 보낸 뒤
> 2초 안에 안 끝나면 **프로세스를 죽인다.**
> 잃는 것은 heartbeat 타임아웃 정지(estopd)뿐인데 그건 3b-2 부터 이미 Redis 의존이었다 —
> **3b-3 이 Redis-down 상황을 더 위험하게 만들지는 않는다.** 실기 확인은 동작 확인용이다.
